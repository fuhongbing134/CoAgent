# 工作台 Git 功能流程（待双审核及用户实测）

新流程由工作台直接调用共用 Git 核心，无需配置三份 Git MCP、host.json 任务绑定、审批文件或 ACL。旧 MCP 接口仅为兼容保留，MCP_SETUP.md 的旧手工 Git 步骤不适用于新流程。批准方案及实现边界见 [设计记录](../docs/GIT_COMMIT_SERVICE_DESIGN.md)。

## 用户操作

1. 在工作台对话中选择项目目录，提出功能开发要求。入口 Agent 在计划中声明编码阶段，工作台建立功能分支、安排非作者审核，通过后提交并推送该分支；不合入 main。
2. 只有仓库远端无法确定时，任务卡询问一次远端选择或 GitHub HTTPS 仓库地址，选择按仓库保存。已有单远端直接使用；现有远端的 fetch/push 目的地必须一致。
3. GitHub HTTPS 缺少可用登录时，点击任务卡“登录GitHub”，在 GCM 打开的浏览器中授权。不粘贴 token。需要 Git for Windows 的 Git Credential Manager 与 Windows 凭据存储；授权成功不意味着本地 .git 可写。授权过期可能再次提示。
4. 任务卡显示阶段、暂停原因与已产生的 commit。网络故障先由负责人分析；“重试原Git操作”只恢复原操作，先查询远端，再补推原提交，不重复编码或 commit。不明退出或不明工作区改动会保留现场，不自动清理。
5. 同一仓库另一功能排队，当前功能成功后自动唤醒；停止或结果未知时仍保留占用，须由 Agent 依据证据排查。立即停止阻止后续 Git 启动，不能承诺撤销已启动命令。

已有未声明阶段的历史计划保持原有行为，不会因为升级自动切分支或提交。新功能必须由入口生成含编码阶段的计划；普通讨论不触发 Git。一次 job 对应一个功能，修订仍交原作者，多个功能分别发起。

## Agent 协议

任务增量字段 `git_stage` 只能是 `code` 或 `revise`，不可自行报告作者身份；调度实际 agent_id 是作者依据。编码 Agent 不执行 Git 写操作。宿主在编码完成且退出确认后，创建绑定内容摘要的指定非作者审核调用。该调用返回标准协议，并附顶层：

```json
{"git_review":{"review_id":"宿主指定标识","approved":true,"issues":"无"}}
```

该片段只说明新增字段，不是完整协议。普通 completed、正文“通过”、作者转述均不构成批准。审核不得修改文件；需要修订时返回 approved=false 与问题，负责人追加原作者 revise 任务。hook 明确失败时保留本功能原暂存内容，核对后新开修订及审核；未知提交结果只查询，不盲目重试。

## 升级与回退边界

工作台启动后首次使用该功能时，经现有事务入口惰性创建四张 `git_*` 状态表；旧 schema v2、历史计划和旧审批文件不重写。状态存储在工作台数据库，用户不维护其中的字段。未登录或未开发前，仅查看状态不会调用浏览器。

停止功能后可回退本轮产品接线，但应先保留数据库、工作区和 Git 操作证据；旧版本不理解新阶段字段，不能让它自动重放未完成的新计划。不要删除占用或审批表来强行继续，也不要 reset、stash 或清空 index。开发分支与已产生的提交保留供核对。

## 待用户验证

审核通过后再重启工作台加载代码，并在目标环境分别让 Codex、DeepSeek、Grok 作为作者走完一项小功能。验证已有登录、缺登录浏览器授权、远端选择记忆、拒绝后修订、多轮提交、断网补推、立即停止和跨对话排队。逐次核对 main 未改变、功能分支推送可见、commit 对应指定非作者审核。当前自动化测试用临时仓库及脚本化 Agent，不能替代这些真实验收。
