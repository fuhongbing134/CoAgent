# 边界校验：解码不是字段契约

版本0.6；0.1两端独立检视无阻断；教学展示已作者自查；真实案例0.4经DeepSeek静态独立检视无阻断，本次说明澄清未另行独立复查。**前半篇强转反例是教学改写；文末REAL-INV-001是真实源码问题，建议改写未落地。**

适用：外部JSON或公开Python对象入口要求非空字符串，类型错误应拒绝而非自动修复。不适用：产品契约明确允许数字转文本，或已证明同一对象的同一事实经过验证且保证未失效的内部路径；不能以此要求每个内部函数重复校验。

### 好例：项目推荐写法（原文）

```python
def _text(value):
    if not isinstance(value, str) or not value.strip():
        raise ValueError("expected nonempty text")
```

`loads_payload`经JSON解码后进入`validate_payload`；后者也可直接接收Python对象。凡经`_text`的字段均受同一非空字符串契约约束，包括handoff值、questions项、blocked状态下的blocked_reason，以及计划结构中的task_id和instruction；这些调用分别位于`validate_payload`和`_validate_plan_structure`。JSON可合法表示数字、空字符串，解码只解决语法，不能建立此处非空文本保证。这里保留检查有明确契约依据，不是因为“多一道检查总更安全”。

### 反例：教学问题写法

```python
def bad_text(value):
    value = str(value)
    if not value.strip():
        raise ValueError("expected nonempty text")
```

`17`会成为`"17"`通过；它改变了应拒绝非字符串的契约。好处是原写法直接表达拒绝条件且不隐式转换；仅在上述契约下推荐，不声称所有系统都应拒绝转换。

### 教学改进对照：优缺点与场景后果

“改进后”即上方好例；不是项目真实修复时间线。

| 写法 | 优点 | 缺点／代价 | 适用条件 |
|---|---|---|---|
| 教学反例：先str强转 | 在明确允许转换的另一种契约下可接受数字输入 | 在本例严格文本契约下掩盖类型错误；多一次隐式转换 | 仅适合另行明确允许转换的接口，不能照搬到本例 |
| 项目好例：先判类型及非空 | 直接拒绝违约输入，判断与契约一致 | 调用者须自行提供字符串；不代替字段定位、业务含义校验 | 公开对象或JSON入口要求非空字符串 |

| 触发输入／场景 | 反例错误机制与可能后果 | 改进后行为 | 证据及剩余限制 |
|---|---|---|---|
| 字段值为整数17，但契约要求字符串 | str变为非空的"17"，本应拒绝却通过；可能使调用者类型错误更晚暴露或丢失明确诊断 | 原_text立即抛ValueError | 整数差异已内存验证；下游实际事故未发生验证，不声称必然错误调度 |
| 字段为空白字符串 | 两版strip后均为空并拒绝；此输入不能区分两版 | 同样拒绝 | 已验证原版拒绝；教学代码静态可见，不把相同结果说成改进收益 |
