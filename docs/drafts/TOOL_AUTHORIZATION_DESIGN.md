## 2. 背景与目标

此前 Git 的分支、提交、合入、推送由用户手动执行。entry-1994 讨论提出有条件开放功能分支写操作，并区分能力、授权与审核；entry-2000 中用户进一步询问如何将这些原则迁移到新增工具。

目标是让 Agent 知道已有工具能做什么、当前任务允许做什么、还需满足哪些条件。同类操作在已有授权范围内可复用判断，减少重复确认；出现新的目标范围或影响时重新核查。工具来自 CLI、harness 或 MCP，不改变这一原则。

范围包含判断原则、四级分类提案、能力目录字段及未来落盘安排。本轮不实现策略引擎、工具代理、MCP 服务、权限配置或审批系统，不自动连接工具，不执行 Git 写操作。

## 3. 核心原则及判断维度

1. **能力 ≠ 授权 ≠ 审核通过**：接口存在不代表获准使用；任务授权不代替领域审核；审核批准不自动授予发布或合入权限。实际执行还须满足环境权限。
2. 按具体操作、参数和目标判断，综合副作用、目标环境、影响范围、可逆性、敏感数据、费用及外部自动化，不按工具名字一刀切。
3. **只读不等于无风险**：读密钥后外发构成信息披露；查询可能产生费用或锁竞争。读取与外发须分别判断，不能因本地未写文件而忽略数据去向。
4. **可回滚不等于外部后果可收回**：恢复文件不能撤销已发送的通知、已触发的部署或数据披露。恢复方式应说明实际可恢复范围。
5. 已有授权覆盖当前目标和影响时不重复询问；范围扩大、信息不足或依赖新的决策时，继续独立可做的工作，先解决受影响部分的疑点。
6. 工具声明、能力目录和 Agent 自填等级都不是授权来源，也不能解除环境硬限制。不同工具执行同一动作，仍受同样的适用约束。

## 4. 四级分类提案

以下等级辅助判断，不是已生效的权限表；分类与授权依据分别记录。

| 等级 | 含义与执行条件 | 边界示例 |
|---|---|---|
| L0 查询 | 在已授权数据范围内读取，检查输出去向、费用及实际副作用 | 工作区读取与敏感数据外发分开；不默认开放所有数据 |
| L1 有限变更 | 任务已授权、目标明确、影响受控，可自主执行 | 限定工作区编辑或功能分支提交仍需避免覆盖他人内容 |
| L2 重大影响 | 生产、共享资源、外部发布等操作核对明确授权；已有授权充分时不重复询问 | 合入、推送、生产写入按目标及触发效果判断 |
| L3 超出常规 | 破坏性或边界不明的操作，不从一般任务推导授权 | 明确目标、影响和恢复边界；硬限制禁止的操作不能靠确认解除 |

不能把所有 reset 都称为不可逆破坏，也不能认为所有 push 风险相同。对未知接口先查证，不用较低等级替代证据。复合操作应检查完整影响链，不能拆成若干低等级步骤规避约束。

## 5. 与现有规范的衔接

- 非作者审核、功能分支隔离及 main 合入门槛按代码检视规范的适用范围执行，不能扩大为所有工具写操作都需要非作者批准。普通文档编辑、日程调整等遵守各自适用规则；代码审核单元中的相关文档仍按该审核范围处理。
- 代码检视规范 §3 约束分支隔离及 main 禁改，§10 是合入门槛；该规范没有 §16。作者可以提交代码，但提交不等于自审批准，审核证据须对应实际版本。
- 当前合入执行者由用户承担的安排不会因本草案改变。今后是否授权 Agent 合入、推送或连接服务，需要依据具体目标讨论，不能由工具可用性推导。
- 设计留痕规范约束本提案的背景、取舍、状态和后续演进；定稿与实施授权前不改代码或权限。本草案不复制代码检视条款，也不替代其门槛。

## 6. 能力目录最小字段

目录记录「事实 + 授权依据」，工具的安装说明或 Agent 自填等级不能使其自动获权。未确认字段标为未知，不填成已授权。

| 字段 | 最小内容 |
|---|---|
| 工具及操作 | 名称、接口或版本来源、具体动作；区分可调用工具与普通内部函数 |
| 目标范围 | 账户、项目、路径、环境及允许参数 |
| 影响 | 写入、敏感数据与外传、费用、通知、外部自动化及拟分类 |
| 授权依据 | 授权主体、原始依据、允许范围及有效期或任务边界 |
| 前置条件 | 适用规范、领域审核、必要检查及运行环境权限 |
| 验证及恢复 | 成功证据、失败处理、可恢复范围、不能撤销的后果 |

同类新工具在实际影响符合既有授权时可复用规则；新数据去向、新权限或新影响仍须查证。目录由谁确认、如何更新及失效，尚待讨论。

## 7. 当前架构事实与证据边界

| 层 | 已有证据或讨论来源 | 能支持的结论与限制 |
|---|---|---|
| Codex CLI | `web_chat.py:1933` 的 `run_codex` 构造 codex exec/resume 命令，指定工作目录及 sandbox，经 `run_managed_process` 执行 | 工作台启动 CLI，由其运行环境提供文件操作能力；未审计 CLI 内部实现及全部外接 MCP 配置，不能断言文件操作绝不经过其他 MCP |
| DeepSeek Harness | `web_chat.py:2072` 有对应后端入口；DeepSeek 在共享讨论中报告其 read/write/edit/glob/grep/pwsh 工具及 DSH 文件沙箱 | 具体工具来源和 read-only/workspace-write 沙箱细节依据 DeepSeek 自述，本轮未审计其外部 harness 实现 |
| 项目 MCP 消息桥 | `agent_bridge.py` 创建 FastMCP，暴露 register_agent、list_agents、send_message、read_inbox、read_conversation；`MCP_SETUP.md` 描述共享 SQLite 消息通信 | 已检查的该服务负责消息通信，不暴露通用文件编辑接口；不代表 MCP 本身不能提供文件工具 |

消息桥读取也可能带写入副作用：`read_inbox` 会更新已读时间并 touch agent。这是按实际行为而非接口名称分类的项目内例子。消息桥仅共享通过它发送的内容，不据此推断它能读取双方完整私有聊天记录。

四级框架与 MCP/CLI/harness 来源无关；服务连接的授权也按实际开放能力、数据去向与既有授权判断，不自动把所有连接固定为某一级。

项目可以自建工具，MCP 消息桥就是现有实例。但 `run_codex`、`finalize_message` 等内部函数不因由项目实现就自动成为 Agent 可直接调用的工具。自建接口仍需明确暴露方式、权限检查、目标边界、失败语义及验证；本轮不设计或部署这些接口。

## 8. 候选方案与落盘规划

| 方向 | 取舍 |
|---|---|
| 按工具名字逐个制定规则 | 简单直观，但同一工具的操作差异大，容易重复且难迁移；不作为主方向 |
| 只按副作用和可逆性四级分类 | 易记，但遗漏数据去向、费用和外部自动化；采用修正后的多维判断 |
| 通用规则与能力目录分开 | 当前倾向：规则说明如何判断，目录记录实际能力与授权事实；需防止目录过时及自填获权 |

若后续定稿，通用规则拟落为独立 spec 并登记规范索引；能力目录另列，引用通用规则及适用领域规范；BACKLOG 仅跟踪未实施事项，三者互相引用。位置、命名和是否立即落 spec 尚待决定。本轮不创建 spec、目录模板或 BACKLOG 条目。

## 9. 后续核对方式、结果与待决问题

本轮结果仅为设计草案落盘，未实施、未测试工具授权机制、未改变权限。后续可用工作区编辑、功能分支提交、消息桥已读写入、敏感查询及外部发布等场景核对：是否识别完整影响、已有授权是否被正确复用、领域约束是否保留、未知事项是否明确披露。这些是验证计划，不是通过结果。

待详细讨论：

1. 四级名称和边界是否定稿，是否足够支持复合操作？
2. 能力目录存放位置、维护者、证据更新和授权失效规则是什么？
3. 是否立即落独立 spec，还是先保留草案并用少量场景检验？
4. 自建工具首批登记范围是什么：消息桥、Git 操作还是文件接口？
5. 如何确认各 Agent 实际工具、沙箱限制与额外 MCP 配置，避免把能力声明当作已验证事实？

保留风险：分类不能独自强制执行权限，文字规范不能代替工具端检查；目前没有证据证明四级覆盖所有未来工具或是最优分类。
