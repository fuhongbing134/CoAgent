## 3. 独立判断与候选取舍

Codex主张：支持按职责拆分；支持在可证明的契约边界完成校验并避免内部重复；支持将删除测试追问作为每个相关分支的审查动作，但不将现存测试作为必要性的唯一裁判。现存测试可能漏掉需求，分支也可能仅维持性能或清理义务；无失败测试应触发查证，而非自动删除或自动补一条镜像测试。

备选A：保持单份、仅加分章，引用简单但不满足用户拆分目标，暂不推荐。备选B：两份按作者与独立检视／合入分工，共享规则单一来源、另一份引用，推荐供讨论。备选C：再拆独立合入规范，会增加第三份与交接成本，当前无必要，不推荐。

### S1. 文件、职责及交接候选

- 编写规范拟名CODE_WRITING_SPEC.md、id code-writing-spec：作者编码、缺陷修复、自查、验证和返修；输出可审核单元及完整证据。自查归编写职责，不赋予作者自批资格。
- 检视规范保留CODE_REVIEW_SPEC.md、id code-review-spec：非作者审核、累计全量复查、批准与合入门槛；合入执行者职责保留在其中，名称不应让人遗漏操作门槛。reviewer修改待合入代码后重新判定作者资格。
- 作者引用检视规范的请求模板及合入规则；检视者引用编写规范的编写约束并独立核对，不以作者自查替代。双方直接引用需求、设计、执行等适用专项，不建立互相要求先完成另一份的循环前置。
- 请求与证据流：作者自查及验证→提交明确基线／版本、来源与图文影响→非作者独立检视→作者逐项返修→相同基线累计全量复查与回归评估→实际版本有效批准→合入者核门槛及已有操作授权。缺证据不标通过。

### S2. description候选（非生效文本）

编写：开展代码编写、代码缺陷修复、作者自查及返修时，约束作者核对有效需求与适用设计、维护输入边界与内部契约、编写必要代码及验证，并提交与具体版本绑定的改动说明、测试及图文影响证据，直至形成可交接独立检视的审核单元。作者自查不代替非作者批准，独立检视及合入门槛由代码检视规范负责；纯讨论或无代码变更任务不适用。

检视：开展代码变更的非作者检视、返修复查、批准及合入时，约束检视者独立核对用户期望、实现与验证证据、分支必要性及累计全量改动与回归影响，并约束合入执行者确认实际版本有效批准及合入门槛。作者编码与自查由代码编写规范负责；纯讨论或无代码变更任务不适用，审核批准不代替合入操作授权。

## 4. 防御代码候选条款

### B1. 边界校验与内部契约（拟入编写规范）

在数据、控制或资源进入信任与契约边界时，完成与调用者可依赖契约相关的校验／规范化，明确有效形态及错误行为。边界按数据来源与约束定义，不按函数层级：外部请求、持久化读入、第三方结果、公开入口均需按实际信任程度判断。同一已校验事实、同一数据及有效期内，内部依赖契约，不重复校验或添加“以防万一”的默认回退。

对象被修改、跨并发或事务时序、权限或环境状态变化、进入新的信任域时，先判断原保证是否仍成立；需要的检查须点名新事实及失效原因，不以“安全起见”泛化。公共函数有未经过上游校验的其他合法入口时，本身可能是边界；须核调用关系，不凭一条路径删除其验证。

### B2. 分支用途区分（拟入编写规范，review引用）

- 输入校验处理契约外数据；业务分支处理契约内不同合法场景，两者不能混同。
- 不变量断言用于暴露内部错误，不应重复用户输入校验；保留须说明不变量、失效来源及诊断价值，不能依靠可被禁用的断言承担必要输入／权限校验。
- 外部调用在输入有效时仍可能失败，异常处理须对应具体错误及有意义的恢复、传播或清理行为；不吞掉意外错误并假装成功。
- 资源释放、事务回滚与生命周期处理按资源契约判断，不能因入口校验已通过而删掉。
- 删除确认不可达、被已有保证涵盖且没有独立用途的防御；保留检查须有场景及依据，不保留纯猜测的未来需求。

### B3. 删除测试追问（拟入检视规范）

检视审核单元内每个if／except／assert及等价条件、提前返回等分支时，追问：“删掉或改变它，会破坏哪个用户场景／契约？哪个现有测试会失败，失败断言是什么？”结合相关未改代码判断，不扩展为全仓逐分支审计。相同契约的分支可合并说明，但须覆盖各分支，不强制逐行日志或新增固定表格。

能指出测试时仍核测试是否断言真实目标，而非恒真、过度模拟或仅复制实现。回答不清时不得直接认定死代码，也不得只以覆盖率或“有测试”关闭问题。

### B4. 无测试答案后的处置（拟入检视规范）

1. 核对需求、输入来源、全部相关入口、状态与资源契约，构造可达场景并检查预期结果。
2. 有必要且可达的场景，但现有测试捕捉不了删除后的差异：属于验证缺口，补有意义的行为断言或修正失真测试；按风险选择集成、故障注入或其他适用验证，不为一行实现凑测试。
3. 已有保证可证明分支不可达或与上游重复，且没有独立效果：提出删除，说明证明范围及回归检查。不可达并不自动代表可删，例如暴露契约破坏的诊断断言需单独评估。
4. 难以可靠触发或自动化的必要情形：提供具体场景、替代证据、限制及未覆盖风险，由reviewer判断充分性；关键验收缺失不能靠解释豁免。自动测试不是唯一证据，但必要性不能仅靠作者口述。
5. 无法判断必要性或测试有效性：结论为证据不足，补定向查证；对影响正确性或关键场景的问题不得批准，不将未知写成死代码或通过。

备选：强制所有分支都必须有删除即失败的自动测试，能强化可检验性，但会诱导镜像测试，且性能短路、诊断与难注入故障未必由现有功能测试区分，暂不推荐。反向备选：只说明“有用”不查测试，过弱，不推荐。候选B3—B4保留测试追问的力度，并以真实目标和证据充分性收尾。
