## 10. 用户授权的正式修订方案（entry-4687）

### 10.1 已确认需求与成功判据

用户同意以“职责单一来源”为目标：每项规范义务有一个权威正文；不同规范可在同一需求的不同动作/阶段互补适用，但不得重复规定同一项义务。不得把适用场景强行做成互斥集合。用户随后授权 Codex 组织落地，并在实施后由 DeepSeek Harness、Grok 独立全量审视全部规范。

已确认的状态与阶段规则如下：

- 生命周期仅追踪需求提出至需求落地，不延伸到运行反馈、持续运行变更或退役。
- 每条需求单独维护一份文档型状态记录，置于 `docs/requirements/tracking/`；需求定义/基线仍由 `docs/requirements/` 中正式需求文档承载，状态记录链接证据，不复制正文。
- 主状态为 `待澄清 → 已基线 → 设计中 → 设计就绪 → 实现中 → 待检视 → 待验收 → 已验证`。合入、发布是单独事实，仅按任务适用时记录，不与“已验证”混同。
- 当前阶段负责人依其阶段证据推进状态；状态变化记录责任人、时间、依据及相关产物版本。
- 阶段结束以适用交付物齐备、阶段验收判据有证据、状态记录已更新为标志。简单修复可合并记录或裁剪不适用交付物，不强造设计文档。
- 严重问题指影响需求达成、接口契约或关键验收标准的问题。按根因回到受影响阶段；返修后所有受影响修改和验收结论重新验证，通过后才继续。仍适用且确认未受影响的证据可复用并记明依据。
- 代码作者自测、非作者检视、合入、需求验收、部署发布各自是不同职责/事实；无部署交接不要求部署说明，无实质复盘事项不要求每项实现都产出复盘。

### 10.2 规范边界与本次修订范围

当前候选职责图为：`task-execution-spec` 是跨阶段导航、统一状态和回退/重验框架的唯一权威来源；`requirements-analysis-spec` 继续唯一负责需求基线内容及目标/范围/验收变化回流；`design-decision-record-spec` 负责有设计取舍时的设计记录、设计阶段交付物及实现授权；`code-writing-spec` 负责作者实现、自查和可交接审核单元；`code-review-spec` 负责非作者独立检视、批准与合入门槛；`document-management-spec` 负责维护文档的归位、索引、状态与历史，以及规定触发的复盘落稿；`agent-discussion-spec` 只约束协作讨论过程。规范可被同一任务多次触发，但正文义务不复制；跨规范引用应指向权威条款。

拟正式修改：

1. `specs/TASK_EXECUTION_SPEC.md`：扩充 description、适用边界及 §1/新增导航章节，承载阶段地图、最小阶段门、每需求统一状态字段与迁移、按根因回退及受影响证据重验规则；清理已有重复的跨阶段检查表述，保留必要通用执行条款。
2. `specs/REQUIREMENTS_ANALYSIS_SPEC.md`：仅增加与统一状态记录的交接链接/引用；不复制状态机，不改其需求基线权威职责。若审查确认不需要增加任何义务性条文，则只保留引用关系并说明理由。
3. `specs/DESIGN_DECISION_RECORD_SPEC.md`：仅以交叉引用说明设计阶段结束证据/实现授权与统一状态的关系；设计正文仍是设计交付物权威来源，不重复状态推进规则。
4. `specs/DOCUMENT_MANAGEMENT_SPEC.md`：仅澄清 tracking 状态文档的归位/索引服从现有文档管理义务；不把需求状态含义纳入文档管理职责。

6. 新建 `docs/requirements/tracking/README.md` 与单需求状态记录模板；不为现存需求推断/预填状态。

### 10.3 Description 与适用边界审视办法

全量审视时按“义务/动作”而不是按“大任务”比较各规范：给每项义务标明唯一权威规范，再检查其他文件是否仅作边界引用。对每个 description、`applies_to`、`not_applies_to` 和 `depends_on` 检查是否简洁、相互一致、足以排除明显不适用动作，并列典型适用/不适用场景。若同一任务跨阶段触发多份规范，需说明不同义务，不据此认定重叠；若两份正文对同一义务均作规范性规定，应收敛到一份权威条款，其他处改为引用。修改任何 description 时必须同次同步索引的逐字摘要及版本历史。全量审计发现但不影响本次导航/状态/职责边界的独立优化，仅登记候选，避免扩大范围。

### 10.4 实施与复核顺序

先将本方案与授权写入讨论草稿并同步草稿索引，再修改正式规范和状态目录；完成后回读所有受影响文件并核对元数据、内部引用、description/索引一致性、状态迁移、阶段门与历史。随后由 DeepSeek Harness 和 Grok 依次独立审计七份规范及 `specs/README.md`；第二位不引用第一位结论。Codex 逐点综合并仅修复属于本次授权范围的明确缺陷，其余优化形成证据清单交付用户。正式修订不等于已用真实需求案例验证行为效果。

## 9. 用户对状态记录与规范范围的补充确认（entry-4669）

### 9.1 已确认决定

- **生命周期边界**：统一需求状态只追踪该需求从提出到落地；不纳入运行反馈、后续运行变更或退役管理。
- **状态主线**：用户接受三方建议的候选状态集合，作为后续正式方案的基线：`待澄清 → 已基线 → 设计中 → 设计就绪 → 实现中 → 待检视 → 待验收 → 已验证`。合入、发布等如适用，作为独立事实/状态记录，不与“已验证”混为一项。此处记录用户接受的方案方向，尚未写入生效规范。
- **记录粒度与责任**：每条需求单独维护一份文档型状态记录，阶段负责人依据本阶段证据推进；不设置固定全程状态管理员。
- **严重问题与返修**：严重问题判据采用“影响需求达成、接口契约或关键验收标准”。返修后，所有受影响的修改均须重新验证，确认验证通过后才继续下游阶段；旧验证结论不得覆盖或冒充新验证。
- **轻量任务**：简单修复不为满足形式而强造文档；可在已有合适记录中合并承载。
- **规范审视范围**：后续讨论每份相关规范时，除评估新增内容外，还须审视现有条款能否优化或合并；description 须精简并准确划定各规范职责。

### 9.2 状态文档与证据建议

现有 `docs/requirements/` 已作为正式需求分析文档目录，并有自己的入口索引。用户已接受新增专用子目录 `docs/requirements/tracking/` 的方向，用于存放每条需求的状态记录；建议按稳定需求编号命名，并在子目录入口索引中列出需求、当前状态和记录链接。这样可将“需求定义/基线”与“跨阶段状态追踪”分开。目录尚未创建，文件模板和索引字段仍待正式改规方案确定。

用户列出的阶段实物适合作为证据入口，但仅有“存在某个文件/代码”不足以证明状态可推进。状态记录应引用对应阶段产物的路径、版本或提交标识，以及针对验收标准的结果：澄清记录需能定位需求来源和基线版本；设计记录需标示需求符合/偏离/未验证及实现交接；代码记录需关联作者验证结果；检视意见需绑定被检视版本；验收结果需逐条对应需求判据。状态变化还需记录推进人、时间、依据及受影响下游结论，避免复制整份材料。

返修后按根因回到受影响阶段；重新验证所有受影响的修改和由其影响的验收结论。未受影响且仍适用于当前版本的独立证据可复用，但须核对适用范围；有疑问则重新验证。这个细化旨在落实“相关修改均重新验证”，同时不把无关项目误判为受影响。

### 9.3 description 唯一性的含义与当前判断

用户要求description精简，且各规范对应场景唯一。现有索引明确允许不同职责、不同阶段的规范衔接；requirements正文也指出，一项跨阶段任务可先后或同时受不同专业规范约束。因此“唯一”若解释为**责任范围不重复、各自职责和排除项能清晰区分**，与现有结构相容；若要求同一工作项只能适用一份规范，则会与现有跨阶段衔接方式冲突。初步看，现行规范在主要职责上已有区分，但“当前是否足够合适”不能仅凭description摘要确认：还需按 `applies_to`、`not_applies_to` 和正文审计边界及具体误用风险。不能仅因一份规范被引用或作为背景参考，就认定它对该动作 `must_follow`。

### 9.4 当前适用边界的初步压力检查

目前可见的分工有合理基础：`requirements-analysis-spec` 管需求基线和变化回流，明确不负责技术方案选择、代码检视和文档生命周期；`design-decision-record-spec` 排除纯问答、无设计取舍的简单修改；`code-review-spec` 排除纯讨论和无代码变更；`agent-discussion-spec` 排除单 Agent 且无协作讨论；`document-management-spec` 排除纯阅读、临时探测物和一般一次性日志。`task-execution-spec` 则有意覆盖各类实质跨阶段工作，但明确不替代这些专项职责。

这些规范会在同一个较大任务中同时适用。例如，形成需求文档时，requirements 管需求基线内容，document-management 管文档归位/索引，task-execution 管证据和停止条件；这是职责互补，不是天然误用。但若把“任务里出现了设计/代码/文档”当成某规范适用的唯一理由，就可能误用：例如仅改错字却套用完整设计决策流程、纯讨论强制启动代码检视、仅阅读文档却触发文档维护义务，或用 task-execution 代替需求/设计/检视专项检查。现有 `applies_to`/`not_applies_to` 能提供排除依据，但索引级长description和缺少统一正反例，不能保证执行者每次都正确判定。

**初步结论：**职责架构总体合适，且已有若干明确排除条件；但尚无证据证明所有规范的适用边界已经互不重复或能充分防止明显误用。后续全量审视应以“具体动作/阶段”为单位，而非把整项任务强行指定给单一规范；逐份补查典型适用例、典型不适用例、交叉触发理由和相邻规范的责任接口，并检查description是否可精简。若发现同一责任被重复规定，合并或收窄；若只是同一任务触发多个不同职责，保留并写清分工。此为审计建议，尚未修改正式规范。

### 9.5 后续正式修订建议映射

继续优先由 `task-execution-spec` 承载端到端导航、统一状态记录的最小字段/推进条件及回退后复核框架；requirements、design、code-writing、code-review、document-management 分别保留需求基线、设计与授权、作者自查、独立检视/合入、文档归位与复盘职责。对每份候选规范逐项做职责边界审计：现有条款、description、applies_to/not_applies_to、depends_on、交叉引用及可合并重复内容一并检查；同步 `specs/README.md` 的摘要和版本/历史。以上是后续讨论输入，不构成正式修改授权。
