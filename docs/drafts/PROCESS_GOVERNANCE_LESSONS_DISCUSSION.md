## 4. 记录格式候选与转正边界

问题记录可用§3表或同字段小节，须让读者不离开文档即可知道原问题；来源精确到job、任务／调用或文档锚点，无法定位时明确缺失，不虚构链接。接受状态可用接受／部分接受／反对／待定，并说明由谁、何时决定；尚未发生的用户决定写未发生。

变更历史候选统一为：时间（含时区）｜版本／议题｜原状态或决定→新状态或决定｜改变原因与证据｜提出／决定者及来源｜影响范围。新增稿原状态写“无”，小修改可同批合并但须能定位改动，不要求制造实质决策。本格式尚待讨论，不在本稿制定全局生效规则。

正式文档候选仅展示各点选定方案及依据、可选提出者和关联草稿；备选／异议／原问题留在可访问草稿。转正需明确决定依据，草稿保留且与正式文档双向关联，不能只迁走并覆盖正文。是否逐文档批准、已有授权何时足够、错字如何轻量处理，均待论证。本次用户要求草稿落盘已直接执行，其余未来规范条款尚未编写或生效。

## 9. Codex综合候选与可执行示例

### C1 全覆盖、按任务合并的前置草稿

独立判断：U1目的合理，文档数量不是合理成本单位；但“低成本”不能推导出无草稿。推荐所有人工维护文档新增／修订均先有落盘草稿，允许同任务多文件合写，不强制每文件副本。新主题在drafts建稿；讨论首次落盘就是草稿起点，无需为草稿另起草稿；后续意见追加历史。既有正式文档修订先在关联修订稿写拟改段落或补丁、原因、目标位置及处理依据，再更新正式文档。小改可以同一条完整记录，不要求全篇复制或新审批。

四例：新设计先落主题草稿；README错字在已有主题修订稿写“原词→新词、来源、接受及理由、目标文件”后改正文；执行中→中断先记事实时间和证据，再同步正文与索引；纯发散讨论直接写为草稿、可不转正。索引本次条目也由本主题稿承接，不另生索引草稿。转正冻结本次草稿基线并双向链接；新需求走下一修订段／稿，不让旧草稿追着正式文档永久更新。仅记录版本号却不能找回内容不够；应保留原正文或必要差异以重建所引用决定。

H-R1收口：没有关联主题时，默认载体拟定为持续草稿 `docs/drafts/MAINTENANCE_REVISIONS.md`，首次真实维护任务再创建，本轮未创建该文件。先追加时间、来源、目标文件／位置、原文→拟改文、接受状态、理由／证据及实际备选，再改正式正文；完成后追加结果与统一历史。例（仅示意，不声称README存在此错字）：“目的：修正用词；范围：README.md该句；拟将‘任意使用’改为‘可任意使用’；来源：阅读发现；接受：是；依据：表达更准确；备选：未发现更优选择。”若已有主题稿覆盖此目标，优先写其修订段。草稿自身的状态头、历史与关联索引由同一修订承接，不再套一份草稿。相比正式文件内事后历史，此载体保留前置阶段；相比逐错字独立文件，避免文件膨胀。

生成JSONL／机器产物是否属于“所有文档”是用户未明确的边界：推荐说明它们是原始证据，生成目的、格式及解释性报告有前置草稿，原始事件不能先编造草稿。此为建议边界，未经用户决定不将X类豁免写成规则。既有历史不追溯伪造，仅从下一次修订留稿并披露旧缺口。D/M/X可帮助分类记录深度，暂不接受用来取消人工维护文档的草稿阶段。

### C2 草稿完整过程，正式文档简洁决策

问题用具体句写清来源、条件、原主张、是否接受、理由和方案位置；各自映射可辨认时允许归组。确有更好选择或实际比较过的备选，记录优势、代价及不选原因；未发现则可简记，禁止为模板虚构。问题追溯使用§8形式，所有文档变更历史推荐统一§7列；正式正文仅列各点选择、依据和可选提出者，关联固定草稿基线，争论及被拒方案不重复搬入正式正文。必要的正式文档状态和历史链接仍保留。

### C3 两份过程规范与明确交接

候选文件名：CODE_WRITING_SPEC.md（新编码规范）与CODE_REVIEW_SPEC.md（缩为检视规范）；名称及新版本尚未定。编码规范只要求作者：分支隔离、设计对应、可读实现与必要说明、自查和隔离验证、形成审核包、逐项返修。检视规范只要求reviewer：独立性、检查基线与累计改动、证据有效性、评论分级、批准／需修改／证据不足、全量复审与批准失效条件。作者在编码规范读取反馈并返修，reviewer在检视规范复查，双方不用互相承担对方过程。

审核包含基线／版本、目的和范围、改动与设计映射、自查及测试、未测项、文档影响；输出是绑定该版本的检视结论。共用目标基线、讨论和文档义务引用既有单一来源，不复制全文。

G-R2收口：合入执行者是消费批准结论的角色，不必新设Agent。检视规范交接段标明结论交给负责人指定的合入执行者，审核批准不授予操作权限；执行通则限定小节规定该执行者如何核对目标、获批版本和已有操作授权。编码规范的提交交接只说明作者提供哪个版本供审核及后续消费，不定义批准或合入操作。角色接口可引用，批准有效性仍只在检视规范定义。

合入分两层：有效独立批准的条件归检视规范；合入执行者核对目标分支、实际内容、授权、阻塞项及回退等操作归现有执行通则的“仅代码合入适用”小节，是Codex优选。Grok方案把全部门槛留检视规范优点是集中，但若直接约束合入执行过程会偏离U3；备选独立第三份合入spec边界更清楚但增加维护，暂不推荐。此分配待交叉回应及用户决定。

落地前须逐条建立旧§1—§14→新条款／已有单一来源的去向表，尤其独立批准、累计全量复审、图文同步和证据绑定不得丢失。检索并更新当前spec索引及depends_on、AGENTS和现行设计引用；旧聊天／历史正文不改写，旧完整规范先保留为有日期与后继链接的历史基线，再明确当前入口。不能在旧路径无说明换语义后声称历史引用仍指原文。拆分同步生效与过渡版本均须有批准依据，不出现两份互相定义同一义务的循环。

### C4 正式长跑前的可审检查点

对为正式证据编写的自制并发／故障／耗时工具：先实现＋作者自查＋有限隔离冒烟，交非作者检视隔离、oracle、同步与统计后，再跑昂贵长矩阵；数据产生后独立复核原始数据至结论。可审版本不依赖全矩阵完成。工具实质改动后重新判断检视及既有样本有效性。不是要求每条普通单测都先获批准，也不是把长跑前检视当作全部验收通过。E3所示失败依赖须有承接：停跑、保护证据、记录未审状态、安排短批恢复，不能以自动任务失败静默免审。

采纳Grok的适用限定：同时满足“新写或实质修改自制工具”“结果拟作正式证据”“运行昂贵或隔离／oracle／统计难以事后核对”才触发此检查点。现有项目单测、提审前隔离冒烟、不作正式证据的一次探测，以及已审工具不影响上述性质的参数变动不自动新增门槛；参数若改变证据有效性仍须重判。工具自测随同审核包，不为自测再设一层长跑审批。

### C5 先分析再实施，按风险决定深度

默认负责人承担类似产品经理的职责，先回答目的／合理性／方向／优先级／范围／验收／未知项，结果写同一主题草稿并随instruction传递。轻任务可一句说明，标准任务给短分析；改规范、重大范围、昂贵或不可逆动作、关键歧义、同类失败或明显自证风险时由现有非实施者独立挑战。仅“负责人也将编码”不自动增加一个分析任务；独立代码检视仍照常。

H-R2收口：轻档最低一句必须含“目的：解决什么；范围：本次只改什么”，不能以“按要求处理”等空话代替。例：“目的：消除README用词歧义；范围：只改该句，不改变功能承诺。”缺目的或范围时先补分析再执行依赖步骤，已有授权不因此重复询问。该分析与前置修订稿合写即可。

执行前显式反馈理解和建议；已有具体授权足够则继续，目标、范围或验收改变／关键歧义影响下一步才等待用户裁决。分析者只能建议不能替用户改需求；内部一致不能新增授权。本次可继续综合和交叉讨论，不必再问用户是否允许讨论；本轮未授权直接变更生效规范。优先级给价值、风险、依赖和成本依据，不凭内部兴趣无限发散。新增固定PM身份作为替代，当前没有证明其额外收益。

### C6 状态及教训的可检查责任

文首简记状态、更新者／时间及事实依据；历史仍保留。负责人在任务失败、取消、阶段交付与恢复时核对文档、索引和待审项，保证“已计划／已实现／已验证”不互换。E2/E4是执行遗漏，不能仅加字段就宣称治愈；后续应以一次真实文档修订和一次短批工具流程观察是否降低遗漏，不在本轮伪造效果数据。
