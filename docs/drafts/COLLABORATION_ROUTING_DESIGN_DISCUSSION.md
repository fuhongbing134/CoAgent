## 1. 背景与需求基线

本设计消费 REQ-004／1.5，不重建需求基线。需求目标是减少协作入口中的角色错配、非法/悬空任务、失败后无法恢复和无意义等待，并支持授权任务实际并行及输出归属清楚。基线中的 R1–R8、A1–A8 是后续设计与产品验收依据；本稿不把讨论意见当成验收结果。

现有源码证据由需求基线 §2.1 与本轮只读审阅共同限定：协作主路径取 `ready[0]` 顺序执行；批次层的并行接口不证明主入口已并行或共享写已隔离；`finish_run` 接受 `not_started`、`confirmed`、`unknown`，但运行记录只持久化 `exit_confirmed` 布尔，`unknown` 转为 `quiescing`。Grok 追踪到协作目录未消费 `exit_evidence`/`exit_confirmed`。各适配器是否始终把真实三值传到 `finish` 尚未端到端核验。

**对基线的判断。** 采用 REQ-004 1.5 的 R1–R8。U1 固定 180 秒，持久受理须严格早于截止，恰好截止归到期且自动释放零次。U2 失败恢复保留现场，关闭回退及其判定、授权、占额和授权沿用分支。具体失败分类、退避与 U3 通道能力仍待设计或验证。

## 2. 范围与约束

本稿比较设计候选并提出依赖顺序，不形成新的实施计划、部署/回退承诺或代码授权。§4.47 定义派发关联、接纳与并行的逻辑契约，具体接口与迁移实现留待后续；不扩大用户已决定的 U1/U2 原则去填补未决边界；不宣称 U3 的通道能力已具备；不复活旧 C1–C7 技术选择。

## 3. 候选方案与取舍

### 候选 1：按正确性风险与依赖递进（推荐提案）

先处理角色、授权、任务关系、协议校验和收尾约束（R1–R5/R8），再在这些前提上设计 R6/R7 的实际并行和分别输出。这里的“分层”只表示设计依赖和风险检查顺序，不表示各层可独立验收、回退、分批交付或已获实施授权。R6 依赖 R2/R5/R8 的授权与依赖安全；R7 与 R6 必须在同一次用户效果验收中验证。

关键行为约束候选：为任务及尝试保留稳定身份/世代；旧尝试不能覆盖当前有效结果；仅当前尝试有效成功且依赖满足、已获授权、未取消时，下游恰释放一次。实现机制留待后续设计。失败需保留足够证据以区分未启动、已确认完成和结果未知，并由调度侧消费分类，决定是否可恢复及是否允许新调用；工具副作用可能发生但未核实时不盲目重放。并行能力、完成信号、输出归属和共享写隔离在方案选择前查证。

**取舍：** 与 REQ-004 §4 的风险/依赖顺序一致，同时保留 R6/R7 的整体用户效果约束；需要后续把调度侧消费契约和 U1/U2/U3 未决依赖设计清楚。

### 候选 2：一体化重写调度状态机

一次纳入 R1–R8。当前不推荐：改动范围集中且较大，U1/U2 的待确认行为与 U3 的能力未知会牵连整体可行性。未决参数并不妨碍讨论不依赖它们的行为接口，但不能据此声称方案可实施。

### 候选 3：仅协议校验与人工兜底

作为保守对照，可覆盖部分 R1/R2/R8；不能满足 R3 失败恢复及 R6/R7 实际并行的完整目标。若将来考虑阶段性交付，须另行取得用户对范围/验收变化的确认，不能将此候选称为完整解决方案。

## 4. 未决事项与验证计划

- **U1（已裁决）。** 授权请求发出后统一等待 180 秒，无单任务例外。持久受理须严格早于截止。恰好截止或晚答均按到期处理，自动释放零次。到期按当前进度交付，披露待答事项及未答事实并终止当前工作。沉默不表示同意或拒绝。
- **U2（已裁决）。** 保留现场，关闭回退及其判定、授权、占额与授权沿用分支。仅在可证无残留、旧运行已确认退出或可证未创建、失败可重试、外部副作用已核实且无重复风险，以及授权和预算有效时自动重试。首次失败后最多重试 2 次，每次扣本轮调用预算。文件状态按已确认残留、已证范围内无残留或未知披露。具体失败分类、退避与取证实现仍待验证。
- **U3（待查证）：** 各通道完成/退出信号、工具禁用能力、并行输出及共享写隔离。方案定稿前验证必要能力，产品验收前再端到端验证。
- **退出证据链（待查证）：** 逐适配器核实三值如何传到 `finish`、哪些证据被持久化以及调度恢复如何消费。当前已证实跟踪层接口存在，协作调度层未见消费引用；不能把“端到端未核验”扩大成“所有调用点必然丢失三值”。
- **验收计划：** 实现后按 A1–A8 验收。特别是 A6/A7 必须通过同一次实际入口的两任务重叠运行及两路分别输出证据；分层中的内部检查不能替代该整体验收。当前没有产品实现或验收结果。

### 4.2 部分修改、回退候选与终止披露

**本项目用户已决定的行为**：确认文件状态且无未处理的代码/文档修改风险后，才可能进入重试资格判断；发现修改时不盲目重放，而要识别改动并判断是否需回退；无法核实文件状态时，按当前进度交付，明确指出可能存在的代码/文档更改并终止。重试总数最多为首次失败后的两次，每次重试消耗本轮调用预算。

**设计候选（尚未获用户批准为规则）：**

1. 在每次尝试前记录工作区/仓库版本、已有 dirty/untracked 文件清单；结束后对照尝试前基线检查状态、差异和新文件。若工作区与尝试无法可靠归属，视为“无法确认”，不自动重试。
2. 把本次尝试产生的改动与预存用户改动分开归属。先检查差异内容、是否完整、是否可能有未落盘副作用；先保护预存用户改动。可用独立 worktree 作为隔离候选，但它不提供自动回退授权。
3. 若发现代码/文档修改，记录文件与差异并暂停自动重试；由尚待决定的授权/判定流程确认是否回退。没有有效回退授权时保留现状并交付差异，不执行 `restore`、覆盖或删除。只有完成获授权的恢复并重新核验无未处理修改风险后，才可再次评估是否还有重试次数和预算资格；回退是否占用两次上限仍待用户决定。
4. 如不能确认文件或副作用状态，终止重试，报告已确认进度、未确认的路径/内容及“可能仍存在修改”；这不是把失败标为成功，也不证明没有改动。

**幂等键（研究候选，尚未选定）：** 客户端为同一操作生成稳定的键，重试时沿用原键与参数。Stripe API v1 保存首次开始执行后的状态码与响应，重复请求可返回原结果（包括 500），参数不一致会报错，键满 24 小时后可清除，清除后重用可能触发新执行。API v2 在能力范围内保留已成功步骤，只继续失败或部分失败的工作。[Stripe 官方说明](https://docs.stripe.com/api/idempotent_requests)

AWS 建议服务端将去重记录与业务变更原子提交，并留存原参数和足以处理迟到请求的记录。该机制降低超时重发带来的重复副作用，但增加存储、保留窗口和一致性处理成本。项目推断：如果文件写入和去重记录无法可靠关联，键本身无法判断几个文件改了哪些，也无法自动回滚；仍须核对差异与归属，并按待定授权处理。[AWS Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### 4.3 公开资料不能决定的用户项与验证边界

- U1：单任务是否允许覆盖三分钟默认期限。
- U2：文件确有改动时谁负责判断/授权回退；授权前是否可继续其他独立任务；回退后能否重试及是否计入两次。
- U2 设计细节：可重试失败分类、重试间隔/退避、确认“无未处理修改风险”的证据阈值，以及是否允许没有文件差异但存在外部副作用时重试。
- A3/A4 应依 REQ-004/1.2 更新后的判据验证。A6/A7 仍必须在同一次真实入口的双任务重叠运行中一起验收；上述分层设计、工作区隔离或超时/重试单项通过均不能替代该整体产品验收。产品尚未实现，当前没有通过结果。

### 4.4 三方独立调查综合（entry-4755／entry-4763）

Codex 从项目现状出发，DeepSeek Harness 补充资源审批和工作区隔离，Grok 重试后补充产品到期语义和部分写入反例。三份交接在保留统一默认期限、保留并核对差异、暂不采用自动回退的建议上方向一致。回退授权人和计数仍无决定。

- **统一三分钟（推荐）**：沿用 REQ-004／1.2 的超时交付和终止语义。显式例外是候选，需有具体审批场景、设定权限、可见截止时间和迟到回复规则。按任务类型配置会增加分类、默认值及冲突处理，现有来源未给出从“写代码／改文档”推算人类答复时长的依据。可先观察同类审批的响应耗时、超时后重开率和返工，再评估是否引入例外。
- **公开契约边界**：Azure YAML 资源审批超时会跳过阶段，经典 Release 审批超时会拒绝部署。GitHub 环境审批和到期后可继续的 wait timer 是各自的规则。Temporal 的单次执行时限、含重试总时限及退避用于执行流程。三者都不能直接作为本项目授权等待值或到期规则。[Azure YAML](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals?view=azure-devops) · [Azure 经典 Release](https://learn.microsoft.com/en-us/azure/devops/pipelines/release/approvals/approvals?view=azure-devops) · [GitHub 环境](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) · [Temporal](https://docs.temporal.io/encyclopedia/detecting-activity-failures)
- **失败恢复候选**：先确认原尝试退出，再核对执行前文件状态、现有差异与外部效果。能归属且有用的部分成果可保留，评估只续做剩余步骤。文件状态已核实且无未处理修改风险时，按失败类别、授权和预算评估重试。退出、归属或副作用仍不明时暂停新写入及重试，无法核实则按基线收尾并披露。只有改动阻碍安全续做、恢复点和范围可核实且能保护用户已有改动时，才建议提出人工授权的回退方案。续做、重试的执行条件和计数应在定稿时明确。
- **机制限制与实证缺口**：共享目录的事后状态只能显示差异。独立工作树可用于事前隔离。Claude 检查点会漏掉仅由 Bash 修改且未被跟踪的文件，子代理及会话外改动的覆盖取决于是否已跟踪及运行方式。服务端幂等只覆盖其接口契约，不能证明本地写入归属。源码能观察到未知退出进入 quiescing，尚未证明调度已端到端消费退出、归属和隔离证据。Grok 重试交接仅核对了可见工作区状态，不能据此证明此前尝试毫无副作用。[Git status](https://git-scm.com/docs/git-status) · [Git worktree](https://git-scm.com/docs/git-worktree) · [Claude 检查点](https://code.claude.com/docs/en/checkpointing) · [Stripe 幂等](https://docs.stripe.com/api/idempotent_requests)

### 4.7 第三轮交接审核（entry-4770）

**扣账（U2／A3）。** 接受 Grok 本轮修订，采用新调用预留提交时扣账作为同任务多尝试的设计口径。现行 reserve 在同一事务写调用并增加 used，随后 call 才进入 _invoke。已有单测源码覆盖通道忙、预留已扣而未启动的情况，本轮未执行。只在实启时扣账需要可核验的启动信号及容量占用和对账规则，当前证据不足。已证实未启动仍占额度是明确代价。授权登记及增加待办不扣账，账本、实际派发与失败分类分别取证。首次之外最多两个恢复预留，每次成功提交扣本轮 1，已扣不自动冲销。

| 正常新预留 | 调用记录和 used 增量同事务提交，各为 1。预留成功只证明账本已登记。 |

**结果与领取（R3／R5、A3／A5）。** 接受 Grok 的单次领取判据，保留历史失败及原任务依赖。提交正式结果须同时匹配 job、task、当前 attempt 和 call，具备完成证据与合法协议，且轮次允许提交。旧尝试或重复结果不得覆盖终态或重复激活下游。下游已授权、未取消、全部依赖满足且尚未领取时，持久化领取恰 1 次，其首次调用独立扣账。其余情况领取 0；须分别验领取、预留和真实启动。现有批次 claim／consume_batch 可供设计对照，主路径 pending 回写及单次历史成功均不足以证明并发下的单次领取。接受同任务多尝试的条件是授权去重、尝试归属与原子扣账、停止与结果提交互斥、下游领取可恢复且不重复，并通过回执丢失、进程崩溃、迟到及并发反例。

**U3／A6–A7。** 接受 DeepSeek 对所查工作台路径的判断。_drive 取 ready[0] 串行执行，execute_batch 提供并行原语并要求调用方保障隔离，所查主路径未接入该原语。按 call_id 保存最终 text/payload 可追踪最终结果。适配器中间事件到卡片的分别展示、共享写冲突保护和工具禁用仍缺验证。并行原语可供评估，接入方式尚未选定。最小验收在同一次工作台入口运行两位不同 Agent 的独立受控任务，各启动一次，同一时基证明区间重叠，两路有唯一标记的中间输出在各自结束前可见，并按 job/task/call/attempt 关联。另以受控冲突验证隔离或明确阻止，并核查部分失败时保留其他成果及迟到输出零覆盖。历史轮次与本轮只读查证均未提供这些端到端证据。

### 4.8 第四轮设计综合

### 4.10 0.9 复核综合（entry-4806）

### 4.16 停止与版本发布的复核结论（entry-4824）

两份 0.15 专项复核均已完成。以下设计结论沿用 REQ-004 1.2 的 R3/R5/R6/R7。

- **取消与恢复线程。** 原 call_id 的取消请求须持久化并可补投给仍在启动的执行对象。取消与 ResumeThread 在同一互斥边界判定。取消先胜时禁止恢复线程。恢复先胜时，按已在途调用取消并核实退出。持久化请求、仲裁生效与退出确认须分别记录。现行 managed_process.py 的 _resume_lock 只覆盖送达该对象的取消。mark_running 成功后若只写库、通知尚未送达，旧执行者仍可调用 ResumeThread。因此不能在仅有持久化请求时确认已封闭恢复入口。
- **恢复证据。** 已创建暂停进程不得标 not_started。只有正面证据证明整次调用从未创建且启动路径已封闭时才可用该值。根进程退出且 Job 为空方可确认受管执行退出，Job 外副作用另查。创建或退出证据不足时保留 unknown 和原 used，按原调用核查及补投，禁止重新创建、重新预留及重放不明副作用。

- **收敛与缺口。** 两项选择均有同版明确回应，当前无会改变选型的剩余异议或需用户裁决的阻断。A3 恢复及副作用、A5 停止竞态及退出、A6 并行及写隔离、A7 流式归属及迟到输出均未执行产品验收。U1 单任务期限例外仅影响例外分支。U2 回退判定及授权、回退后重试资格与计数、失败分类细节及退避仍约束对应策略分支。本轮快照 20/50，余 30 次，留负责人审核及最终交付各一次。

### 4.18 到期仲裁与回退计数复判（entry-4852）

依据 REQ-004 1.2 的 S8/S9、U1–U4、R3/R4、A3/A4 与 §4.17，复判 Grok 的到期顺序交接及 DeepSeek Harness 的回退计数交接。

- **U1 源码证据。** Grok 追踪的 `accept_result` / `_drive` 写入等待状态和问题，所查路径没有持久化请求发出时刻或截止时间。`operate(answer)` 的 SQLite 事务按阶段受理，现行提交可排序答复和人工 `finalize`，但所查路径缺独立到期动作及计时调度。关闭后直接拒答，缺 A4 要求的负责人迟答路由。人工收尾、额度收尾、页面请求中止及迟到调用结果各有独立语义，均无法证明授权等待到期获胜。
- **U1 仲裁候选与保留意见。** 接受由同一等待记录串行裁决、持久记录胜者的方向。保留对“答复先提交即准时”的异议：截止后 1 秒才送达的答复可能在延迟计时器之前提交，从而变相延长期限。建议以服务端持久受理为依据，在同一等待状态转换中核验截止谓词。截止前已有效受理的答复即使之后才处理仍准时，截止后才受理的答复走迟答路由，即使到期任务尚未提交。同刻候选采用半开区间，受理时刻小于截止为准时，大于等于截止进入到期边界。到期获胜须有同一等待仍开放、已达截止、无已有效受理答复及到期状态转换持久提交的证据，不能从同时到达推断。迟答交负责人，原等待终态不自动重开。最小复核是纸面核对三条时序及事务可见性，特别区分服务端持久受理与客户端点击、处理时间。默认三分钟照常设计。仅单任务例外需用户选择维持默认或允许用户在请求发出前明确约定可见截止，建议当前只采用默认。

### 4.20 跨截止提交复核（entry-4865）

- **已接受的边界。** Grok 接受 §4.19 的最小反例。截止前执行 UPDATE、截止后提交，语句时刻不足以证明准时。所查 transaction() 通过 BEGIN IMMEDIATE 串行写入，由连接上下文提交。写互斥可确定状态更新顺序。提交前中断且恢复确认事务未提交时，答复未受理。提交期间中断须核对恢复状态，不能仅据进程中断判断。默认仍从发出起等三分钟，只有截止前持久受理才可按准时处理。
- **候选取舍。** 提交前最后一次读钟若已达截止，可在提交前中止准时路径。若读钟尚早，提交仍可能跨线，不能把采样值写成已证实的 accepted_at，也不能在提交后靠回滚撤销已经对外生效的授权。该方法只适合作提前拒绝，严格方案仍须在释放依赖工作前提供可恢复的提交时点证据或可靠的截止前上界。已证实迟答走迟答路由。无法区分时保留答复及证据，标明受理时序未证实，不释放受阻工作，亦不据此宣称到期胜出。
- **最小查证。** 只读评估当前事务接口能否提供与同一等待记录绑定、重启后可核验的提交证据。可检验的保守候选是先落暂存答复，提交成功返回后用同一时钟采样。采样早于截止可作为暂存提交的上界，采样跨线只表示缺证。该候选还需证明到期与待确认状态互斥、证明持久化及崩溃恢复可收敛，并说明如何处理实际准时却无可恢复证明的答复。覆盖截止前写入后延迟提交、提交前中断、提交后证明未持久化三种时序，当前仅为设计推演。

### 4.23 恢复证据候选与 A4 最小验收

- **U3 证据来源与旧记录。** [执行跟踪](../../workbench/execution/execution_tracking.py)的 finish_run 以令牌围栏核对当前执行，写入状态和布尔位。当前路径上，confirmed 写 1，unknown 写 0 且进入 quiescing，not_started 写 0 且要求待启动运行和预留域，不能以 completed 收尾。状态与布尔位组合在已证明由该版本、该校验路径写入并正确关联到本次运行时，可提供额外线索。缺少版本或来源的 false、默认值及缺行按 unknown，禁止批量推断未启动。可信旧 true 仅支持确认退出，仍须核对作用域与调用归属。

### 4.24 恢复与截止竞态复核

- **旧记录与围栏。** 接受 Grok 对旧记录的保守规则。只有可证写入版本、校验路径和本次 run/call 归属时，才使用状态与布尔位的组合。failed/cancelled+0 仍需当时 pending+reserved 的路径证据。缺行、默认 0、来源未证或异常组合按 unknown。确认退出仅通过退出门槛。当前 execution_runs 无 fence，域的当前 fence 不能还原旧 run 的代次，但现有令牌检查仍能拒绝旧回写。建议权威退出证据绑定 call_id、run_id、原始 fence、来源及证据版本。查得多个 run 时须明确证据归属，dispatch 的 LIMIT 1 无法承担该裁决。现有 StaleRun 拒绝路径与拟议的迟到证据审计是两项能力。

### 4.25 恢复预留与执行接纳的事务边界

- **源码事实。** Web 入口把同一个 DB_PATH 交给 CollaborationService 与 begin_execution（web_chat.py:125、335–341）。BatchStore.transaction 与 ExecutionTracker._transaction 各自打开连接并执行 BEGIN IMMEDIATE。reserve 在其事务中按 call_id 查重、写 collab_calls 并增加 used，之后服务才调用传输。执行层 begin_run 另开事务检查域空闲及未结束 run，写 pending run 并递增域围栏。finish_run 在执行层事务更新退出布尔值及域状态。当前同文件可串行化数据库写入，但两个现有方法各自提交。
- **预留候选。** 在同一连接、同一写事务重读当前尝试、权威退出证据版本与归属、域状态和围栏、工作流许可与预算，原子写入唯一目标恢复键、原 call_id 对应关系及扣账。目标键由 job、原任务、已确定的目标尝试组成，重放须沿用已分配序号。缺证、版本变化或条件冲突时本次不预留、不扣账，重新裁决。文件哈希、外部副作用与进程创建在 SQLite 事务之外，文件状态核验仍需与隔离或工作区版本约束配合。
- **执行接纳候选。** 预留后若出现停止、域占用、围栏变动或证据冲突，在 begin_run 的写事务中再次检查并条件领取同一预留，将领取与 pending run、域围栏写入一起提交。冲突时持久记录同一调用的已预留未接纳及原因，禁止启动和下游释放，已提交的 used 保留 1，不补扣也不退账。仅有确定的未接纳且启动路径已封闭时才能报告未启动。现行传输异常可将 reserved 调用改为 failed 并保留 used，缺少上述专门裁决。数据库接纳后到实际启动之间仍须核对启动门与停止衔接。
- **重复与重启。** 同键重复请求在事务中查回原调用与裁决，换请求 UUID 也不得再扣账。未接纳的记录只可在原身份下、重过有效条件后条件领取，终结记录只返回既有裁决。已接纳则按原 run 和围栏核对，无法证实实际启动状态时暂停并留证；单凭 pending 或缺结果不得再创建进程。预留提交前中断应无扣账，提交后重放应仍为一次扣账。
- **验证边界。** 上述为设计条件。待验证证据变动前后、两路同时接纳、停止竞态、在各提交点中断重放及工作区隔离。U3 与 A3/A4/A5 未验，U4 仍缺原始材料。U1 例外与 U2 回退政策未阻断本项查证。

### 4.26 恢复尝试名额的计数点

- **需求与异议。** REQ-004 1.2 的 S8/S9、U2/R3、A3 规定首次失败后最多两次重试、每次消耗本轮预算及保留扣减证据。DeepSeek Harness 认为预留计名额可从基线推出，Grok 指出原文未指定预留、接纳或启动哪个时点才算一次重试。综合采纳 Grok 对原文的解读，保留 DeepSeek Harness 的推导意见。两方均支持以下设计选择。
- **选定设计。** 每个原任务首次失败后最多分配两个不同的恢复尝试。新目标键首次预留提交时，在同一事务内登记一个名额并扣一次本轮预算。提交后未接纳或终结，两条记录均保留。第三个不同目标拒绝，新增名额和扣账均为零。同键重放与原身份条件领取沿用原记录，不增加名额或扣账。重新领取遵守 §4.25 的证据、围栏、停止和授权条件，终结后只返回原裁决，启动不明则暂停。
- **候选比较。** 接纳才计名额且另设每任务累计两个成功新目标预留的硬上限，在拒绝第三个新尝试上效果相同。前两个预留未接纳时，该方案的接纳名额账仍为零，选定方案已占两个名额。仅限制同时未接纳的数量时，顺序发生的 DomainBusy 仍可让第三个目标预留成功，受本轮总预算约束。选择一笔事务登记两项，便于审计和重放。执行接纳和进程启动仍分别留证。

### 4.27 接纳后的取消、唤醒与重启证据

- **源码与回应。** 采纳 Grok 对三条路径的区分。协作层先提交停止及待处理取消事件（collaboration_actions.py:70–79），再由 collaboration_service.py:114–117 和 dispatch.py:20–41 尝试取消活动对象。Execution.cancel 先设置内存取消并调用进程取消，再尝试写 cancel_requested（execution_runtime.py:159–170）。创建前检查与 _resume_lock 内的 ResumeThread 判断使用内存谓词（managed_process.py:273–295），数据库取消字段可挡状态登记，但写库本身不能封闭唤醒。最小时序为登记完成、停止落库、唤醒获胜、取消才送达。即使再加一次独立读库，读完到唤醒之间仍可发生停止。
- **证据分界。** 意图提交、送达原执行对象、取消赢得唤醒裁决、可证从未创建、独立确认退出，须分别记录。创建前取消确实挡住创建且权威结果与该运行匹配，才支持 not_started。已创建暂停进程时，取消先胜只证明唤醒被拦，仍须取得退出证据。原执行实例产出的可追溯持久证据可在重启后核验，不能据重启后的状态倒推。
- **重启处置。** 接纳提交后在创建前崩溃，或创建后在运行登记前崩溃，都可能留下同样的 pending 与域预留记录。缺登记和 Kill-on-close 均不足以确认退出。缺证记 unknown，保留原名额及预算，暂停自动重放，禁止按旧记录再创建、登记或唤醒。已证退出也只进入原恢复裁决条件核验。
- **候选与限制。** 将持久取消意图和补投绑定 run_id 及其可核验代次，对仍可定位的原对象幂等补投并单记送达和裁决结果。缺对象时保留待处置意图。补写或补投不能追溯性证明已挡住唤醒。若要求停止提交先于唤醒即必须禁止唤醒，候选须让两者在覆盖实际唤醒的同一有效裁决边界互斥，并说明实例重启和崩溃后的证据；本轮未选定实现机制。
- **A5 待验时序。** 覆盖接纳后创建前取消送达、暂停创建后取消先胜、停止落库后唤醒抢先及补投、唤醒先胜后取消、创建前与创建后登记前分别崩溃、活动对象缺失时重启和重复补投。核对事件、唤醒与退出证据分别归属原运行，账目只记一次，缺证不重放，旧结果不覆盖新代次或放行下游。U3、A3/A4/A5 仍待产品验证，U4 缺历史原始材料。沿用名额计数、严格截止与缺证收尾、停止先于接纳的原有条件，以及单次期限例外、回退判定与授权、回退名额、回退后授权沿用四项待决政策。entry-4899 快照 4/20，余 16。

### 4.28 停止提交与实际唤醒的串行边界

- **源码边界。** 协作停止在写事务中更新 stopped、取消待办并登记事件，提交后才处理取消投递。Execution.cancel 持运行对象锁，先设内存事件及调用进程取消（后者短持 _resume_lock），再写跟踪库。唤醒在 _resume_lock 内检查内存谓词后调用 ResumeThread。跟踪库的 _owned 校验 run_id、instance_id 和域 fence，只约束走该校验的操作。旧实例若已过数据库检查，仍可能走到实际唤醒。来源：collaboration_actions.py:70–85、collaboration_service.py:110–117、execution_runtime.py:159–170、managed_process.py:147–150、288–293、execution_tracking.py:156–169。
- **候选比较。** 持久取消加异步补投能保留意图并重试送达，但停止提交后、送达前仍可唤醒。共同串行边界可有条件保证顺序：停止事务和每个实际唤醒路径均参与同一跨实例裁决，唤醒侧在边界内用新鲜状态核验 stopped、运行身份及代次，并持有边界直到系统调用返回。若利用同库 BEGIN IMMEDIATE 串行，必须避免嵌套写事务和锁逆序。例如停止侧拿数据库写锁后等运行对象锁，而取消路径拿运行对象锁后等写锁，可互等。不能直接在现有私有 _resume_lock 内加读库或回调。单实例锁、一次独立读库或可被旧持有者越过的租约不足。共同边界的具体实现待复核。
- **顺序与故障。** 停止先提交则参与裁决的旧运行不可唤醒；此前创建的暂停进程仍需退出证明。唤醒先发生则按已启动竞争处置。唤醒成功但落库前崩溃，或唤醒后提交失败，数据库回滚不能撤销系统调用；缺独立证据记 unknown，暂停重放，保留预算和名额。停止提交失败不得回报停止已持久生效；若内存取消已经生效，保留取消结果并重新核对持久状态。唤醒侧校验或取得裁决失败时禁止调用，只有可核验的未调用证据才支持该次唤醒被拦截。旧实例迟到须在系统调用前失去资格，迟到结果只作归属核验和审计。
- **语义与验证。** REQ-004 1.2 R5/A5 要求停止生效后新增尝试及迟到覆盖为零、退出有独立证据。共同边界若把保证扩展为停止提交后禁止已接纳运行唤醒，属于额外候选保证；若使停止提交等待正在进行的唤醒，还会改变停止响应时序。均须明确生效点，不能当作已批准变更。A5 增列两种胜序、成功后未落库、提交失败及旧实例迟到；本次仅静态推演。U3、A3/A4/A5 未验，U4 缺历史原始材料。保留单次期限例外、回退判定与授权、回退名额、回退后授权沿用。entry-4899 快照 6/20，余 14。

### 4.29 停止与唤醒入口的独立复核

- **现行入口。** Grok 核对了 `/api/collaboration/action` 和 `/api/stop` 中匹配协作任务时走的 `operate(stop)`。持久停止以该事务提交为准。`/api/stop` 另有 `stop_active_run` 路径，可能先有内存取消，持久状态仍须核实。`operate(finalize)` 写入 `cancel_then_finalize` 意图，不置 `stopped`。现行 `cancel_collaboration` 仅向 `ACTIVE_RUNS` 中的对象投递取消，找不到对象时只查询未完成记录，没有按运行标识补写 `cancel_requested`。来源：`collaboration_http.py:33–36`、`routes.py:141–226`、`collaboration_actions.py:70–85`、`dispatch.py:20–41`。
- **实际唤醒与锁序。** 两条 `web_runs` 启动路径经 `Execution.launch` 汇入 `ManagedProcess.run` 的实际 `ResumeThread` 调用。`mark_running` 在调用之前，`running` 只证明登记。跟踪库的 `_owned` 核验实例与域围栏，实际调用没有这道检查，旧实例可能在先前校验过后迟到。取消路径从 `state_lock` 到执行对象锁，短持并释放 `_resume_lock` 后才写跟踪库。若改成停止持数据库写锁等 `_resume_lock`、唤醒持 `_resume_lock` 等写锁，两者会互等。现有 `_resume_lock` 内不得直接加数据库访问或调用方回调。来源：`web_runs.py:179–194`、`execution_runtime.py:159–195`、`managed_process.py:145–150、273–295`、`execution_tracking.py:100–214`。
- **候选约束。** 采纳 Grok 对入口覆盖与锁逆序的意见。SQLite 冲突写事务是候选之一。共同边界须在所有参与实例中覆盖持久停止提交和实际唤醒，从边界内重新核验停止或取消状态、运行身份、实例及代次，一直持有到系统调用返回。另路取消和 finalize 应按各自语义核对覆盖，不能假定它们都会写 stopped。WAL 下独立只读查询、进程内锁、异步补投及允许旧持有者继续调用的租约均无法提供这一保证。
- **胜序与故障。** 若候选成立，停止先提交则拦截后续实际唤醒，已创建的暂停进程仍需独立退出证据。唤醒先成功则进入在途取消处置。锁等待或提交失败且无法确认持久停止时，回报等待、失败或未确认，按实际证据决定，不能回报已提交。内存取消可能已送达，应保留该事实并重新核对持久状态。若唤醒成功但结果未落库，数据库回滚无法撤销系统调用。缺证时保持 `unknown`，暂停重放并保留原预算和尝试名额。旧实例到达调用前须重新校验并拒绝失效代次，迟到结果按原归属审计，不能覆盖终态。
- **取舍与待验。** REQ-004 1.2 R5/A5 要求停止生效后零新增尝试、迟到结果零覆盖终态、独立退出证据及保留 used。提交后禁止已接纳运行唤醒保留为可选设计。停止提交可能等待在途系统调用返回，进程退出仍是后续独立步骤。两种胜序、提交失败、成功后未落库、旧实例迟到及无对象补投均待产品验证。U3、A3/A4/A5 待验，U4 缺历史原始材料。保留单任务期限例外、回退判定与授权、回退名额及回退后授权沿用四项待定政策。工作台快照 10/20，余 10。

| A6 | 主入口同一次授权两个 Agent，采集同一时基的启动结束事件并证明区间正重叠。另核对依赖等待、同批失败不丢成果、共享写冲突隔离或阻止。 |
| A7 | 使用 A6 同一运行，保存两路原事件、存储与界面证据。各路在结束前可见且归属正确，中间协议不触发派发，取消后迟到输出不覆盖终态。 |
| A8 | 保存各角色合法、完整与增量计划、多目标尾部及非法样例的校验和派发记录。合法解释唯一，非法零派发且定位明确，未就绪及格式错误可区分。 |

U4 仍缺第二次等待快照、旧运行版本绑定、4358 完整入口上下文及原始多目标失败回复。历史联调只覆盖原场景。优先复核前置诊断及重启后证据消费，再据通道覆盖和迟到写入结果比较工作区候选。未具备设计就绪或验收证据，状态记为设计中。

### 4.34 定向复核与重启证据边界（entry-4924）

调度快照已用 15／20 次。原 Grok 调用因正常完成证据缺失或 stopReason 不受支持而失败，无有效回执。以下依据 Codex 前置诊断与文件候选回执，以及 DeepSeek Harness 独立补查回执。

- **前置诊断。** 接受 Codex 回执。版本探测在受管启动前调用，按可执行路径在进程内缓存，缓存也可保存 unknown。同路径替换可能保留旧版本。快照字段只关联运行，不能证明本次实际执行了探测或排除文件、网络和遥测副作用。U3 应按二进制身份验证冷暖缓存、同路径替换及超时。
- **退出消费。** 接受 DeepSeek Harness 对观测、运行时释放和持久化三者的区分。现行 finish_run 成功提交且记录来源可核实时，可以按写入不变量从状态与布尔值解释三值：failed/cancelled + 0 对应 not_started，终态 + 1 对应 confirmed，quiescing + 0 对应 unknown。保留边界异议：域 idle、无行、旧版来源不明或不一致记录均不能单独证明未创建。创建前未提交收尾与创建后未提交收尾可留下相同 pending + 0。未完成态阻止同域再入，所查路径未见读取三值并完成重试裁决的消费者。显式保存三值和契约化复用现有字段均为候选，U3/A5 须验证版本、重启、未提交及记录矛盾时的处理。
- **文件证据。** 接受两种候选的条件性结论。按尝试隔离须约束全部实际可写根，包括适用的共享 Git 元数据、生成物、临时目录和缓存。共享范围须提前记录既有修改，并以排他控制或可核验写入记录确认归属。A3/A5 验证未跟踪文件、已有修改、迟到写入及旧运行退出未知；可写根变化、归属缺失或保护中断后原证据失效。两种候选尚未定案。
- **重试与历史。** not_started 与 confirmed 只满足退出条件，含前置诊断及 Job 外委托的副作用须独立核实，文件、失败分类、授权与预算也须符合 U2。缺证或证据过期时保留现场、披露未知，自动重试预留为零。统一三分钟、无回退及最多两次并逐次扣账继续适用。U4 四项历史原始材料仍缺，受控验证不能补足历史归因。

本轮形成取证边界与待验条件，未执行产品验收。REQ-004 处于设计中。

## 5. 讨论结论、异议与授权边界

Codex、DeepSeek Harness 与 Grok 对候选 1 作为设计依赖顺序、候选 2 暂不推荐、候选 3 仅作对照，以及上述 U1/U2/U3 与实现细节边界达成讨论一致。Grok 特别指出，即使三值能到达 `finish_run`，调度侧仍需定义分类到恢复决策/新调用的消费契约；本稿已纳入该设计缺口。该一致仅是对**提案方向**的讨论一致，不等于用户验收、正式设计决定、产品实现授权或验收通过。

用户先后明确 U1/U2 的部分规则，需求基线随之更新为 REQ-004／1.2；本稿消费该有效基线，不另建需求基线。U1 默认三分钟与超时收尾、U2 首次失败后最多两次且每次重试消耗本轮调用预算、未知文件状态时终止披露，均按用户原意记录。行业资料只提供比较依据，没有替用户决定单任务覆盖期限、已确认改动的回退授权/判定人、回退后重试资格及计数。当前下一步仍是请用户验收本提案方向；验收方案后须另行确认产品实施授权。源代码调用链与 U3 能力验证应作为进入相关设计/实施前的查证项。

### 4.35 退出证据、文件取证与重试裁决（entry-4942）

依据 [REQ-004 1.4](../requirements/COLLABORATION_ROUTING_REQUIREMENTS.md) U1–U4、R3、A3–A5 与 §4.33–§4.34，对照 DeepSeek Harness、Grok、Codex 三份只读回执。方案仍在讨论，以下为综合建议与验证条件。

1. **重启裁决。** 支持 DeepSeek Harness 优先比较显式退出三值列，理由是减少业务状态变化对证据语义的影响。现有字段组合仍可作为兼容候选，仅对写入来源可证且收尾已提交的记录考虑回填。两个方案均需按同一 call_id 恢复裁决。崩溃前未提交、字段为空、来源不明或证据矛盾，均按 unknown 处理。验证状态复用、旧字段语义漂移及创建或唤醒后崩溃，预期均不误判未创建。
2. **文件取证。** 支持 Grok 将按尝试隔离作为有条件的主候选。须证实实际写权限覆盖登记的所有根，包含临时目录、共享 Git 元数据与工具缓存。目录切换、执行域互斥或串行派发不足以证明这一点。共享方案仍可比较，前提是有起始基线和可核验归属，且证据持续有效至接纳。范围外写入、并发归属不明或取证后迟到写入均使无残留证据失效。
3. **副作用异议。** 保留对“not_started 后仅需核对文件”的异议。诊断子进程可能先于受管进程启动，版本快照受路径缓存影响。Job 空与文件无残留也无法判定已发出的外部请求或 Job 外委托。无论退出证据为 not_started 或 confirmed，均须独立核实副作用无重复风险，并满足 U2 其余条件。
4. **分类与退避。** 采用 Codex 按阶段与证据映射的建议。DomainBusy、503、查询失败或归属异常，仅在有创建前拒绝且路径封闭的正面证据时归为尚未启动，旧占用仍须另查。超时、失联或缺完成信号归为可能已执行。有可信正常完成信号但校验失败归为格式错。明确取消、授权拒绝及永久失败收尾，退出另证。五项条件齐备才进入退避，预留前复核证据、停止、授权、预算及名额，接纳时复核仍需有效的条件。预留前失效零新增预留和扣账，已提交记录保留。同键重放不重复计数，新目标首次预留提交时同事务占名额并扣预算。间隔、抖动及是否立即重试待同类合格样本。
5. **下一项查证。** 建议先核对各通道能否提供绑定同一 call_id 和版本的退出记录来源、强制可写根及前置诊断和外部操作证据。用 U3/A3/A5 的崩溃、范围外写入、迟到写入及缺证对照确定候选可行性，再按 A4 验证等待期间到期，验证同键重放和第三个新目标拒绝。统一三分钟授权等待独立计时，失败恢复无回退，首次失败后最多两次重试。U4 四项原始材料仍缺，历史归因独立。产品验收待执行。

### 4.36 旧记录来源与通道取证（entry-4942）

对照 [REQ-004 1.4](../requirements/COLLABORATION_ROUTING_REQUIREMENTS.md) U2/U3/A3/A5、§4.35 与两份独立回执。下列为静态查证及综合取舍，产品验收待执行。

- **退出证据。** 两份回执均确认协作调用可经 source_job_id/source_call_id 关联 run_id 及启动快照。DeepSeek Harness 查得 finish_run 持久化状态和布尔值，记录缺少退出证据写入版本。workspace_version 和 config_fingerprint 只标识会话配置。收尾已提交且组合自洽是旧记录回填的必要条件，还须独立证明写入者语义，例如绑定到该次运行且排除混用版本的部署记录。保留对仅凭自洽组合或部署时间回填的异议。来源不明、组合矛盾、收尾未提交一律按 unknown 裁决。显式 exit_evidence 连同可核验的写入语义为新记录首选，字段非空仍须校验来源；恢复逻辑及旧数据迁移尚待验证。
- **通道边界。** Grok 的源码回执显示，启动快照可关联调用，但缺实际可写根清单与 Job 外操作回执。Codex 的 CLI 权限请求与临时目录须分别核对，cli_version 缓存和 Job 外 MXC PowerShell 观测须独立取证。Grok 的 CLI 权限、MCP 路径约束、临时根和 git 预检须分别核对，现有诊断写入仅接受 workbench 来源。DeepSeek 快照可见 profile 与补丁路径哈希，实际可写范围及外部操作仍待核实。所查工作台入口未见统一的 OS 写入约束，通道自身的实际限制仍需实测。保留按尝试隔离为有条件首选，须验证写权限限制在登记根。共享候选须证明写入归属与接纳前证据有效性，两者当前均缺自动重试所需证据。
- **副作用。** 两份回执均支持 §4.35 的异议。not_started 只提供受管进程的证据，仍须核实前置操作。confirmed 的覆盖限于受管退出边界，Job 外操作和已生效外部请求须另证。按 U2 分别披露文件残留和副作用未知，保留现场，暂停自动重试。
- **最小对照。** U3 按通道分别使用独立 call_id，绑定写入版本及运行身份。对照已知写入来源、相同字段但来源不明、创建后收尾未提交三组，检查重启裁决及未知值保留。逐通道用隔离测试目录核对登记根内与范围外写入、临时根、Git 元数据和工具缓存，用受控观测核对冷暖缓存、同路径替换与超时下的诊断，以及 Git 预检和 Job 外观测。A3 对照既有修改、未跟踪文件及写入归属缺失；A5 对照创建前停止、创建后未提交与取证后迟到写入。通过条件为证据确实关联原调用及版本，未覆盖项如实披露，缺证或失效时新增预留与扣账均为零。
- **既定约束。** 统一三分钟授权等待、无回退及最多两次重试继续适用。退避参数仍缺运行数据；U4 历史原始材料缺口独立，受控结果不能用于补齐历史归因。

### 4.37 恢复裁决与预留边界（entry-4942）

依据 [REQ-004 1.4](../requirements/COLLABORATION_ROUTING_REQUIREMENTS.md) U2/U3/R3/A3/A5、§4.25–§4.26、§4.36 和隔离夹具回执。前序在 b795861 上有 25 个隔离用例通过，覆盖运行身份、进程清理、执行域保护、迟到结果拒收和普通调用计账。普通调用可先扣账后遭 DomainBusy，恢复设计因此需要在首次重试预留之前裁决。以下是供复核的设计和预期结果。

1. **恢复入口与旧记录。** 用原 `(job_id, call_id, run_id)` 唯一关联原尝试。对尚无 run 行的拒绝，须有绑定原调用的正面拒绝回执，且启动路径已经封闭。新记录首选在收尾事务中提交显式 `exit_evidence` 三值、写入语义版本及来源。会话配置、CLI 版本和测试代码版本各自仅标识其对应对象。兼容旧字段可省迁移，但字段组合依赖写入者语义。仅在来源可核验、能绑定该次运行、收尾已提交且字段自洽时，按对应版本解释或回填。即使两行同为 failed/0，来源不明的一行仍按 unknown。未提交、空值、版本不支持、身份错配或证据冲突也按 unknown，保留原记录和原因，暂停自动重试。显式列同样无法恢复崩溃前未提交的证据。
2. **文件证据。** 有条件首选按尝试隔离。启动前登记操作系统实际约束的所有可写根，涵盖临时目录、未跟踪文件、生成物、Git 元数据和缓存，保存基线。收尾比较实际路径及内容，区分原有修改、本次残留和未知归属。受约束共享还须覆盖其他写者，靠排他保护或可核验写入记录归属到尝试。文件证据有效期以根、权限、基线、写入记录和保护连续性为准。范围外写入、迟到写入、归属不明、监测断档或保护失效时，旧证据立即作废，按 U2 披露并保留现场。切换目录和 CLI 权限请求仅提供配置线索。
3. **外部副作用。** 独立回执关联原调用、运行（如已分配）、生产者及语义版本，并记录操作标识、覆盖范围、结果和可核验依据。有效结果须能证明操作未发生，或重放不会重复生效，例如权威结果或仍有效且覆盖拟重放操作的幂等保证。not_started 只闭合受管进程的启动路径，Codex 版本诊断、Grok Git 预检及 Job 外操作仍须各自核实。confirmed 同样只证明受管退出边界。无回执、回执错配、诊断缓存只剩版本字符串、外部状态未知或保证过期时，保留缺证结论。
4. **复核、首次预留和接纳。** R3 按失败阶段和证据分类。U2 五项齐备才进入独立退避，三分钟授权等待按原截止处理。退避后以保护覆盖取证到预留提交的窗口。文件根采用能约束所有相关写者的排他保护，或与所有写入和失效事件同步的代际栅栏，校验并持有到提交。外部证据须已有可核验的终态保证，或有覆盖到接纳的有效保证。SQLite 写事务只负责数据库内的比较和更新。事务核对停止、授权截止、预算、已用重试次数、归属、证据版本及唯一预留键，在首次成功提交中一并写预留、占名额、增加 used。保护无法维持或任一前提在提交前失效则零新增预留、零扣账。同键同目标重放返回已有预留；键与目标冲突拒绝。预留后、执行接纳或唤醒前再次按 §4.25–§4.29 核对停止和证据。此间失效则禁止启动，保留原预留及扣账，不再新增。无法同步约束写者的共享路径暂停自动重试。

| 核验 | 最小正对照 | 最小负对照与预期 |
|---|---|---|
| U3 | 重启读回绑定原调用、运行和写入版本的已收尾三值；有来源凭据的旧记录按版本解释。逐通道核对实际登记根及前置操作回执 | 同字段无来源、版本或身份错配、创建后收尾未提交 → unknown，0/0。用冷暖缓存、同路径换二进制及超时区分 Codex 诊断执行与缓存；核对 Grok 预检及 MCP 路径、DeepSeek 桌面运行的实际写根、Job 外操作回执。 |

## 4.38 提交歧义、实际唤醒与外部生效（0.38，综合复核）

本节细化 §4.25–§4.29，并以本节的时点要求替代 §4.37 中截至预留提交的文件保护和截至接纳的外部保证。沿用 REQ-004 1.4：统一等待用户授权三分钟，自请求发出计时，到时汇总未答项并结束；授权等待和授权有效期分别检查。禁止自动回退，原任务最多预留两次重试，U4 对原结果可得性和根因独立归因。以下是设计规则与待验收判据。

| 复核发现 | 处理 |
|---|---|

## 4.39 重试名额与接纳证据

依据 REQ-004 1.4、§4.26、§4.38 和 entry-4968 两份独立只读复核，本节记录有条件的设计首选。沿用三分钟授权等待、无回退、每个原任务最多两次重试、U4 独立归因，以及 §4.38 的文件保护和外部生效证据要求。

| 复核意见 | 综合取舍 |
|---|---|
| DeepSeek Harness：名额检查须在取得写锁后重读 | 采纳。优先按作业和原任务统计已提交的唯一重试预留。取得写锁后，先查稳定键。匹配则只读返回原记录，键、身份或语义冲突则暂停。新键须在同一写事务内重读名额与轮次预算，再提交唯一预留和一次轮次扣账。名额随预留提交占用，后续停止、失败或归档均不释放。 |
| DeepSeek Harness：归档删键会漏计，建议用独立计数列保留累计值 | 接受漏计反例。保留完整行，或保留能恢复原预留身份、去重并计数的持久映射，均可验证。归档迁移期间也须维持跨存储位置的唯一性与完整计数。独立计数列可作为备选，按作业和原任务只增不减，与同键首次预留及轮次扣账一并提交，需可对账。它只保存累计值，原预留映射仍须保留以支持同键重放。 |
| DeepSeek Harness：旧记录缺键时按已占满处理 | 接受暂停的行为。实际占用记为未知，已有账目原样保留。只有可核对原调用、预留目标、写入语义及计账来源时才回填。禁止将缺证写成占满、清零或再次扣账。 |
| Grok：接纳须有稳定键唯一约束，专用状态须同事务条件更新 | 采纳。执行侧优先在建立执行行的同一事务中持久提交唯一接纳映射，绑定稳定预留键、call_id、run_id 和写入语义版本。专用状态须在该事务凭原状态、稳定键与绑定身份做一次性条件更新，并具备同等跨进程唯一性和归档后查询保证，才等价。使用同一 SQLite 文件的不同事务仍有独立提交窗口。 |
| Grok：唯一冲突可用于证明旧路径已失效 | 采纳其作为重复接纳被拒绝的证据，证明范围限于该次写入。恢复一笔确实未接纳的预留需要分别证明历史接纳未提交，以及旧派发已在接纳边界失去资格。可验证候选是执行侧在同一接纳事务中拒绝已作废的派发凭据，同时确认原键从未接纳。缺行、域空闲、进程重启和单次唯一冲突均不足以证明这两点。 |
| Grok：接纳、回执送达、进程创建、实际唤醒和外部生效分别取证 | 采纳。接纳记录只证明执行侧已提交。回执丢失可以和接纳同时成立。实际创建、解除暂停及操作实际生效分别留证，外部动作可能早于唤醒。已接纳但创建、唤醒或外部结果未知时，保留原账并暂停。 |

**U3 / A3 / A5 待运行对照。** 记录新增预留、重试占额、轮次扣账、执行接纳、实际创建、实际唤醒及指定外部操作生效七项增量，以下按此顺序。用本地替身记录外部操作，已发生或在途的历史动作独立记录，缺证记未知。验证必须覆盖跨进程，且记录稳定键、call_id、run_id、写入语义版本和拒绝原因。

| 场景 | 预期判据 |
|---|---|
| 两个不同键争抢最后一个名额 | 两者从旧计数 1 出发，在预留边界截停下游。合计仅一笔提交，增量 1/1/1/0/0/0/0。写锁内重读后拒绝另一笔。 |
| 同键查询重放或预留回执丢失 | 查回原预留，增量 0/0/0/0/0/0/0。键、目标或语义冲突时暂停。 |
| 归档保留映射或故意丢失映射 | 保留时同键查回原预留且历史占用不变，已满时拒绝新键。丢失时报告未知、保留原账并暂停。两种负对照增量均为 0/0/0/0/0/0/0。 |
| 旧数据迁移对账 | 对照迁移前后身份、已知占用与轮次扣账。重复迁移无新增。缺键、冲突或无法对账时保留原账并暂停，业务增量 0/0/0/0/0/0/0。 |
| 接纳已提交但接纳回执丢失，或完结释放执行域后旧派发迟到 | 匹配既有唯一接纳，返回证据或拒绝，第二接纳不建立新运行或改变执行域。增量 0/0/0/0/0/0/0。 |
| 预留已提交、首次接纳尚未证明 | 只有缺行时暂停。正向证明尚未接纳且旧派发已排除、各门槛有效时，通过独立动作接纳原预留。接纳边界增量 0/0/0/1/0/0/0，创建、唤醒和外部生效继续按 §4.38 验证。 |

现有源码旁证来自两份回执对 `reserve`、`dispatch`、`begin_run`、`finish_run` 和 `ResumeThread` 的只读核查。首选方案的归档留存、迁移对账、并发与跨进程排他均待实测。DeepSeek Harness 对留存策略的条件及 Grok 对物理存储形式的保留意见继续记录。负责人对唯一冲突证明范围的收窄尚待 Grok 明确回应。

## 4.40 旧派发接纳边界

依据 REQ-004 1.4、§4.39、Grok 聚焦复核及负责人回应，形成以下条件性一致。

1. **接受唯一冲突的证明范围。** 唯一键冲突仅证明该次接纳写入被拒绝。其他在途派发及使用不同键的旧写入路径须另行核对。
2. **附条件接受恢复首次接纳。** 执行侧须在同一写事务取得写锁后，核验同一预留的历史接纳记录可完整查回、此前无已提交接纳，以及旧派发已失去接纳资格，随后写入唯一接纳记录及执行行并一并提交。历史已接纳则查回原记录。所有仍可接纳同一预留的旧写入路径，均须在写入边界服从同一拒绝条件，例如共同受持久唯一约束，或在事务内检查同一凭据作废事实。旧写入先提交时，恢复侧须识别历史接纳。恢复先提交时，迟到写入须被拒绝。历史缺证或排他覆盖不足时，保留原账并暂停自动恢复首次接纳。
3. **接受后续动作分别取证。** 实际创建、实际唤醒和外部操作生效分别查证。接纳凭据检查的保证止于接纳边界，已提交接纳的在途操作仍须独立查证。外部操作的时点因通道而异。

**静态证据。** Grok 核对的现行 `begin_run` 只检查域和未完成运行，尚无派发凭据核验。`finish_run` 在确认退出或确认未创建后可释放域。现行协作入口使用原调用 UUID，`source_call_id` 无相应唯一约束。另有 `call_id='entry'` 的入口及直接调用 `begin_run` 的路径。覆盖范围以能否接纳同一预留为准，三类路径逐一判断并记录依据。相关源码见 `dispatch.py:69–102,194–196`、`execution_tracking.py:127–154,470–474` 和 `schema_definition.py:109–118`。

**候选假设。** 若旧版本仍可凭原 UUID 写执行行，同时绕开新稳定键映射和凭据检查，则新映射上的唯一约束无法约束该写入。仅新版本读取的作废凭据也有相同缺口。该推断待验证。

**U3/A3/A5 负对照。** 在独立旧进程通过派发查询后、进入 `begin_run` 前暂停其派发。让恢复任务接纳同一预留并完结，确认执行域已释放，再释放旧派发。以释放时刻为基线，只计此后由迟到派发新增的已提交接纳、实际创建及实际唤醒。合格为 **0/0/0**。出现任一新增接纳即证伪候选，即使创建和唤醒均为零。恢复任务自身的次数不计入。待实测旧版本与新版本混跑、原 UUID 与新稳定键的映射、所有可接纳同一预留的入口，以及归档、迁移后历史记录和拒绝条件的可用性。

**状态记录同步依据。** 根据本节的条件性一致及待实测判据，将 [REQ-004 状态记录](../requirements/tracking/REQ-004.md) 的方案设计证据更新至 0.40 §4.40。需求仍为「设计中」。

## 4.44 首次接纳与后续取证条件

依据 REQ-004 1.4、§§4.40–4.43 和 entry-4986 Grok 回执，负责人选定部署切换屏障与同事务历史核验作为首次接纳的设计首选。持久代次可用于新版写者资格核验。原调用身份的唯一约束承担重复接纳保护。

### 生效限制与停止仲裁

- 旧写事务未证排空、切换后持续拒绝未证，或相关历史归属无法唯一确认时，暂停受影响的自动首次接纳。旧写拒绝覆盖运行写入边界及直调。归档先保全权威关联，迁出失败保留热详情。

采纳跨进程共同仲裁要求。首选候选为同主机上按数据库实例和 job_id 标识的操作系统命名互斥量，配合数据库中的持久停止状态和逐路唤醒意图。所有停止提交、领取、派发及实际唤醒路径须进入同一仲裁对象。实际唤醒持有互斥量跨越系统调用，进入后重读持久停止状态，先持久登记意图再唤醒。停止先提交则拒绝后续动作。先唤醒则停止后进入清理并独立取证。唤醒意图已提交但结果不明，或发现锁被遗弃时，恢复先核对原运行、进程和清理证据，缺证暂停，禁止再次唤醒。进程内锁无法覆盖第二进程。仅用数据库状态更新会在提交与唤醒之间留下竞态。

该候选待核实跨用户或服务进程的可见性和权限、锁顺序、进程崩溃恢复以及所有入口的覆盖。若运行拓扑无法提供同一对象，须另选有统一停止和唤醒所有权的执行服务，相关自动动作在仲裁未证时暂停。实施后验证停止先提交时相应动作增量为零、唤醒先发生时独立取退出证据，以及意图落盘后崩溃时不重复唤醒。

**仲裁与恢复契约**

- 同主机首选按稳定数据库实例标识和原 `job_id` 命名的操作系统互斥量。先取共同互斥量，再进入迁移保护及数据库事务。禁止持数据库事务或迁移保护等待互斥量。各路在锁内重读持久停止状态并核对领取和派发资格。实际唤醒前先提交绑定原调用及运行身份的唤醒意图，持外层互斥量跨越 `ResumeThread`，结果另行持久记录。
- 停止先提交则后续新增领取、派发和实际唤醒均为零，已创建但未唤醒的进程走清理入口。实际唤醒先发生则停止提交后按原运行身份清理，独立取得退出证据。
- 遇未决唤醒意图或遗弃锁，恢复只核对原接纳、进程身份、唤醒回执与清理证据，确认身份后可清理。禁止补唤醒和仅凭 PID 清理。缺证则保留原账并暂停该路，新增唤醒为零。
- 若拓扑无法共享同一对象，备选为统一执行服务独占创建、实际唤醒及停止提交，其余入口只送请求。备选须满足同等仲裁、入口覆盖及恢复约束。仲裁未证时，受影响范围暂停自动唤醒及依赖该仲裁的自动首次接纳和自动重试。继续适用 §4.48 对接纳、缺证重试及默认共享写根的限制。U1/A4 的持久受理须严格早于固定 180 秒截止，恰好 180 秒归到期，自动释放零次。

**实施前核对**

- 同库的路径别名、不同进程与服务身份须用同一数据库实例标识及原 `job_id` 解析到同一对象。逐一记录参与进程所在主机、会话、账户、命名空间和访问权限。同一会话可采用 `Local\`。同主机跨会话采用一致的 `Global\` 名称及显式 ACL，确认全部必要身份均能打开及获取同一对象。命名或访问条件缺证时保持暂停。
- 列出停止提交、领取、派发、实际唤醒及已创建未唤醒进程清理的完整调用路径，覆盖 Web、Worker、恢复、直调及适用的 MCP 路径。逐条核对共同仲裁、持锁阶段、迁移保护及事务顺序。实际部署拓扑、权限和完整入口清单待核对。

**实施后运行验收**
