# 规范澄清草稿：需求分析／需求设计／复盘必须落草稿

状态：已形成正式记录（entry-4328 用户确认落地）。0.2 一致稿为拟改基线，已落地到三份正式规范，正式规则见 §6 关联的正式规范正文。

## 1. 来源与需求基线

- **来源**：用户 entry-4320（「至少需求分析，需求设计，复盘这三个行为必须要文档，也就是必须要草稿，随意的闲聊无所谓」）。
- **需求基线**：
  - 需求分析、需求设计、复盘 **三类行为必须产出文档（草稿）**。
  - 随意闲聊／纯寒暄／无实质工作的问答 **无需落稿**。

## 2. 归位判定（含两方检视结论）

| 行为 | 归属 | 处置 |
|---|---|---|
| 需求分析 | `requirements-analysis-spec` §4.2 | **重写载体段**：实质需求分析形成的基线必须落草稿，instruction/handoff 只用于引用或摘要，不再是基线的唯一载体 |
| 需求设计 | `design-decision-record-spec` §2–§4（内容义务已覆盖） | 横切规则写清触发点；设计规范加一句载体回指（非阻断） |
| 复盘 | 无专门规范 | 由 `document-management-spec` 横切规则点名（讨论规范有单 Agent 排除项，不能承载） |
| 闲聊 | 各规范 `not_applies_to` | 显式「无需落稿」，按实际行为判定 |

## 3. 拟改文本（一致版）

### 3.1 `document-management-spec`：在 §2.5 之后新增第 6 条（横切落稿义务）

- **目标位置**：`specs/DOCUMENT_MANAGEMENT_SPEC.md` §2，第 5 条（现第 33 行）之后新增第 6 条。
- **拟新增文本**：

> 6. 需求分析（实质需求，非纯寒暄）、需求设计（实际开展的方案设计、评估或实质修订，含尚未定案的候选）、复盘（对实际事件、故障或调查开展的实质复盘）三类行为，须在形成或更新相应基线／方案／复盘结论、并进入依赖它的下一步（设计、实施或交接）之前，落同主题草稿（至少落 `docs/drafts/`），记录关键结论与依据。随意闲聊、纯寒暄、无实质工作的问答无需落稿；一段闲聊转入上述三类行为时，从触发该行为起适用落稿。例行进度回报、简单收悉按相应规范的 not_applies_to 判定。

### 3.2 `requirements-analysis-spec` §4.2：重写载体段

- **目标位置**：`specs/REQUIREMENTS_ANALYSIS_SPEC.md` §4.2（现第 55 行）。
- **原句**：

> 记录可用现有instruction、handoff或同主题文档，不强制每条消息建文件。跨人／跨阶段持续复用的基线放同主题草稿并引用有效版本／章节；已有可承载同主题记录时复用。需求理解记录与文档前置拟改草稿用途不同，不相互豁免；文档生命周期遵守[文档管理规范](DOCUMENT_MANAGEMENT_SPEC.md)。

- **拟改后**：

> 实质需求分析形成或更新的需求基线，在交接或进入依赖该基线的设计、实施前，须写入同主题草稿（至少落 `docs/drafts/`）；轻档仍可只写最低理解记录，已有同主题草稿可追加，instruction、handoff 用于引用或摘要，不作为基线的唯一载体。跨人／跨阶段持续复用的基线另须引用有效版本／章节。需求理解记录与文档前置拟改草稿用途不同，不相互豁免；文档生命周期遵守[文档管理规范](DOCUMENT_MANAGEMENT_SPEC.md)。

### 3.3 `design-decision-record-spec`：载体回指（非阻断）

- **目标位置**：`specs/DESIGN_DECISION_RECORD_SPEC.md` §2（何时落盘）或 §3（落在哪里）。
- **拟新增一句**（回指统一草稿载体义务）：

> 设计文档的草稿载体与「先落草稿再转正」义务遵循[文档管理规范](DOCUMENT_MANAGEMENT_SPEC.md)。

- 此项为非阻断；内容义务（§2–§4）已覆盖，仅补载体回指，避免设计与文档两规范口径不一。
