## 3. 机制和归因

- **卡片等待**。调度器在一次负责人决策后仍无可运行工作时可自动设为 `blocked`。卡片 `answer` 可从 `blocked` 或 `waiting_user` 唤回负责人。4343 已请求协作，须核验失败任务的重试资格及授权是否生成了可运行任务。此路径解释了可能的表现，历史 phase 未恢复。[调度服务](../../workbench/collaboration/collaboration_service.py)、[卡片动作](../../workbench/collaboration/collaboration_actions.py)。
- **旧任务依赖**。三次拒绝均可对应到当前计划缺失的依赖项。旧成果可作为新任务的输入，任务依赖由当前 job 的任务图表达。同一 job 的增量计划对已有任务的引用是另一种情形，已有设计专门讨论解析层与合并校验。[协议校验](../../workbench/collaboration/collaboration_protocol.py)、[调度设计](../design/COLLABORATION_DISPATCH_DESIGN.md)。
- **双行邀请**。入口解析限制协议之后只能有一个终止邀请行。邀请解析器读取末行，尾部校验拒绝整个多行尾部。此次有两位计划内接收者，故障在格式层。实际把有效邀请发给错误接收人的案例尚未定位。[入口解析](../../workbench/collaboration/collaboration_entry.py)、[邀请解析](../../workbench/collaboration/collaboration_invitation.py)。
- **完成证据失败**。Grok 适配器检查正常完成证据，缺失或不支持的 `stopReason` 会使调用失败。这是任务失败的上游原因。后续能否重试还取决于调度规则。[Grok 适配器](../../workbench/adapters/grok_adapter.py)。

## 4. 设计协作的语义与规范

4357 明确指定牵头人、先转正再设计的顺序及文档参考结构。此前同一主题的三方一致要求明确针对需求分析。两份参考设计提供协作惯例：并发设计由两方独立检视，目录重组有两方独立提案和针对同一 0.2 的检视。用户随后明确设计也须三方一致。[并发设计](../design/CONCURRENCY_VERIFICATION_DESIGN.md)、[目录重组设计](../design/SOURCE_LAYOUT_DESIGN.md)。

设计规范 1.4.1 §1、§2.1 涵盖单人和多人设计，并要求核对有效基线和用户原意。讨论规范 1.3.1 §§6–10 规定讨论何时可结束、何时可等待裁决及预算说明。两份规范均未规定所有设计默认采用三方。现场可确认入口遗漏了用户预期的协作环节。尚缺完整上下文注入记录和对照实验，无法区分模型如何权衡历史惯例、当时呈现给模型的上下文是否充分，以及项目是否需要明确默认路由。[设计规范](../../specs/DESIGN_DECISION_RECORD_SPEC.md)、[讨论规范](../../specs/AGENT_DISCUSSION_SPEC.md)。

### Grok 重试后的独立复核

工作台 entry-4514 记录首次调用 e849c804a1e644db960f54e1296ce508 已派发，因正常结束证据缺失或 stopReason 不受支持而失败，载荷为空。用户授权后以独立任务重试，调用 e5c31ff2f08f4daaa332edbe5b909591 已完成并返回有效回执。Grok 的独立分析与 Codex 补查主结论一致，并补充以下源码证据。

- **提示差异**：入口的 `entry_prompt` 提供 JSON 示例，有任务时要求计划。后续 `collaboration_service.call` 以文字说明协议，默认可省略计划。两条路径的角色规则不同，固定模板可分别明确适用条件。具体历史空任务报错与提示差异的因果关系仍待证。
- **拒绝后的状态**：入口在创建协作前拒绝格式错误并标记入口消息失败。`accept_result` 中协作者失败记为调用失败，主循环据此记任务失败。负责人或最终答复者在该接收路径失败时，协作也会进入失败状态。
- **校验顺序**：Grok 适配器先校验正常结束证据，成功返回的回复才进入协作协议解析。首次调用止于适配器检查。现有出口校验仍负责拦截非法字段和尾部格式，所查路径未发现把错误反馈给模型以自动修正回复的流程。

候选机制仍待选定。Grok 的 CLI 原生 schema 探测被取消，结构化输出支持和回退能力未实测。用户报告的多目标报错仍缺原始失败回复。补录时的 13/20 调用快照显示首次格式任务仍为 failed，原汇总仍为 pending，独立重试已完成。

## 10. entry-4530 Agent 失败后的重试

用户询问现行重试规则，并提出把重试纳入路由修复。范围包括失败分类、重新派发、依赖恢复与收尾。本节记录候选规则和验收，方案待定。

**现状。** 工作台主调度只派发已授权且依赖全部完成的 pending 任务。工作台代码中，Codex、DeepSeek Harness、Grok 的调用包装均未见失败后重新启动调用的循环。CLI 或服务内部的请求重试未实测。协议拒绝也未见仅修正回复的重试路径。调用预算默认 20 轮，协作者派发检查额外预留 2 轮，预算不足时不派发。这是协作总预算，当前未见每任务重试上限。见 [调度](../../workbench/collaboration/collaboration_service.py)、[生命周期](../../workbench/collaboration/collaboration_lifecycle.py)、[通道包装](../../workbench/adapters/web_backends.py)及[预算测试](../../tests/unit/test_collaboration_lifecycle.py)。本轮静态核对测试，未复跑。

entry-4514 中，Grok 首次调用在协议解析前因结束信号检查失败。负责人追加新任务并授权后重试成功。下游仍依赖原失败任务，最终由「结束协作」取消遗留待办并进入交付。首次调用返回失败时，工具是否执行过未确认。

| 场景 | 候选规则 | 可观察验收 |
|---|---|---|
| 可确认尚未执行的临时故障 | 有界退避重试，同一逻辑任务关联不同尝试，每次计入协作预算 | 首次失败和重试分别可查，只有验收有效结果后下游才派发一次 |
| 已取得回复但格式有误 | 用校验诊断和原回复进行仅文本修正，禁止该修正调用执行工具，再校验内容、授权和依赖 | 有修正回执，工具调用数不增加，非法或越权回复仍被拒绝 |
| 超时或缺正常结束信号，可能已执行工具 | 先核实状态。只有确认未生效或已有可靠幂等保证时才考虑重放，否则交负责人处理 | 模拟工具已写入后断连，确认无重复写入并显示待核实原因 |
| 用户取消、达到任务上限或协作预算不足 | 停止新尝试，取消或明确标记已无法满足依赖的任务，保留可用结果与失败原因 | 取消与重试竞争时不再启动新调用，耗尽后可汇总已有结果或明确报告无法收尾的原因 |

保留手动追加的成本较低，但需要显式替换旧依赖并处理遗留待办。将尝试归到同一逻辑任务，需要持久化尝试状态并防止重复接受结果，但能让下游继续引用原任务。次数、退避、可重试类别及各通道的幂等能力需在选型时验证。

### 12.2 契约与实施依赖

1. 先固定角色、状态及错误阶段的契约。正常结束证据 → 解析与字段校验 → 事务内复核计划和授权 → 调度计算就绪。协议合法、任务可派发、执行完成分别记录。Grok 缺少正常结束证据发生在解析之前。旧回复省略计划、显式空计划与入口完成态携带任务的保护继续纳入兼容回归。
2. 再设计重试和收尾状态。区分逻辑任务和调用尝试，通过当前尝试标识与状态条件原子接受结果。取消与启动使用同一状态边界，已终止的 job 不开放新尝试。活动任务、待核实副作用及仍可恢复的依赖均参与收尾判断。进程退出与任务状态分别取证。旧记录沿用原终态和预算，以历史调用关联尝试，缺失项保留未知。失败分类、次数、退避和存储细节待定。
3. 将并行接入与事件输出一起验证。先用可控执行器覆盖预算争抢、重复回传、依赖未就绪和取消。再逐通道验证真实入口、运行区间、结束前输出、工作区隔离和实际退出。仅文本修正前须逐通道验证工具确实被禁用。Grok 现有 deny 参数仅作查证入口，Codex 只读沙箱仍可能允许工具，DeepSeek Harness 的现有接线也未证明工具可禁用。能力未经验证时保留字段诊断和人工处理。
4. 引入前核对旧 job 与原始结果可读，回退应先停止新派发并处理活跃调用，再关闭新增执行路径。保留已写入的调用、预算与失败证据。迁移兼容与回退演练在实施方案明确后验证。
