## 2. 澄清确认 → 澄清记录

**解决谁的什么问题？** 使用工作台组织多 Agent 协作的用户，在任务交接、失败恢复和结果汇总时，被格式错误、遗漏角色、悬空依赖和空问题卡片打断；需要已明确授权的协作按正确对象和阶段继续，结果及受阻原因可理解，无需重复输入来推动本可自动进行的工作。

**何时／何地？** 一次新协作、同协作追加任务、失败后恢复、多个目标可同时执行、停止或预算将耗尽、最后交付等工作台场景。**为何？** S1 明确用户体验受损，S3 明确缺少实际并行和分别输出。**如何观察改善？** 按 §5 的场景逐项取证，不以 Agent 自称完成代替派发、界面或终态证据。

**成功数字是什么？** 非法请求或重复提交新增派发 0 次。当前尝试的有效成功使已授权且未取消的下游满足全部依赖时，该下游释放 1 次，其余情形新增释放 0 次（A1–A5、A8）。并行以 S3 和复盘 §8 为据，最小样例为同一次合法请求中 2 位不同 Agent 的 2 项独立任务，各首次派发 1 次，同一可靠时基下重叠区间长度大于 0（公式见 A6），2/2 路均在各自完成前显示归属正确的中间输出（A7）。更多并发受授权、就绪、预算及容量约束，实际容量待确认。

**本次不做什么？** 见 §4：本次交付是需求分析及必要规范修订，不执行产品修复；不恢复删除设计，不重开 DLL/MXC 六项改进，不默认所有设计三方参与，不新增跨 job 直接依赖、不指定技术架构。

## 4. 优先级与范围 → 范围说明

本次文档范围纳入 R1–R8 全部需求与验收分析，U1–U3 具体依赖部分保持待确认/待验，不把未冻结等同排除。建议后续优先保证正确对象、授权、恢复、停止及收尾（R1–R5/R8），并将实际并行和分别输出作为同一用户效果验收（R6/R7），不是分两次验收后拼成成功。顺序基于错误派发/副作用风险与依赖，最终服从用户，不形成新的实施计划。

明确不做：本任务不改产品代码或运行态，不提交合入发布；不重开已完成的 DLL/MXC 六项；不将所有设计强制多人；不引入新框架或确定数据库字段、锁/CAS、接口和算法；不把跨 job 任务直接互引当既定能力；不复活旧稿技术决定；不以外部框架重试规则代替本项目授权；不承诺任意共享写任务立即可安全并行。原生 schema、自动文本修正、换 Agent、额外预算预占均是后续可比较手段，不是当前必做功能。

R6 的授权/依赖安全以 R2/R5/R8 约束为前提，R7 的用户效果验收依赖 R6 的同次重叠运行。R3 自动尝试受 U2 及副作用证据约束，R4 到期行为受 U1 约束；已明确行为分析可继续，不进入依赖未知的实现。
