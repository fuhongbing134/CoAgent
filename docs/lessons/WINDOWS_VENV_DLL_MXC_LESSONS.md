# Windows 虚拟环境 DLL 故障与 MXC 排查教训

正式记录 1.0。entry-4300 授权整理，依据 entry-4290 三方复盘与[原调查及形成记录](../drafts/CODEX_WINDOWS_VENV_DLL_MXC_INVESTIGATION.md)。本机验证范围见下文，排查方法的后续使用效果尚待观察。

## 1. 故障和本机验收

在调查记录所列 Windows、CLI 与 CPython 版本下，工作台 Codex 的旧 `elevated` 启动链经原 `.venv` 启动器派生 Python 时，`_ctypes`、`_ssl` 导入报 Win32 1114。同一工作台、目录和权限下，直接启动基础 Python 可以导入。ProcMon 记录主要依赖从相同路径映射，WinDbg 在原失败进程捕获 `USER32.dll` 的 `DLL_PROCESS_ATTACH` 返回失败。同期读到的 `STATUS_ACCESS_DENIED`、无效句柄状态及私有桌面是取证线索。具体拒绝对象、访问掩码、系统调用，以及桌面、令牌和 Job 各自的作用仍未知。更早的同类症状缺少等价断点证据。

同一基础解释器创建的临时环境与原环境启动器 SHA-256 相同，两套环境在旧链上均失败，临时环境在普通终端通过。这推翻了本案的同版本重建建议。项目级配置随后选择 MXC，仍使用原任务权限配置。真实工作台新建和续接通过导入验收，停止试验确认启动器和解释器均退出，停止后同会话再次续接也通过。

普通宿主与 MXC 配合 `step1-git` 各运行 202 项，201 项通过、1 项跳过。MXC 使用默认 `:workspace` 的完整套件仍出现 6 项本地 HTTP 回环错误，外层验证入口经虚拟环境启动时也曾报告 MXC 不可用。以上是历史实测，细节见[调查记录 §3–9](../drafts/CODEX_WINDOWS_VENV_DLL_MXC_INVESTIGATION.md)。

## 3. 可复用的排查步骤

1. 固定实际 CLI 路径与版本、工作目录、任务权限和运行中观测到的沙箱后端。记录父子进程和实际解释器，用独立的最小导入探针收集退出码。跨环境成功只覆盖对应启动链。
2. 评估是否值得重建时，先用同版本基础解释器建立临时实例，在原失败链对照。比较同类启动器及结果，保留原环境。若两组同样失败，转向共同启动条件。
3. 主要依赖已映射但仍报初始化失败时，尽早协调宿主侧取证。对真实失败进程捕获加载与初始化，保留通过组作对照，分别记录文件访问、初始化返回值和同时出现的线程状态。
4. 通过实际入口验收。先核实后端及原解释器导入，再测新建、续接和取消。完整单测还要核对外层与内层解释器、临时目录和回环权限，记录退出码、发现数和跳过原因。协作协议中断时单独记录交接缺口。
