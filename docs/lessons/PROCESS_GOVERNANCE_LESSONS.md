四项要求均合理。以下保存正式处理方向和依据，详细比较与异议保留在草稿；正式归档不表示相关spec已经拆分或更新。

| 问题 | 选定处理 | 依据与提出来源 |
|---|---|---|
| U1：所有文档须有落盘草稿阶段 | 人工维护文档新增或修订先保存草稿，允许同任务多文件合并记录。讨论首次落盘本身就是草稿，不递归创建草稿；已有正式文档从下次修订留稿并披露旧缺口。转正保留草稿基线并双向关联，后续修订追加分隔记录，避免永久维护两份相同正文 | 用户明确要求；Codex C1综合，Grok与DeepSeek交叉接受。合并记录兼顾追溯和成本，不以机械修改为由取消草稿阶段 |
| U2：问题来源、接受情况和理由须可追溯 | 草稿写完整来源、具体问题／主张、接受状态、依据、对应选择及实际更优备选；没有真实备选不硬凑。正式文档只留各点选择、依据及必要关联。统一历史字段为本文件文末六列 | 用户要求；两端及Codex共同支持。问题处理映射与时间演进历史分开；合理归组不得丢失各自主张和处理映射 |
| U3：编码和检视只约束各自过程 | 编码规范管理作者实现、自查、审核包和返修；检视规范管理非作者独立检查、证据有效性、分级、批准与复审。审核包绑定基线和版本，含目的、范围、自查／测试、未测项及文档影响；批准不替代操作授权 | 用户明确要求拆分；三端支持按职责切分。作者自查不能替代独立检视；拆分前须建立旧条款去向及有效引用迁移表，避免漏掉全量复审、图文同步等义务 |
| U4：需求提交后先分析目的、合理性、方向、优先级和范围 | 默认负责人承担需求分析职责，产出落同一主题草稿并传递。轻任务至少说明目的与范围，标准任务补方案、验收和未知项；规范变更、重大范围、昂贵／不可逆或关键歧义等事项由现有非实施者独立挑战。已有授权充分时继续，改变目标、范围、验收或关键歧义才交用户裁决 | 用户所述问题；Codex C5及两端分层分析意见。价值、风险、依赖和成本决定深度，当前不默认新增固定PM Agent或普遍审批关卡 |

无关联主题的机械修订可在持续维护草稿中先记拟改文本、来源、接受及理由，再更新正文；候选载体名为 `docs/drafts/MAINTENANCE_REVISIONS.md`，尚未创建。该名称是整理建议，不冒称用户指定或生效条款。轻档分析示例：“目的：消除README用词歧义；范围：只改该句，不改变功能承诺。”

## 4. 相关改进的优先级

1. P0：草稿生命周期与逐项追溯、编码／检视职责及交接、需求分析职责。条款迁移和有效引用映射是拆分前提。
2. 与U3同步：新写或实质修改的自制工具，若结果拟作正式证据，且运行昂贵或隔离／oracle／统计难以事后核对，先实现、自查及有限隔离冒烟，再独立检视工具，之后正式长跑并独立复核数据。普通项目单测、提审冒烟不额外设置长跑审批门。
3. P1：失败、取消、阶段交付时负责人保护证据，更新正文和索引，标明未审项及承接顺序；不让失败任务静默取消后续职责。
4. P2：工具说明覆盖目的、输入输出、副作用、复杂同步理由及证据边界，不按注释数量或逐行注释衡量可理解性。

这些改进与E2—E5有直接因果联系；当前不新增自动拦截器、状态机、固定第四身份或全仓历史回填。
