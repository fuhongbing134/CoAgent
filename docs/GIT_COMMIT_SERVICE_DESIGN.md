## 2. 背景与目标

统一服务让所有接入的 Agent 使用同一种提交能力，避免把执行能力固定给某一 Agent。实际任务仍可只授权其中一个 Agent 提交；具备接口不意味着随时获准提交。提交产生可供审核绑定的 commit ID，不代替非作者审核或 main 合入门槛。

本期目标是指定仓库、指定功能分支上的受限提交及结果查询；不开放 push、main 合入、分支创建或切换、force、reset、清理工作区等命令，也不接收任意 shell 字符串。远端发布与合入仍保持现有用户执行安排。

## 3. 服务形态与事实边界

`Agent → MCP 工具适配（复用 agent_bridge）→ 统一 Git 服务（服务端执行）→ Git`

MCP 是 Agent 接入层，HTTP 可作为适配层与服务的内部传输；两者不构成互斥选项。执行核心集中处理身份、授权、仓库检查、互斥及结果记录，避免各入口各写一套规则。部署位置、传输鉴权和单实例约束见第8节，尚未指定必须在 web_chat.py 内实现。

服务通过正常配置获得仓库写权限及操作授权，**不是绕过沙箱**。前轮当前 Codex 会话的 `.git` 明确只读，仅能证明该会话的限制，不能推广为所有 Agent 的权限；DeepSeek 和未来 Agent 的实际运行权限须分别核对。服务自身能否写 Git 元数据也需部署验证，不能从工具名称推导。

项目内依据：`agent_bridge.py` 使用 stdio MCP，各客户端可能启动独立进程；`AGENT_ID` 来自环境变量。现有消息桥登记信息不是可信 Git 授权凭证，页面 capability token 也不是 Agent 身份证明。复用接入方式不等于直接复用现有身份信任模型。

## 4. 接入、授权与互斥分别处理

| 概念 | 责任与边界 |
|---|---|
| 接入能力 | 所有获配置的 Agent 可发现并调用共享接口；每个新增 Agent 需验证实际接入，不宣称未来任意客户端自动兼容 |
| 提交授权 | 服务按可信调用身份、任务、仓库、分支和有效范围判断；某任务可仅允许 Codex，另一任务可允许 DeepSeek；调用者不能凭自填身份或任务号获权 |
| 执行互斥 | 同一工作区的提交串行，多个 stdio 适配进程须受同一协调机制约束；串行不代替授权 |

授权在实际执行前重新核对，等待期间被撤销或范围变化则拒绝执行。授予、撤销主体及其可信入口待决定；不默认让 Agent 自授提交权。

仅在每个 MCP 进程中创建进程内锁不足以协调多个进程。可由单执行服务统一协调并保证单实例，或采用跨进程锁；选型须覆盖全部服务实例。不得持有 SQLite 写事务执行整个 Git 子进程；租约超时也不能直接放行第二个提交，需确认旧执行已退出或进入受控恢复。

锁只约束遵守服务协议的执行者，不能阻止用户直接执行 Git。执行前仍需核对 HEAD、分支、暂存区；工作区或 Git 状态变化时应拒绝或进入明确恢复流程，不能声称服务锁提供绝对隔离。不同 worktree 的共享 Git 元数据及锁范围须在支持前明确，首期不默认支持任意并行 worktree。

## 5. 首期接口契约

以下为接口语义，MCP 工具最终命名、错误码与响应格式在实现细节中确定。所有接口包括只读与结果查询均检查调用权限。

| 接口 | 输入及输出约定 |
|---|---|
| status(repository_id, task_id) | 返回获准仓库的当前分支、HEAD、暂存及未暂存状态，不修改工作区内容或引用 |
| diff(repository_id, task_id, files) | 返回明确文件范围的待提交差异、当前分支与 HEAD，以及服务生成的 expected_diff_digest；包括允许的新建、删除等变化，不遗漏二进制或文件模式信息 |
| commit(repository_id, task_id, expected_branch, expected_head, files, expected_diff_digest, message, operation_id) | 校验并提交获准快照，成功返回 commit_id、父提交、实际文件清单及内容摘要；不将退出码独自当作完整成功证据 |
| operation_result(operation_id) | 在可信调用者的授权范围内查询原请求的处理中、成功、失败或结果待核实状态；成功结果含原 commit_id |

repository_id 由服务映射至受控仓库路径，不接受任意路径选仓库。files 是显式字面文件清单；身份从可信连接绑定而非 commit 参数获得。提交信息需非空、限长，保留实际代码作者与提交操作 Agent 的区别，不能用代提交掩盖作者资格。

operation_id 在可信调用者及仓库上下文中唯一绑定请求内容；同一 ID、相同内容返回原状态或结果，不重复创建提交；同一 ID、不同内容拒绝。结果查询不能读到其他调用者无权查看的请求。响应丢失后先查询原请求，不新造 ID 盲目重试。

## 6. 提交检查与失败语义

1. **分支与仓库**：仅允许获授权的功能分支，拒绝 main、分离 HEAD 及不支持的仓库状态；预期分支与 HEAD 必须匹配。Git 参数用受控参数数组构造，不拼接 shell 字符串。
2. **文件边界**：拒绝绝对路径、越界、Git 元数据路径及路径模式注入；按字面解析文件，明确重命名的两端范围。检查敏感文件授权；白名单不是敏感信息审查的替代品。
3. **暂存区**：已有他人或来源不明的暂存内容时拒绝并报告，不顺手提交、不自动清空。首期可采用“进入提交前暂存区必须为空”的保守策略，具体策略待第8节定稿。其他未声明、未暂存文件存在改动不必全拒绝，但必须保持不被提交。
4. **贡献归属**：同一文件被多个 Agent 修改时，路径清单无法区分贡献；服务不能假装从 status 推断作者。调用者需确认完整差异属于获准任务，无法分清则停止提交，不猜测拆分。
5. **内容快照**：服务生成摘要，绑定文件集合、变化类型、实际拟提交内容、基线及必要元数据；不能只哈希文件名或展示文本。取得互斥后重新验证，暂存后核对拟提交内容与预期一致。摘要检测不等于冻结工作区，选取的快照机制须防止校验与实际提交之间被修改，具体实现待决定。
6. **实际执行**：执行前复核授权及 Git 状态，记录 operation_id 与执行意图；不持有数据库写事务等待 Git。受控快照、Git 引用更新及操作结果数据库不是天然同一事务，须设计故障恢复，不能仅添加 operation_id 字段便宣称幂等成立。
7. **结果及恢复**：核对新提交的父提交、实际树及文件范围；记录 commit ID 后返回。超时、崩溃或数据库落盘失败导致结果不明时保留“待核实”及阻断范围，先核实引用/提交与原请求的对应关系，再决定恢复；不得自动 reset、删历史或重复提交。服务造成的暂存变化如何在不覆盖用户改动的前提下恢复，属于实施前待决项。

hooks 可执行任意项目脚本或改变文件，需明确受信策略、执行环境、超时与副作用边界；不能不经决定就沿用全部本机 hooks，也不能默默跳过项目要求的检查。首期无 push，不应向 Agent 暴露远端凭据；服务日志和错误输出需脱敏，签名密钥或其他本地凭据也需按实际使用保护。

## 7. 方案取舍

| 考虑过的方向 | 决定与理由 |
|---|---|
| 仅写规则，让所有 Agent 直接执行 Git | 不作为统一方案；环境权限可能不同，也无法统一强制任务授权和执行协调 |
| MCP 或 HTTP 二选一 | 不采用；MCP负责Agent接入，HTTP可作内部传输，策略统一在执行核心 |
| 各 stdio 进程各自执行加普通锁 | 不采用；锁不跨进程，无法覆盖共同工作区 |
| 所有未声明文件有改动就拒绝 | 不采用；过度限制无关工作，重点是不提交它们并保护已有暂存内容 |
| 只有固定一个 Agent 能提交 | 不采用；与全员接入目标冲突；按任务授权和串行执行满足临时限制 |
| 首期同时实现 push/main 合入 | 暂缓；先验证本地提交链路，保留现有合入审核和用户执行安排 |

## 8. 待决实现细节与风险

| 待决点 | 实施前需要明确 |

| 可信身份绑定 | 谁配置适配进程凭证、如何绑定 Agent 与任务，如何防止自填 AGENT_ID 冒充，凭证如何隔离和失效 |
| 授权授予与撤销 | 可信管理主体及入口、仓库分支文件范围、有效期、任务结束和撤销后的处理 |

| 内容快照与暂存 | 摘要编码、二进制/新建/删除/模式变化处理、原暂存保护、检查与提交竞态、外部Git并发的支持边界 |
| 幂等与恢复 | 请求状态持久化、Git成功而结果未落盘时的可靠识别、何时解除阻断、保留期及结果查询权限 |

现有消息桥与页面鉴权并未证明足以支持这些要求。首期实现选择须经负责人讨论、记录后再执行；本记录不承诺能对不受控的外部进程提供绝对隔离。

## 9. 验收计划与交付顺序

先在隔离临时仓库验证，按需要配置本地 bare 远端以模拟仓库拓扑；首期不调用 push，不因准备本地远端扩大接口范围。至少覆盖：

- 两个 Agent 均能接入，同一任务只授权其中一个时另一个被拒绝，撤销授权立即影响后续执行。
- 正常提交恰含声明内容，返回的 commit ID、父提交、树与范围可核查；main、越界路径、路径模式注入及不支持状态被拒绝。
- 已有暂存内容得到保护，未声明的未暂存改动保持原样；同文件贡献无法分清时拒绝。
- diff之后内容变化、HEAD变化、分支变化、暂存区变化及两个适配进程并发得到明确处理，不产生夹带。
- 相同operation_id重试返回原结果，异内容复用被拒绝；覆盖响应丢失、服务崩溃及Git成功而结果落盘失败，不重复提交。
- hooks失败、超时、旧执行未退出及凭据相关输出符合决定的策略，恢复不丢用户改动。

隔离验收通过后，正常配置服务权限与两端接入，再依据明确任务授权接真实仓库验证。相关代码须完成作者自查、非作者review和适用回归；测试、审核证据绑定实际版本。只有真实接入验证完成，才能宣布每个受支持Agent实际具备提交能力。

本轮交付仅为本文及索引登记，未实现服务、未授予提交权限、未运行上述验收。后续先解决第8节关键问题并更新记录，再按授权进入实现；实施和验证后补实际结果。存在未知结果时先核实，关闭或回退服务不应回滚用户已有提交或工作区改动。
