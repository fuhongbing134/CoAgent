# Git 自动化设计记录

## 当前方案：一次授权，工作台自动完成 Git（P2.1，entry-2225）

**文档状态：已决定；方案状态：三方一致，宿主接线已编码，本地验证完成后送双审核，目标环境尚未验收。** 当前方案取代旧的手填 host.json 任务绑定、三套 Git MCP 和用户配置审批 ACL 的使用路径。以下 G1–G10 为批准版本 P2.1；P2.1 仅修正 P2 的 G6 停止条件，其余条款不变。历史实现与测试证据在下文保留，不能作为新流程完成的证明。G10 中的“当前”描述批准当时；本轮实施与验证状态见下一节。

设计留痕依据：[设计决策留痕规范 v1.1.0](../specs/DESIGN_DECISION_RECORD_SPEC.md)。P2.1 共识记录及当时适用规范见文末折叠附录；进入实施时重新判定适用规范。

### 目标

必要时完成浏览器登录，之后由工作台和三个 Agent 自动完成 Git 功能分支流程；功能关联、分支基线、审核批准和执行状态由系统管理。

### G1：用户流程与范围

已有可用登录就直接使用；缺少登录时，由工作台引导完成浏览器授权。仓库可确定时不询问，确有歧义才问一次并保存。日常不要求填写 task、branch、base、审批文件、目录权限或三份 MCP 配置。授权过期可能需要重新登录，不承诺永久免交互。合入 main 必须由用户明确提出；本期只实现功能分支工作流。

### G2：宿主功能节点触发

采用工作台功能调度→共用 GitAutomation→Git。三个 Agent 通过现有任务调度参与开发和审核，不另外在 handoff 中发送 Git 命令。宿主在编码前建分支、编码结束后安排审核、审核通过后提交推送。宿主掌握执行条件，因此不另增 Agent Git 命令入口；审核结论仍须正式结构化契约，不等于完全不用扩展协议。

### G3：功能与阶段关联

入口 Agent 按用户语义制定开发计划，系统保存明确功能关联与任务阶段；普通聊天、方案讨论不登记为开发执行。每个功能自动获得稳定标识，编码、修订和审核任务关联同一功能。最小业务信息包括功能标识、任务阶段、实际作者、仓库、分支、当前基线和远端。作者取实际调度记录，Git 信息由宿主发现并保存；Agent 不自报执行身份。计划经严格结构及关联校验后才能进入编码。缺失或非法由系统要求 Agent 修正，不让用户补字段。具体协议键名、兼容策略在实施前落实，不能直接向现有白名单塞未知字段。

### G4：同仓库占用与不明改动

宿主按规范化仓库标识管理占用，覆盖不同对话；同一仓库同时只推进一个功能，第二个功能排队并展示原因。占用贯穿编码、审核和提交，Agent 退出不意味着功能占用释放。既有不明改动先识别来源；来源不能唯一确定时，不启动该功能，不把改动归入排队功能，只展示不明改动路径及暂停原因。不自动 stash、reset 或清空 index，不要求用户填写 task、branch 或 base。首期不建设 worktree 或跨进程锁，外部编辑仍须重新核对。

### G5：非作者审核与内容绑定

编码进程退出且释放确认后，宿主生成审核记录：审核标识、功能及轮次、基线、文件集合、内容摘要，并安排非作者 reviewer。reviewer 返回审核标识、明确结论和问题说明；其身份及任务关联取实际调用记录。只有指定审核调用的合法、有效通过结论才能形成批准。completed、正文通过或作者转述都不算批准。内容变化、基线变化或审核任务失效，批准失效并重新审核。提交前检查工作文件与 index，提交后核对实际 commit，再关联审核记录。释放与停止以 G6 为准。

### G6：结果事务、执行释放与停止

接收结果的数据库事务只保存合法结果及待执行状态，事务内不运行 Git。宿主在真正启动每项 Git 写操作前，核对功能有效、相关 Agent 执行已确认释放、仓库仍由该功能占用、当前操作所需前置条件满足，且任务既未停止，也未正在停止。提交推送必须有有效审核；编码前建分支不要求尚未发生的代码审核。未知退出不算释放；释放须沿用宿主已有退出证据规则，不以收到回复代替。

停止生效与操作启动必须协调，不能只做一次提前检查。停止生效后不启动新的 Git 写操作；已启动命令可能产生副作用，不承诺撤销。宿主记录并查询实际结果，停止后续步骤并保留现场。Agent 进程停止不等于宿主 Git 命令停止。释放失败或命令结果不明时停止自动推进，不把超时当作没有执行。

### G7：多轮提交与幂等恢复

一个功能可有多轮提交，每轮分别保存基线、审核、操作标识、commit 和推送状态。上一轮推送确认后，其 commit 成为下一轮基线。重复结果或重启恢复只查询原操作，不重复建分支或 commit。推送失败保留原 commit，先查询远端，再补推原提交；结果确认前不启动下一轮。内容改变必须形成新审核轮次，不覆盖旧操作记录。

### G8：认证、正常权限与信任边界

工作台检测其实际使用的 Git 和安全凭据管理能力，优先复用可用登录；需要授权时提供内置浏览器引导，不要求用户安装、学习 gh 或手写 token。凭据交系统安全存储，不写聊天、仓库或明文配置。

Git 使用工作台正常获得的权限。登录不代表 .git 可写，换脚本也不产生权限；宿主受限时展示原因及必要的正常设置步骤。本模型不防御同账户恶意本地进程；作者不自批依靠调度来源和接口分工保证正常流程，不是 OS 级隔离。用户不需要配置独立 OS 账户。

### G9：失败处理与必要用户交互

测试、hook 或审核问题交给 Agent 修订、验证、重审；不跳过 hook 或强推。网络故障按原操作恢复；冲突先由 Agent 分析处理。只有需要业务判断、仓库选择、重新授权或系统无法自行解决的权限问题，才向用户提出具体问题。工作台始终展示当前阶段、失败原因、已产生的 commit 和下一步，不让用户维护内部状态。

G7 的查询、补推与 G9 的网络故障恢复，均是宿主恢复原功能操作，不是新增 Agent Git 命令入口，与 G2 一致。

### G10：真实验收标准

验收包括宿主对目标仓库真实建分支、提交及推送；三名 Agent 分别作为作者走通工作台完整链路。另覆盖无登录引导、已有登录零操作、仓库选择保存、非作者审核、自审拒绝、修改后重审、多轮提交、失败补推、重复接收、停止竞争和同仓库排队。

status、remote 成功只算只读预检；临时仓库测试不能替代目标环境验收。全部测试都须保持 main 不变。当前尚未完成这些实现或验收。

### 实施记录（entry-2255，待双审核与用户测试）

旧修改无需整体回退。保留 `git_automation.py` 的内容摘要、index 核对、固定远端和幂等提交/补推核心；旧 `git_workbench.py` 与 stdio MCP 保留兼容，不再作为自动流程的产品入口。新增 `git_feature_workflow.py` 由 `CollaborationService` 直接调用，界面接入仓库选择、授权和原操作恢复。未改既有 MCP_SETUP.md 的手工步骤；新流程说明见 [GIT_WORKFLOW_USAGE.md](../guides/GIT_WORKFLOW_USAGE.md)。

具体接线：协议 v1 增量接受任务 `git_stage=code/revise` 及顶层 `git_review={review_id,approved,issues}`，旧计划不含阶段时保持旧行为。功能标识、轮次、作者、分支和远端由宿主保存；审核身份来自持久化的实际调用。用户不填这些字段。当前每个 job 对应一个功能，多个功能由入口拆成不同 job；同功能修订保持同一作者。

存储使用现有 schema v2 事务入口，惰性新增 `git_features`、`git_repo_owners`、`git_feature_reviews`、`git_repo_preferences` 四张表，不重写旧任务、调用或审批文件。规范化仓库唯一占用跨对话保存，选择的远端按仓库记忆；已停止或结果未知的功能保留占用和现场。无跨进程锁，同账户恶意进程仍不在防护范围内。

Git Popen 启动与停止接收共用短时进程内门闩，检查事务结束后启动进程，等待命令不持有门闩。每步复核工作阶段、退出证据、仓库占用及所需审核，避免停止后再启动。审核持久化精确文件/blob/模式和指定 reviewer 调用；失效内容新开轮次。推送恢复查询原 commit；不能确认的编码/分支/审核调用不自动重放。hook 明确非零退出、HEAD 未变且 index 仍精确等于本功能原暂存树时，可携带该 index 进入新修订及审核，不 reset 或清空 index；未知退出不适用该恢复。

认证实现限定当前 Windows 工作台：复用 Git for Windows 的 GCM，显式选择 `manager` helper 与 `wincredman`，缺登录时由任务卡按钮请求 GCM 浏览器授权；凭据输出仅在内存中交回 helper，不写聊天、数据库或文件。GitHub HTTPS 无远端时才询问地址；已有单远端自动使用，多远端选择后保存。非 GitHub HTTPS/SSH 使用已有 Git 认证环境，不承诺通用浏览器引导。依据 [GCM usage](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/usage.md) 与 [环境选项](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/environment.md)；实际宿主 helper、浏览器和权限尚未实测。

验证仅使用临时 SQLite、临时仓库/本地 bare 远端及脚本化 Agent 返回；包含宿主成功链路、三种作者身份、拒绝/内容变化重审、多轮及重启补推、未知退出、停止竞争、脏工作区与跨对话排队、远端选择/变更保护、中文路径、hook 修订、HTTP 来源/令牌检查及认证命令隔离。三种脚本化身份不是三个真实 Agent 验收。本轮未操作目标仓库 Git 引用，未读取生产数据/凭据，未实际登录、部署或重启。测试命令、最终数量及审核版本以本轮交接证据为准；双审核及用户真实环境测试待进行。

审核修订（R1/R2，待双方复审）：原先把 `exit_confirmed=0` 一律视为未释放，误伤 `not_started`。现复用跟踪器状态语义：pending/running/quiescing 拒绝；历史终态还必须能核对执行域为空闲且无 owner，缺少域证据也暂停。重试使用同一判断。测试通过真实 ExecutionTracker 产生未启动失败、取消、确认退出和未知退出，不再伪造 failed 为未知退出。

分支操作保存固定基线和 failed/confirmed/unknown 结果：明确失败且分支引用不存在、HEAD 未变、工作区干净时可重新创建；已成功检出且基线一致时不重复创建。HEAD 移动、已有分支未检出、超时或缺少结果记录继续暂停。创建成功但 ready 状态保存失败，可依据已持久化的 confirmed 结果恢复；若连结果证据也未保存，则保守暂停，不能仅凭分支存在推断命令已结束。

非阻塞意见回应：D1 补充 probe/paths 仅限只读的注释；D2 明示用户请求的 GCM fill/approve 不在仓库停止门闩内，停止功能不承诺取消该凭据操作；D3 解析当前调用约定中任意数量的前置 `-c` 配置对后再判断 Git 子命令，不再固定搜索前五个参数。R3 增加持久化非零 commit 返回码检查，后续恢复也不自动推送，保留提交并交作者分析；不重做 commit 或强推。真实 post-commit hook 非零与 Git commit 返回码是否非零分别验证，不能混为一谈。

### 背景与决策理由

用户需要的是必要时完成一次浏览器登录，之后描述功能即可由工作台和三个 Agent 自动完成 Git 流程。旧路径要求用户维护 task、branch、base、审批文件和权限部署，把内部状态管理交给了用户，偏离免手填目标。登录本身也不能产生功能关联、分支基线和审核批准，因此不能只删配置或读一次凭据；这些衔接必须由工作台补齐。

### 历史实现复用依据

保留 git_automation.py 的受控参数执行、分支创建、内容核对、暂存保护、明确推送目标及结果查询能力；其一次任务一个 operation 的映射仍需适配多轮。git_workbench.py 的手工 tasks 绑定与独立 stdio 入口不再是主产品使用路径。已有模块和适配器测试结果保留于历史第 9 节，验证范围是隔离仓库，不代表当前目标环境链路可用。

### entry-2183 工作台接入决定与配置边界

未采用在消息桥里直接扩大 Git 写权限的方式。只暴露 create_branch/commit_and_push；配置和批准格式见 MCP_SETUP.md。本次不修改用户配置、不访问生产数据库、不验证真实权限；MCP 客户端实际连接待配置后验收。

## 2. 背景与目标

目标流程：**一个功能 → 文档与功能分支 → 编码 → 非作者 review 通过 → Agent commit + push 到对应功能分支。** Git 工具不检查设计文档是否存在，文档要求由功能流程承担。

首期提供建功能分支并切换，以及审核后的提交和普通功能分支 push。合入 main 是独立动作，只有用户明确提出才允许；merge_to_main 不进首期。明确排除 push main、force push、删除分支，不提供任意 shell、自动 reset、清理或丢弃改动的入口。

串行锁、worktree 和通用凭证体系留后，不作为首期必做。review 内容核对和失败结果区分保留为小检查，不恢复原完整平台。

## 3. 实现形态与权限边界

`Agent → 共用工具入口 → 一个共用 Git 模块 → Git`

模块内部通过受控参数执行 Git，不由三个 Agent 分别拼装三套逻辑；不建设独立 HTTP 服务或通用权限平台。需要 MCP 接入时可以增加薄适配。

哪个运行环境具有正常授予的 .git 写权限，就在那里运行模块。当前 Codex 会话的 .git 只读，需要配置有权限的执行入口；换脚本或工具不能绕过限制，也不能推广为所有 Agent 的权限事实。实际接入、写权限与远端认证都需验证。

任务上下文确定仓库、目录、分支与允许执行者；参数里的 agent_id 不作为授权依据。首期复用明确任务安排和 reviewer 记录，不另建通用凭证体系。远端认证沿用执行环境已有配置，日志和结果不暴露凭据。

## 4. 首期使用前提

**同一时间一个功能独占当前工作区，靠调度安排，不实现锁。** 这是使用前提，不代表现有调度器已经保证；实施接入时需落实。其他功能同时写入时停止并报告，不宣称支持并发。

建分支前确认工作区适合切换；提交前核对当前仓库、分支、基线及受检内容。用户手工 Git 或编辑改变状态时重新核对，不沿用旧结论。不自动 stash、不清空他人暂存、不覆盖改动。

## 5. 最小接口契约

| 接口 | 语义 |
|---|---|
| create_branch(task_id, name) | 从任务记录明确的基线创建并切换功能分支，返回基线、实际分支和 HEAD；名称不能是 main，重名报错不重置，工作区不适合切换时拒绝，不丢弃或藏起改动。 |
| commit_and_push(task_id, branch, files, message) | 前提为有效非作者 review 通过且拟提交内容仍一致。按显式文件清单提交，向固定已有远端的同名功能分支普通 push；结果分阶段返回 commit_id、push_status 及错误说明。 |
| merge_to_main(...)（后续独立能力） | 不进首期实现；将来仍须用户明确的合入请求与有效非作者审核，不能从普通功能任务或 Agent 转述推导许可。 |

所有接口带 task_id，通过任务上下文解析仓库、目录、分支基线及远端，不接收任意仓库路径或 push URL。files 是仓库内显式字面路径，不允许越界或 Git 元数据路径；提交信息非空，Git 参数不拼成 shell 字符串。

commit_and_push 是便利操作，不承诺本地提交与网络推送原子完成。提交已成功而 push 失败时保留并返回 commit_id，只重试推送该提交；超时、响应丢失或结果不明时先查询本地提交与远端目标，再决定下一步，不盲重试、不强推。

## 6. 五个小检查与失败处理

1. **review 绑定受检内容**：通过记录关联任务、分支、基线、非作者 reviewer、受检文件及差异；不能只有 review_passed=true，也不能由作者自填。提交前核对拟提交内容未变，变化就补 review。提交成功后确认实际提交对应受检内容，将 commit_id 写回同一记录；写回失败说明已提交事实，不再重复提交。
2. **commit 与 push 结果分开**：区分尚未提交、已提交未推送、推送成功和结果待核实。push 失败只补推原提交，非零退出或超时不自动等同“没有提交”。保留现场，不自动回滚用户文件或历史。
3. **建分支明确基线与切换**：核对任务基线和分支名称，创建并切换；重名报错，不重置同名分支，不创建 main，不在不适合切换的工作区强行执行。
4. **push 目标明确**：只用事先确定的已有远端名，显式推到同名功能分支；不依赖可能指向别处的默认上游，不推 main、不强推、不接收 URL。核对目标分支与提交结果。
5. **作者归属与暂存保护**：提交说明区分编码作者与执行提交的 Agent，代提交不改变作者或独立审核资格。已有无关暂存内容时停止，不自动清空；只提交声明且审核过的内容。同文件贡献无法分清时报告，不猜测归属。

首期沿用正常 git commit 和仓库 hooks，不默认跳过检查。hook 在提交前失败时报告并保留现场；若提交已经产生，返回该 commit 并说明后处理失败，不再创建第二次提交。专门 hooks 隔离与策略系统留后，基本结果核实不延期。

## 7. 方案取舍与扩展空间

| 方向 | 当前取舍及理由 |
|---|---|
| 原完整统一提交服务 | 收敛为共用模块及必要接入；多进程协调和通用授权超出当前单功能流程，保留五个小检查。 |
| 各 Agent 各自拼 Git 命令 | 不采用；检查容易重复，且不能解决环境权限差异。共用封装即可。 |
| HTTP 服务、通用凭证与权限平台 | 首期不建设，避免把减少手工 Git 扩成通用平台。 |
| 串行锁、独立 worktree | 留后扩展，首期依赖单功能独占工作区。 |
| 首期 main 合入 | 不实现，保持用户明确请求的独立边界。 |

扩展只留两处：

- **任务上下文解析**：接口带 task_id，目录由“任务 → 工作目录”解析；首期可以关联既有对话目录。将来 worktree 改解析结果，Agent 侧上述业务接口保持不变。
- **唯一执行入口**：Git 从共用模块同一个执行函数出去，将来串行锁包住执行函数，不让 Agent 感知锁细节。扩展时仍需验证目录、会话等集成影响，不宣称 worktree 只需加一个命令。

### entry-2170 模块实现与接入契约（2026-11-01）

- 新增 `git_automation.py`：`GitAutomation(resolve_task, reviews)` 提供两个操作和只读的 `content(task_id, files)` 辅助函数。所有 Git 进程经 `_git`，未实现 main 合入、锁、worktree 或凭证平台。任务范围首期收紧为 `feature/` 分支；符号链接、子模块和目录文件清单不支持，遇到即拒绝。
