## 2. 背景与目标（含功能定位）

- 用户报告任务交接过程中多次出现「未派发/交接中断」，涉及 `request_collaboration`、`continue_work`，曾需手动说「继续吧」。
- 计划接收与派发层负责验证 Agent 输出、保存任务及依赖、控制授权与预算，并推进协作者、owner 和 final 调用。
- 本文固化已确认断点、证据与未覆盖范围，为后续修复设计提供依据；不把定位完成写成修复完成，也不将全部中断归为同一原因。

## 3. 范围与约束

- 范围限协议校验、生命周期计划接收及服务驱动（protocol / lifecycle / drive）。
- 真实执行域释放、并发唤醒尚未验证，不属于本次已确认结论的覆盖范围。
- 不自动重试历史 job：其中任务已经执行，可能产生副作用，重试存在重复执行风险。
- 保留已有任务定义保护；本设计阶段不修改生产代码、数据库、任务状态或授权。
- 本轮仅更新本文，不扩展为调度器重构。

## 4. 选定方案与当前定位结论

- **方案状态：已决定，尚未实施、尚未验证**。选定「空计划兼容 + 只追加增量输入」，使用一套共享 owner 计划归一化规则；历史断点如下，后续规则为拟实施行为。
- **A：21 条收尾失败**。协作者任务已完成，owner 返回 `completed + plan.tasks=[]`；协议层对 owner 设置 `allow_empty=False`，报 `tasks must be a nonempty list`，导致 job 失败。这类记录不能直接称为已有任务未派发。
- **B：5 条新阶段未派发**。owner 返回只包含新任务的替换式 plan，遗漏旧任务；生命周期层以 `existing task definitions must not change` 拒绝，新任务未入库，因而未派发。
- `owner == final_responder` 不是必要条件；owner 与 final 不同的空计划对照同样失败。

### 4.1 共享 owner 计划归一化规则

- **省略 plan**：无计划更新，保留当前完整计划。
- **owner 返回 completed + 空 plan**：先检查输入结构合法、owner/final 与当前计划一致，再视为无计划更新；归一化不得吞掉身份冲突或清除已有任务。继续走现有收尾检查，未完成任务或活动调用仍阻止完成。
- **非空 plan**：解释为追加输入，遗漏旧任务表示保留而非删除。owner/final 不可变，旧任务定义、状态、结果和执行身份全部保留；同 ID 规范化后须与旧定义一致，否则拒绝，已完成任务也受保护；同次输入重复 ID 拒绝。新 ID 按输入顺序追加，旧任务顺序保持不变，完整计划输入自然兼容。
- 新任务可依赖旧任务或同次新增任务；归一化后复用现有完整依赖图与协议校验，未知依赖、自依赖、环及其他非法结构仍拒绝。全部检查成功后单事务接收完整计划并只插入新增任务；失败不部分写入计划或新增任务。
- 增量输入本身不产生授权，邀请须有明确任务依据，现有授权过滤与预算规则继续生效。entry 的 completed 携带非空任务仍拒绝，collaborator/final 的计划修改限制不变；不将其他状态的空计划自动视为完成。

### 4.2 接入位置与最小改动边界

- 共享规则供**解析层与事务接收层两处复用**，不能只在 `call()` 单独实现。`parse_entry_response` 当前先运行 `validate_plan`，依赖未重复提交旧任务的增量会提前报 `unknown dependency`；解析校验须支持当前计划上下文，或拆分输入结构校验与合并后完整校验，不能全局关闭依赖校验。
- 事务接收层基于事务内最新计划重新归一化并校验，不将解析快照作为最终写入依据。保留原始输出，明确区分原始输入与规范化结果，避免提前合并造成遗漏信息丢失或旧快照覆盖新计划；具体接口在实施时确认，两处不复制合并逻辑。
- 复用现有完整校验与事务写入，不改驱动、授权模型、预算或数据库结构，不建双模式框架，不增加自动纠错/重试；`append_plan()` 保持完整计划契约，实施时核查实际调用方。

## 5. 判断依据与决策理由

以下为 `entry-1806` 前序核查材料，数量代表当时查询样本，不代表所有中断的总数。

- **数据库证据**：对 `agent_bridge.db` 使用 `mode=ro` 查询。21 条为协作者完成后 owner 输出空计划收尾失败；样例 `entry-1538`、`entry-1570`。另 5 条为追加阶段时遗漏旧任务；样例 `entry-1526`（stage2 → stage3）、`entry-1530`（stage3 → stage4）。核对了 call 序列、owner 原始输出及错误原因。
- **代码证据**：`collaboration_protocol.py:28–29、82–83` 对应空任务列表校验及 `allow_empty` 条件；`collaboration_lifecycle.py:102–110` 对应角色和已有任务定义保护。行号为定位时位置，后续修改后应以函数和条件定位。
- **隔离证据**：前序使用临时数据库、模拟 Agent 响应完成 8 组实验；未连接真实后端或重试历史任务。

| 对照条件 | 实际结果 |
|---|---|
| owner=final，完成时携带空 plan | 任务完成，收尾失败 |
| owner≠final，完成时携带空 plan | 同样收尾失败 |
| owner=final，完成时省略 plan | 正常完成 |
| owner≠final，完成时省略 plan | 正常派发 final 并完成 |
| 单任务同身份入口返回 continue_work | 自任务正常执行并完成 |
| owner 保留旧计划并追加自任务，返回 continue_work | 两个任务均执行完成 |
| owner 保留旧计划并追加他人任务，返回 request_collaboration 并正确邀请 | 两个任务均执行完成 |
| owner 只提交新任务，遗漏旧任务 | 计划被拒，新任务未入库 |

- **第二层拒绝**：另一个临时实验仅在内存放开 `allow_empty` 后，空计划仍被生命周期层以已有任务定义不得改变拒绝。因此只改这一处条件不足以修复。
- 依据上述证据，将原先「正常派发链普遍中断」的怀疑收窄为两类已复现的计划输入与接收语义不匹配；尚无依据断言其覆盖用户所有中断。

- 解析层在 `accept()` 之前校验依赖，是不能只改生命周期接收的依据；事务接收已具备只插入新任务与计划更新的事务基础，是复用而非重建调度体系的依据。相关核查与双方回应保留在第 11 节。

## 7. 验收标准与验证方式

以下为待实施后执行的三组回归标准，不是已通过的测试结果；采用临时数据库和模拟响应覆盖解析入口至事务接收及派发路径。

1. **空计划与省略计划收尾**：owner/final 相同或不同均能按现有角色流程完成；合法空计划不删除任务历史；角色冲突仍拒绝，存在未完成工作或活动调用仍阻止完成。
2. **合法追加与兼容性**：增量追加自任务或他人任务能够依赖旧任务并正常派发，新增任务只执行一次；完整计划仍兼容，旧定义、状态及结果保留。解析和事务接收共享规则，事务内按最新计划复核，授权与预算约束继续有效。
3. **非法追加与原子性**：篡改旧任务（含已完成任务）、重复 ID、未知依赖、自依赖或环均拒绝，计划及新增任务不部分入库；entry/collaborator/final 原有角色限制不被放宽。

## 11. 最小改动复核提案（entry-1839，待讨论）

- 记录时间：2026-10-28 19:07:49 +08:00。Codex 独立审核提案，待 DeepSeek 逐点回应；不覆盖前序讨论决定，不代表用户授权实施。当前文件仍是定位草案，前序「方案已收敛」的写回任务尚未体现在本文中。
- **判断**：空计划兼容与只追加增量输入能针对两类已确认失败，不只是改善输出体验；但尚不能证明绝对最优。保留该方向，收窄实现为一个明确的 owner 计划归一化规则，避免同时建设两套合并流程或通用可切换校验框架。

| 比较方案 | 对收尾空计划的覆盖 | 对只提交新任务的覆盖 | 代价与限制 |
|---|---|---|---|
| 只改提示，继续严格完整计划 | 仍拒绝原空计划输入 | 仍拒绝原增量输入 | 改动最少，但仅降低违规概率，不能作为两类故障的可靠修复 |
| 兼容空计划，完整计划契约加提示/错误反馈 | 可覆盖结构及身份合法的空计划 | 仍拒绝遗漏旧任务的输入 | 接收语义改动较少，但 B 类故障保留；反馈不能自行推进已经 failed 的 job |
| 兼容空计划，只追加增量输入且兼容完整计划 | 可覆盖 | 可覆盖通过身份、定义、依赖及邀请检查的输入 | 需要在解析与事务接收两处正确使用当前计划，但可复用现有完整计划验证和入库流程 |

- **建议收窄**：仅 owner 计划输入使用共享的纯函数归一化规则；省略 plan 不更新，completed 空 plan 先验证结构与身份再视为无更新，非空输入保留旧任务并追加新 ID。重复携带旧 ID 必须与规范化后的旧定义一致，输入内重复 ID 仍拒绝。归一化后复用完整依赖图与协议校验；事务内基于最新计划重做归一化与校验，成功后沿用只插入新任务的事务写入。原始输出保留，不把解析时的快照当最终写入依据。
- 这不是新增计划模式、协议字段、数据库表、重试/纠错循环或调度器重构。解析接口可只增加可选当前计划上下文，非 owner/无上下文调用保持严格；具体函数位置和接口仍待实施阶段确认。邀请也须有明确任务依据，增量本身不增加授权。
- **依据**：`CollaborationService.call` 先经 `parse_entry_response` → `loads_payload` → `validate_payload` → `validate_plan` 再调用 `LifecycleStore.accept`；依赖旧任务的增量会在解析时被拒。因此仅修改 accept 不够。accept 已在同一事务中检查旧定义、插入新增任务并更新计划，可复用；`append_plan` 另有完整计划契约，不能无依据扩为全局增量接口。
- **最强反对理由**：扩展输入契约会增加上下文传递与一致性测试成本；只修 A、继续要求完整计划更便宜。回应：如果目标包含修复已确认的 B 类中断，提示和可读错误仍会拒绝同类输入，除非用户明确同意将 B 降为暂缓项；否则以少改代码为由保留该故障不满足目标。尚无量化数据证明增量可降低多少真实失败率。
