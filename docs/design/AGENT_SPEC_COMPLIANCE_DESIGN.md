## 1. 背景与目标

本需求起于对规范与工作流程接入可靠性的担忧：已有入口与文档，不代表所有执行路径都会发现、正确理解并应用适用内容。长期目标覆盖后续新增的规范与工作流程，当前讨论规范是第一个验证场景。

| 层次 | 内容 |
|---|---|
| 长期目标 | 让 Agent 在执行任务前及任务场景变化时，自动发现、判断并应用相关规范（spec）与工作流程（skill），在执行过程中遵守约束，并提供可检查的执行结果。 |
| 当前做法 | 先做通用入口「发现 → 判断 → 加载」，以 [agent-discussion-spec v1.0.0](../../specs/AGENT_DISCUSSION_SPEC.md) 为第一个验证场景打通；任务场景变化时重新判断适用内容，不一次铺开所有场景。 |
| 保障手段 | 当前聚焦「拦 + 查」；它们服务于长期目标，是保障手段，不是目标本身。 |

本文中，**spec** 表示适用时必须遵守的约束；**skill** 表示固定工作流程，是否强制使用依其适用条件与相关要求判断。两者在「发现 → 判断 → 加载」层采用通用思路，加载后的约束与流程执行方式仍需分别设计和验证；加载完成不等于已经遵从。

用户已同意先讨论「拦 + 查」，并将前期讨论、后续技术选型、实施及调试结果集中保存在本文，作为项目可持续查阅的记忆。

- **拦**：针对可机械判定的规则，在执行或状态转移前进行检查，阻止违反已编码条件的操作。
- **查**：检查讨论内容、协议行为与结果，保留证据和异议；语义审核可能误判，留痕本身不阻断错误。
- **当前范围**：围绕通用入口与首个验证场景讨论设计，聚焦「拦 + 查」的保障方式；本次仅更新目标与范围，尚未确定具体技术方案或开始生产代码实施。
- **当前不纳入**：通用入口所需内容之外的「劝」的额外优化，以及 SFT、DPO、RFT 等训练工作；既有规则指导仍是基础，不因此移除。

范围边界：字段结构、`depends_on`、末行邀请格式和部分角色边界来自协作协议，并非全部属于规范正文；后续须逐项标清规则来源。规范 v1.1.0 §10（原 v1.0.0 §9）当前明确不新增 `discussing` 状态，讨论状态检查不等于已决定修改状态机。

## 2. 前期讨论

### 2.1 调研与理解框架

Codex 与 DeepSeek 分别调研后，汇总为 [43 个措施条目](../drafts/AGENT_SPEC_COMPLIANCE_RESEARCH.md)。它们包含产品机制、应用设计、社区实现和研究方法，部分可组合或重叠，不是 43 套互斥的完整方案。

| 环节 | 解决的问题 |
|---|---|
| 规范送达 | 让 Agent 收到规范入口和内容 |
| 适用性判断 | 挑出当前任务需要遵守的条款 |
| 执行约束 | 阻止违反已编码规则的操作 |
| 结果检查 | 检查行为和结果，保留审核依据 |
| 持续改进 | 根据反馈维护规则、记忆或训练行为 |

讨论以「劝、拦、查」帮助理解：规则提示提供指导，执行检查提供阻断，审核与记录帮助发现和追溯问题。此类比不代表任一类能够完整保障遵从，也不表示改进必然有效。

### 2.2 三档适用性筛选

| 档位 | 措施与筛选理由 |
|---|---|
| A：直接适合（六类） | 规则提示／项目指令文件：提供规则基础；结构化输出与程序校验：检查格式及字段；工作流／调度关卡：检查权限、依赖和预算；独立审核：检查理由、证据及异议；回归测试：检查已覆盖规则是否被改坏；审计记录：保留异议与观点变更。 |
| B：辅助可选 | 示例、Skills、计划清单、角色分工、Hooks、网关、用户裁决、模型评分及上下文管理等；价值取决于适用条件和接入方式，尚未选定。 |
| C：当前暂不用 | 训练类、代码执行沙箱、PII 扫描及大型规范检索等；有的与当前讨论规范关联较弱，有的尚无投入依据，不代表永远无用。 |

上述筛选只说明适用性，不代表这些能力尚未实现或已决定全部建设；现有代码覆盖情况和具体缺口尚待核查。

### 2.3 先讨论「拦 + 查」的四条理由及保留边界

1. **已有「劝」的基础，但送达不等于遵守。** 前期曾表述为「劝已做且证明不够」；准确边界是已有 AGENTS.md 与规范索引，但所有入口的送达和遵从情况尚未验证，不能据此认定提示优化收益很低。
2. **「拦」适合可机械判定的规则。** 字段、权限、依赖、预算等可以形成明确检查；P0-2 期间出现过派发和记账异常，说明此类错误值得关注，但不能未经根因核查就认定增加校验能修复这些历史问题。确定性只限于正确实现、完整接入的规则，成本与收益尚未评估。
3. **「查」补充内容质量检查。** 理由是否充分、证据是否可靠、是否回应异议，需要独立审核和记录辅助判断；不能保证识别「假装同意」或所有语义错误。
4. **训练暂不纳入。** 目前没有数据、训练权限和效果评估依据支撑投入，先保留为其他方向，不预设以后一定需要训练。

用户已确认聚焦「拦 + 查」的讨论方向；「最低成本、最高确定性」「所有硬规则都能卡死」等前期说法不作为已验证结论。后续每次决定仍须返回顶部三问，防止将当前手段替代原始目标。

## 3. 技术选型

「查」的落地方式为负责人交付审核（见 [agent-discussion-spec v1.1.0 §6](../../specs/AGENT_DISCUSSION_SPEC.md)）：实际核对五项、留下依据并在已有授权内纠正；owner 负责审核，final_responder 据已审核材料汇总披露。复用现有输出，不新增角色、协议字段或审核系统；新增程序「拦」按具体风险与成本单独决定，不预设候选项实施顺序。核对与纠正有实际成本，效果仍待验证。

### 3.1 候选规则（备选，待定）

- **规则内容**：讨论过程中，除非用户明确要求调整文档，否则任何角色（尤其 final）不得对文档进行写操作。
- **实现思路（待验证）**：采用「约束 + 拦」，在工具调用前检查当前角色、动作是否为写文档、用户是否明确要求相应调整；属于受限写操作且不满足授权条件时拒绝。仅把规则写入提示不等于执行前阻断。
- **提出动机**：作为「补 DSH final 只读沙箱」的替代思路，期望支持默认只读、用户明确要求时按授权范围调整文档，并复用通用「拦」机制；是否更灵活、能否替代沙箱仍需验证。
- **状态与关联**：备选，与「角色执行前约束」（缺口 1）合并考虑，未决定纳入首期，尚非正式规范或实施决定，不改变现有角色权限与沙箱限制。
- **待确认边界**：用户明确要求如何形成可检查的授权、如何覆盖直接编辑及通过命令等间接写入、如何与 final 当前仅汇总的职责衔接，均待讨论；不能仅凭角色或模型自报授权认定可写，也不据此认定 DSH 外部权限配置已无写入限制。

### 3.2 候选方案：编号+各Agent独立判断+差异复核+按需加载

**状态：候选，待定。** 当前主线回到「发现 → 判断 → 加载」；第 3.1 节保留为后续保障手段的备选素材。本节记录讨论与机制分析，不是定稿、实施授权或效果实测。

#### 方案描述

1. **编号与索引**：为规范建立稳定编号，例如 `001`，可采用 `001-xxx.md` 命名，并与现有 `id`、`version` 建立对应；编号不随排序改变、不复用。本次不重命名文件。工作流程（skill）同样需可发现、可定位，具体编号方式待定。
2. **各自判断**：每个 Agent 在当前任务首次发言、执行任务前，读取同一版索引，根据自己的任务范围独立记录「适用／不适用／待确认 + 理由」。首次判断不意味着整个会话只判断一次；任务场景或相关文档版本变化时应复核。空清单不能兼作「尚未判断」的标识。
3. **按需读正文**：根据编号读取适用文档的对应版本正文；必要时先读正文澄清适用条件。需要区分适用清单、实际加载记录和执行结果，不能仅凭自报「读过」认定加载或遵从。
4. **差异是复核提示**：对比同一任务上下文中其他 Agent 的清单，发现不同编号时，读取相应适用条件与正文后，自主决定补充、更正或维持原判断，并简要记录理由。不自动合并列表、不要求列表一致、不因差异本身升级用户裁决；仅在影响共同任务的真实冲突经查证仍无法解决时，按既有规范处理。比较对象不能简单等同于最近发言者。
5. **后台分工**：负责传递清单、提供文档和保存判断／加载／修正记录；这些是候选设计职责，并非现有实现。后台预判仅为可选建议，不视为确定正确，也不替代各 Agent 的语义判断。不使用后台预判，不等于只能靠自觉：是否完成判断、编号是否有效、所需正文是否已提供，仍可由程序检查；具体执行前衔接待设计。
6. **修正与反馈**：保留原判断及修正理由、证据和影响范围。单次任务清单可以更新；留存理由作为人工或受控修订公共规则的依据，不让一次 Agent 意见自动修改公共规则，也不预设自动学习、定期审核或后台规则更新机制已获采用。

#### 与本项目的适用性

| 契合点 | 依据与边界 |
|---|---|
| 编号与结构化清单 | 可关联现有 id + version，便于引用和检查；仍需定义清单状态、任务归属和传递方式，不能直接认定实现轻量。 |
| 各 Agent 独立判断 | 与 AGENTS.md 的按场景判定、协作者提出遗漏及场景变化重判方向一致；现有索引主要要求负责人判定传递，本候选将独立判断明确扩展到每个参与者，并非规范已逐字要求相同机制。 |
| 差异复核 | 与讨论规范 §3 的理由明确、允许反驳和不假装同意一致；不同职责可以合理使用不同清单。 |
| 按需读正文 | 与索引要求只读 must_follow 正文的流程一致，可避免默认加载全部文档；漏选、读取失败和上下文保留仍需处理。 |

需权衡三点：①各 Agent 重复读索引、判断和读正文会消耗上下文、时间，若拆分调用还会增加调用预算；实际成本未测。②独立判断不等于错误独立，所有人可能共同漏判；差异复核无法提示所有人都未选中的条目。③后台预判可选，加入后需维护条件和规则，也可能造成共同锚定；是否增加收益尚无证据，不应默认作为正确性兜底。

#### 与其他候选思路对比

下表比较机制差异，不给未经测量的高／中／低评分。三者可以组合，不是严格互斥的三选一；「后台预判」指代码根据已定义条件提出清单建议，「全量注入」指发送既定范围内全部正文。

| 维度 | 各自判断 + 差异复核（本候选） | 后台预判方案 | 全量注入方案 |

## 5. 验收标准

### 负责人交付审核五项检查

依据规范 v1.1.0 §6，负责人（owner）实际核对以下五项，各一行记录「检查项：结论；依据或证据位置；有问题时的处理」：

1. 目标是否偏移了原始目标？
2. 是否扩大范围或增加不必要的复杂度？
3. 目标是否完成？
4. 结论是否有证据？
5. 缺口是否披露？

- **结论与留痕**：使用「符合 / 有问题 / 未验证 / 不适用」，不适用说明理由；复用可读正文或现有 `handoff` 保留一份，正常项简写、异常项说明处理。填写完成不等于审核完成，结论须对应实际材料。
- **时机**：前两项在规划、准备扩展任务或机制、需求或方案变化时复核，与顶部决策三问衔接；执行中发现任何一项问题立即处理，交付前完整核对五项。
- **范围与复杂度**：说明新增项解决什么必要问题、为何简单方案不够及是否在授权内；必要的深入与保障应保留，不为轻量而漏做必要工作。
- **纠正与披露**：先在已有授权内补做遗漏、核验证据、纠正结论、按需重新验证，或删减计划、暂停偏离部分、简化方案；不擅自删除已有成果。无法解决或需用户取舍时披露障碍、剩余缺口或请求决定，执行中及时说明影响。不能以「目标未完成但已披露」认定审核通过。
- **职责与边界**：owner 审核与纠正，final_responder 依据已审核材料汇总披露。这里只落实检查与纠正；程序拦截依据后果、发生或复现证据、恢复难度、覆盖范围和实现成本另行决定，不要求等待真实事故，也不预排四个候选缺口。
