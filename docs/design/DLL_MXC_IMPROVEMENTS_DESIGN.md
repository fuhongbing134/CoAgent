## 1. 摘要、目标与非目标

本设计针对 REQ-003 的 6 项「验证／诊断／错误分类」改进给出实现方案。共同目标：让每条结论绑定到实际运行的对象、环境和阶段，取不到时显式标未知/未测；不改变权限、锁、Job、探测的现有语义与拒绝行为。

**非目标**：新增 Agent 沙箱探测接口、改变锁/Job/权限语义、改变生产接口契约、做性能或容量优化、对全部后端与操作系统穷举。

## 2. 背景、问题与范围

本机工作台 Windows 启动链故障经切换沙箱后端到 MXC 修复，复盘留下 6 项改进（见 REQ-003 §3）。范围限定为：诊断字段补齐与结构化（事项 1）、错误按阶段分类（事项 2）、单测入口前提与阶段定位（事项 3）、Grok 文件工具子进程身份与原生失败呈现（事项 4）、双进程 Job 归属验证（事项 5）、宿主与 Agent 能力边界表达（事项 6）。

## 5. 方案总览与依赖方向

六项相对独立，均落在「记录/分类/验收/表达」层，不改生产语义。共享两条表达约定贯穿全篇：

- **错误分类**：原生加载失败／锁竞争（`ERROR_LOCK_VIOLATION`）／其他系统错误。
- **能力边界**：宿主结果／工具或 Agent 子进程结果／未测。

依赖方向：事项 1、3、5 共用「实际 CLI/解释器身份」术语；事项 2、4、6 共用「原生加载失败」术语；事项 4、6 共用「宿主 vs 子进程」表达。

## 6. 详细设计

### 事项 1（高）Codex CLI 身份与观测后端

- **选定方案**：扩展 `diagnostic_metadata`，权限字段拆为 `permission_mode`（`read-only`／`default`，命名配置路径如 `-c default_permissions="step1-git"` 记 `default`，默认 `--sandbox CODEX_SANDBOX` 记 `default`）与 `permission_profile`（配置名，如 `step1-git`）；`step1-git` 只作配置名，不写入模式。复用快照 `executable` 记 CLI 路径；`cli_version` 用 `codex --version` 一次性获取，缓存键绑定本次解析出的可执行文件（路径变化则缓存失效）；新增 `observed_backend` 与 `backend_evidence_source`。
- **证据与降级**：本诊断须关联本次运行快照；观测后端仅接受独立证据来源（如 CLI 日志的 `Windows sandbox selection: mxc`）；证据缺失或与请求冲突时降为 `unknown`。
- **验证方式**：正例——有证据能辨认后端时输出对应后端；反例——仅有请求配置、无观测证据时输出 `unknown`；新建/续接/只读汇总各跑一次；显式 CLI 覆盖验证记录与实际一致；新增字段不破坏既有 consumer。

### 事项 2（高）迁移屏障错误分类

- **选定方案**：按失败阶段拆三段：`import ctypes` 与 `WinDLL('kernel32')` 失败 → 原生加载失败（同类两个注入点分别验收）；`LockFileEx` 返回 FALSE 且 `ERROR_LOCK_VIOLATION` → 锁竞争（仅此类提示等待重试）；其余 `WinError`/异常 → 其他系统错误。三类均拒绝进入临界区、保留 `from error` 链、清理已打开 `fd`/`file`。
- **验证方式**：分别注入 `ctypes` 导入失败、`WinDLL` 加载失败、真实锁竞争、非竞争系统错误；正常获锁与 POSIX 回归；D1 前核对调用方对异常类型/文本的依赖（仓内仅 `migration_barrier.py:43` 字面匹配）。

### 事项 3（高）MXC 单测入口前提

- **选定方案**：入口输出关联外层/内层解释器、本次选中 CLI（含版本）、请求配置、发现数、跳过原因、退出码；回环可用性以同一 MXC 执行上下文证据判定。
- **诊断时序**：以可观察量分阶段判定，五个阶段各自报告失败、不跨阶段归因——①CLI 无效（解析/启动失败）、②MXC 未启动（后端选择/启动证据缺失）、③内层无法启动（受控子程序运行标记缺失）、④回环不满足（同一上下文内的回环探测失败，入口返回非零并保留实际退出信息）、⑤普通测试失败（已启动后的用例失败）。
- **验证方式**：基础 Python 启动外层 + 项目解释器跑内层；五个阶段分别可定位；回环不满足时报告完整套件未通过并保留已执行用例与退出信息；显式 CLI 覆盖一致。

### 事项 4（中）Grok 文件工具子进程身份与原生依赖

- **选定方案（P1）**：两类异常走既有通道——`tools/call` 内 `OSError` 等已捕获异常走现有 `isError`；`ImportError`（`workspace_files_windows.py:4` 模块级 `import ctypes`）不捕获、表现为子进程退出，由**可观察该退出的边界（Grok 客户端或工作台上层）**按退出/错误特征分类到原生加载阶段，不在 `tools/call` 内额外捕获。诊断记录本次 MCP 子进程实际解释器身份，供观察方关联。
- **验证方式**：真实 MCP 有界文件操作 + 独立核对文件结果 + 该次子进程解释器身份；注入原生加载失败后调用侧定位原生加载阶段且文件不变；路径拒绝保持独立含义；缺身份/证据标未知/未测；注册事件只覆盖注册阶段。

### 事项 5（中）双进程 Job 归属、取消、退出

- **选定方案**：以各组入口实际证据为验收单位；复用 `tests/unit/test_managed_process.py`（已有 `test_breakaway_cannot_escape_managed_job` 双 PID 验证）为主，`verify_task6_breakaway.py` 保留独立 breakaway 实验语义。基础 Python 与 `.venv` 分别记录实际启动器与脚本解释器；取消前取得各 PID 的进程身份与句柄；对每个 PID 查 `IsProcessInJob(handle, owner.job_handle)`；取消后用已确认句柄验退出并核 Job 清空。
- **边界**：系统直接拒绝只走拒绝分支；身份取不到单列证据不足；「离开内层启动器 Job」不得写成「离开 CoAgent Job」（嵌套 Job）。
- **验证方式**：两组入口各跑一次，断言 Job 归属、取消退出与 Job 清空；同 PID 时给出身份依据，双 PID 时取消后两句柄均退出；`outcome=cancelled`、`exit_evidence=confirmed`（取不到身份则单列证据不足）；系统直接拒绝只走拒绝分支。

### 事项 6（中）宿主与 Agent 能力边界

- **选定方案**：在 HTTPS 探测内隔离依赖失败——把 `ssl` 延迟到 HTTPS 探测项，使文件/Git 等宿主项在 `ssl` 失败时仍按实际结果呈现。能力快照增加 Agent 沙箱字段固定为未测，禁止回填宿主结果；宿主 `ssl` 失败报可区分的原生依赖失败；`ctypes` 仅在确认本入口确有对应依赖和验收需要时纳入。
- **兼容**：`environment="workbench"` 保留；新增 Agent 字段显式未测；`cli_found` 不升级为沙箱能力。
- **验证方式**：正常宿主探测标 `workbench`、Agent 未测；注入 `ssl` 失败从真实调用入口定位宿主原生失败阶段，受影响 HTTPS 探测据实报告、其余探测按实际结果；两端文案可区分。

## 8. 失败处理与收尾

诊断记录失败不阻塞主路径；错误分类失败仍拒绝进入临界区并清理 `fd`/`file`；测试入口失败保留阶段定位与真实退出码；文件工具原生失败（P1）进程退出且文件不变；进程身份取不到标未知不臆造。清理仅针对自有进程，不扫描同名进程。

## 11. 验证、验收与完成定义

- **设计完成**：6 项均有候选/选定方案、理由、依据、异议与取舍、验证方式；两方检视达成一致。
- **实施完成**：代码落地记「已实现」，绑定实际版本与配置；必要场景缺证据记「待环境验收」；通过相应验收的实测才记「已验证」。`unknown`/未测仅为诊断值，不用于判定实施或验收完成。
- 完成口径分列三档，不得混用：**已实现**（代码落地）/ **已验证**（通过相应验收的实测证据）/ **待环境验收**（真实 MCP、双入口 Job 等必要场景缺证据时标此档）。
- 动态验收在实施后完成，包含真实 MCP、两组入口 Job 实测和故障注入。

按第 7 节和本节的原定判据，六项主要验收已完成。工作树版本、实际后端与未单独实测的范围见[收尾结论与复验边界](../verification/DLL_MXC_IMPROVEMENTS_VERIFICATION.md#11-收尾结论与复验边界)。
