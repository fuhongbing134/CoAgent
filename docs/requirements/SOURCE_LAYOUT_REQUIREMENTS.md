## 1. 背景与目的

用户要求将测试代码与源码放在不同目录，源码按功能分级，并拆分 `web_chat.py` 集中的职责。用户要求沿用 [REQ-001 1.1](CONCURRENCY_LOAD_TEST_REQUIREMENTS.md) 的分析格式，协作达成一致后正式归档。entry-3689 补充了协作约束，每次只邀请一位 Agent。

基线跟踪的 64 个 Python 或 JavaScript 文件中，55 个在根目录，其中 27 个文件名符合 `test_*`、`verify_*` 或 `smoke_test.py`。文件名统计反映目录混放，文件实际职责需按使用关系确认。[架构记录](../architecture/ARCHITECTURE.md#L17) 已指出宿主职责集中。

## 2. 可行性与接纳结论

**建议接纳三项目标。** 协作、执行和持久化已有部分独立模块，现有文档及测试提供了可核对的迁移基线。可行性判断来自静态分析，运行和迁移验收尚未执行。

用户在 entry-3689 回复「按建议」确认本次重组的兼容政策。现有 Web 启动命令（含 `--port`）和 MCP 配置中的 `agent_bridge.py` 路径须继续可用。默认数据库与默认工作目录须继续按重组前的规则解析。允许随测试迁移调整文档中的测试模块路径，届时须同步更新 README 和 MCP 说明并验证新命令。

| R3 维护者单独修改宿主中的某项职责 | 提交拆分前后的职责对应关系，核对数据库连接及初始化、协作与消息终态、执行与取消、提示组装、后端 CLI、worker、HTTP 与页面各自的归属。至少能沿功能路径找到独立实现。验证既有命令、HTTP、会话、取消和事务语义。 |
| 兼容验收：用户按既有说明启动并使用工作台 | 实际验证现有 Web 启动、`--port`、MCP 客户端连接、默认数据库与工作目录解析、`GET /` 页面及受影响的既有 API。按相同输入与配置对照迁移前后的代表性请求、状态及结果。 |

## 4. 价值性

维护者能按功能定位实现，查明一个改动涉及哪些职责和测试。使用者能继续按已经验证的说明启动、连接 MCP 并访问原有数据。回归结果与公开入口的实测结合，可发现测试全部通过但使用说明或配置已失效的情况。
