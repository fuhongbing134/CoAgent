# issue #8 修复方案（已定稿）

> 记录 issue #8（协作调度：漏执行 / 提前完成 / 追加任务被 blocked）的修复方案、审核过程与最终定稿规则，作为后续最小实施的依据。本文不修改代码。修复已完成并通过验证（自动化 60 项 59 通过 1 真实 CLI 跳过 + 真实 CLI 场景 A–E 覆盖）。

## 一、问题定义（两条路径）

1. **入口误判完成**：`seed()` 只凭「`completed` + 单任务 + 同身份」就把任务标为完成，无法区分「已经执行」和「只是列出计划」——会**漏执行**。
2. **负责人追加任务后受阻**：`call()` 先保存新增计划，`accept()` 再发现 pending 任务，将 job 置为 `blocked`——负责人回复 `completed`，实际却还有未执行工作，**卡住流程**。

## 二、修复目标

让「设计 → 审核 → 回应 → 记录 → 实施」的协作流程完整，且不重跑、不漏跑、不无限循环。最小修复，不展开整套协作规范重构。

## 三、最终协议规则

**协作入口只规划，任务统一交给调度器执行。** 普通非协作聊天不受此规则影响。

新增状态 **`continue_work`**，表示「本次规划/协调已完成，整个 job 还要继续」。

| 角色 | `completed` 的含义 | 有后续工作时 |
|---|---|---|
| entry | 不再用于提交待执行计划 | 返回 `continue_work`；需要其他 Agent 时用 `request_collaboration` |
| collaborator | 当前分配任务完成 | 不追加计划，由负责人决定后续 |
| owner | 请求完成整个 job | 有剩余任务时返回 `continue_work` 或 `request_collaboration` |
| final | 完成最终交付 | 不追加任务、不再执行工作 |

- `waiting_user`、`blocked`、显式提前交付继续保留。
- **自任务不需要末行邀请**：调度器可执行负责人自己的就绪任务；其他 Agent 仍须显式邀请，不能扩大授权。
- **collaborator / final 不允许用 `continue_work` 追加流程。**

## 四、具体修改清单

1. **统一入口契约**（`collaboration_entry.py`）
   - 删除「单任务可直接完成工作并附计划」。
   - 明确入口只规划，不执行计划中的修改或命令。
   - 默认示例改用 `continue_work`。
   - 入口创建的任务统一为 pending，不根据 Agent 身份推断完成。
   - 移除 `seed()` 的自动完成捷径。
   - 旧式入口 `completed + 非空任务` 回复：报协议不兼容，保留原始回复，**不自动重跑**（旧回复可能已执行过，程序无法可靠判断）。合法纯问答允许 `completed + 空 tasks`，直接结束、不创建 job。

2. **追加计划与状态接受原子化**（`collaboration_service.py`、`collaboration_lifecycle.py`）
   - 同一事务内完成：校验调用仍有效/用户材料版本未变化 → 校验新增计划及邀请 → 保存新增任务和授权 → 保存调用结果 → 更新 job 状态。
   - 任一步失败整次回滚，避免「计划已追加、结果被拒」的半完成态。
   - 保留旧任务、角色不可变、新增 `task_id` 不重复的限制；重复接受同一调用不重复插入任务。

3. **按数据库真实状态决定完成**
   - `continue_work`：有可推进工作则保持 working，让 `drive()` 继续。
   - `request_collaboration`：校验邀请与授权。
   - `completed`：校验无未完成待办、无活动调用后才算完成。

4. **drive 无进展保护**
   - 初版**不引入可调 N 轮**。
   - 没有可运行或正在执行的任务时，最多允许负责人**一次补充决策**；仍不能形成可推进工作就 `blocked`。
   - 单纯回复、消耗轮次、改写说明文字**不算进展**。

## 五、审核过程与定稿要点

### DeepSeek 审核（A–D + 同步）
- A：`continue_work` 与 `request_collaboration` 精确分工（自任务 / 邀请）。
- B：`continue_work` 无可执行任务 → `blocked`。
- C：无进展保护阈值需明确。
- D：旧式 `completed` 拒绝需用户可读提示。
- 同步入口校验器允许 `continue_work` 状态。

### Codex 回应（最终口径）
- **A（部分同意）**：一个计划可同时包含自任务和他人任务，**不强制二选一**；有效邀请不阻止就绪自任务执行。
- **B（部分同意）**：区分「暂时没有 ready 任务」和「无法推进」。依赖任务正在执行时应等待；依赖失败、缺少授权且无其他推进路径时，才明确受阻（`blocked`）。
- **C（同意，简化）**：见上文「一次补充决策」上限，不引入可调 N。
- **D（同意）**：保留原始回复，明确说明「入口现在只规划，此回复未被自动执行或重跑」；**不提示用户直接重试**，以免旧调用实际已改文件而重复执行。
- **同步校验器（同意）**：状态集合、角色限制、入口示例及协作提示词一起更新。

## 六、实施范围与注意

- 不修改 P0-2 并发方案。
- 不自动恢复或重跑历史 blocked / completed job。
- 协议状态有新增，提示词、解析器及相关客户端必须同步更新；不兼容的活动 job 不跨版本续跑。
- 保留原始回复和明确错误原因，避免用户只看到「未完成任务」而不知道如何处理。
- 用户显式提前交付、预算收尾走专门路径，不被普通完成规则误伤。
- **`continue_work` 已实现**，并已通过回归验证；入口纯问答使用 `completed + 空 tasks` 直接结束。

## 七、首个回归用例（建议）

「owner 追加自任务 → 返回 `continue_work` → drive 执行自任务 → 完成后 `completed` 收尾」这条路径（即 entry-807 的复现场景）作为最小修复后的首个回归用例。

## 八、后续修复（在核心修复之上）

- **纯问答直接终结**：合法入口 `completed + 空 tasks` 直接结束、不创建执行 job；协议结果与消息完成状态同事务保存；`continue_work`/`request_collaboration` 仍须非空计划；旧式 `completed + 非空任务` 继续拒绝。
- **入口持久化与取消保护**：入口消息暂存复用合法 `pending` 状态，并以 `entry_reply_received` 标志单独确认调用成功；协议校验与落库成功后再置 `completed`（修复了 `status='running'` 违反 CHECK 约束的回归，详见 ISSUE_CHECK_CONSTRAINT_REGRESSION.md）。
- **澄清终结分支**：澄清后直接答复通过保留标识 `__clarify_entry__` + 来源核验 + 调用记录联合识别，事务原子完成占位任务并置 `completed`/`final_ready`；`drive()` 优先处理 `final_ready`，仅 pending 且来源核验通过的占位才触发 `replan()`。
- **验证证据**：自动化回归 60 项 59 通过 1 真实 CLI 跳过（OK）；真实 CLI 场景 A–E 覆盖（E-2 取消的任务卡状态/进程退出待单独核对）。
