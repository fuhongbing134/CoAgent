## 一、执行摘要

- **原始问题**（用户最终定义）：同一 agent 在执行任务 A 尚未完成时，用户再次派任务 B，导致两个执行并发写同一个后端 session（writer conflict）。
- **最终修复程度**：
  - ✅ **核心「防并发写坏」已闭环**：执行域状态机 + `begin_run` 拒绝非 idle + 6A 的 R1（孤立 run）/R2（残留 owner）/R3（共享 session）加固 + 任务 A 的友好「正在忙」提示。
  - ❌ **sub-agent 并发多任务未做**（backlog B，待评估）。
  - ❌ **崩溃遗留占用的解除/恢复未做**（6B，暂缓）。
- **一句话结论**：P0-2 的「防止两个任务写坏同一 session」这条安全主线已闭环（自动化 17 验收 + 51 回归全绿 + 真实启动正常）；但「并发多任务」与「崩溃恢复」两条支线仍未完成，且代码审计发现 12 项未触发的潜在问题需后续关注。

## 三、走的弯路与低效环节

1. **任务 6 方案反复推翻（最大代价）**
   - 当时想法：初始方案 T1-T6 假设「命名 Job + 持久化 created 记录 + `OpenJobObjectW error==2` = 进程树已终止」，可直接作为释放证据。
   - 为何错：该假设依赖「Job 配置不可变」「无 breakaway」两个未验证前提；同用户受管进程实测可清除 `KILL_ON_JOB_CLOSE`、可开启 breakaway，两者都导致「名称无法重新打开但进程仍存活」→ 误放行。
   - 代价：跨三轮验证（机制验证 / 补充验证 / 针对性验证）、两次观点反转（Codex 两次撤回「进程存活时 Job 不销毁」断言），最终整个「跨崩溃自动恢复」机制被否，降级为方案 A（人工解除）。

2. **验证结论被反复修正**
   - 当时想法：`verify_job_recovery.py exit_code=0` 时一度写「闭环成立」。
   - 为何错：该实验控制器预持全部节点句柄，属受控实验，不等于生产「无预持句柄」的恢复路径。
   - 代价：先写「闭环成立」→ 被复核降级「受控实验成立」→ 再被补充/针对性验证否定，多轮口径反复。

3. **6A 设计分多轮补缺口**
   - 当时想法：6A 首轮设计 D1-D6 后即认为可定稿。
   - 为何错：首轮复审未覆盖「孤立 run / 残留 owner / 跨域共享 session / 拒绝后收尾」等异常路径。
   - 代价：Codex 复审补 R1-R3 两轮讨论，随后又补 F1-F4，定稿被反复打断。

4. **协作调度派发异常（元 bug）**
   - 现象：owner==final_responder 的 `continue_work` / `request_collaboration` 多次未被调度器派发，靠用户「继续吧」手动重触发；另有 owner 最终交付被记账 `failed` 的偏差。
   - 代价：多轮协作靠用户手动推动，效率受损；根因（`collaboration_service.py` 的 drive / 终端邀请处理）**仍未核实**。

5. **交付描述不精确**
   - 现象：任务 A 的「正在忙」文案被描述为「覆盖原始场景」，但 Codex 审计发现网页/HTTP 接口已有前置拦截，普通网页提交时用户可能根本看不到新文案（见 P1）。
   - 教训：交付描述要精确到「覆盖哪些入口、哪些没覆盖」。

## 五、教训提炼（可执行）

1. **先证伪关键假设再设计**——任务 6 的「Job 语义 / 配置不可变」若早期做对抗性实验，能省三轮反复。
2. **受控实验正向通过 ≠ 生产成立**——验证结论必须同时写明「验证了什么、没验证什么」。
3. **威胁模型先行**——任务 6 反复折腾的根源是「防意外并发」vs「防恶意同用户篡改」边界没先定死。
4. **设计审查主动构造反例**——孤立 run、残留 owner、跨域共享、拒绝后收尾，应首轮审全，不等到实现后才发现。
5. **设计验收覆盖完整生命周期**——不只审主路径（准入），要审「拒绝 → 收尾 → 失败」全链。
6. **交付描述精确到入口**——写「覆盖了哪些入口、哪些没覆盖」，不写「已覆盖原始场景」这种模糊话。
7. **协作调度元 bug 优先修**——owner==final_responder 的派发异常反复打断协作，属于「元工具」问题，应先于业务功能修复。
