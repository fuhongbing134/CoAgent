## 1. 目的与范围

- 约束方案讨论与设计决策的产物留痕，确保后续能够回溯背景、为何如此设计以及变更原因。
- `agent-discussion-spec` 管讨论过程；本规范管讨论产物的落盘与后续维护，适用于单 Agent 和多 Agent。
- 登记规范索引使规则随入口送达并供判定适用；实际遵从仍需执行与审核，不因写成规范而自动保证。
- **阶段边界**：方案的设计与讨论过程，只允许修改对应的设计文档（`docs/` 下）；不修改任何代码（生产/测试）或其他文档（spec、BACKLOG、AGENTS.md 等）。读取与探查现状不受限。方案定稿并获授权进入实施后，方可修改代码与相关文档；不涉及设计取舍的纯实施/修复任务不受此限。

## 2. 何时落盘

- 讨论形成结论、改变已有方案，或留下影响实现的分歧时，必须更新对应设计文档；进入相关实现前完成记录。
- 实施及验证后更新实际结果和剩余缺口。
- 纯问答、无设计取舍的简单修改不强制新建设计文档；已有文档能够承载时，更新已有文档。

### 2.1 用户期望基线与持续核对〔强制〕

- 方案设计、评估、修订前，须核对并引用按[需求理解与澄清规范](REQUIREMENTS_ANALYSIS_SPEC.md)§2—§4建立的有效基线及用户消息／需求来源，在任务 `instruction` 或设计文档中记录引用。须实际核对原始问题、期望场景、结果、范围约束和验收是否足以比较方案，不把内部技术目标当用户期望，不因已有记录免核对。
- 基线缺失、理解冲突或关键歧义影响设计时，按需求规范§3返回澄清并暂停依赖部分；独立且已授权部分继续。共享确认原则由该节定义，不重复建立基线。
- 每个有意义的设计、评估、修订步骤及任务拆分、需求/方案变化、交付编码或 bug 修复、review 等阶段切换，均须对照基线检查是否仍解决原始问题、满足期望场景；在现有设计记录或交接中简记「符合/偏离/未验证 + 依据」，可引用复用，不要求逐命令记录。进入编码/修复/review 后按 [CODE_WRITING_SPEC.md](CODE_WRITING_SPEC.md) / [代码检视与合入规范](CODE_REVIEW_SPEC.md) 继续核对，不能在交接后丢失基线。
- 发现偏离须在已有授权内纠正并重新核验；拟改变用户目标、场景、范围或验收时，按需求规范§6.2返回澄清与确认，并同步设计记录和变更历史。不得只修改设计文档将偏离变成“符合”。

## 3. 落在哪里

- 设计文档放在 `docs/` 下；同一主题的连续演进归并到同一份文档，通过变更历史记录演进。设计文档的草稿载体与「先落草稿再转正」义务遵循[文档管理规范](DOCUMENT_MANAGEMENT_SPEC.md)。
- 有独立目标、范围和验收标准，可单独实施的较大方案可另建文档；相关文档必须互相引用，共同背景只保留一处，其余位置引用。
- 文档过长或包含多个独立决策时再拆分，不预先建立复杂目录体系。
- `docs/` 下维护设计文档索引，记录「主题 → 文档路径 → 一句话现状」；涉及设计的任务开始前，据此定位并阅读相关文档。

## 4. 记录什么

以下十项信息应能在文档或其明确引用的位置找到。不强制套满固定标题，小方案可合并章节、简短记录；尚未发生或不适用的内容如实标明。

1. **文档状态与关联**：草案/已决定/已取代，以及关联规范、代码和设计文档链接。
2. **背景与目标**：包含功能在系统中的定位，以及第 2.1 节核对的有效需求基线及来源（可引用）；需求信息及分层深度按需求规范§2、§4定义，设计须实际核对其是否支持本次方案比较，保留相关背景与设计目标。
3. **范围与约束**：边界、硬约束，以及明确的「不做什么」。
4. **选定方案**：描述方案本身，并标明状态；尚未选定时记录候选方案与待决事项。
5. **决策理由**：为什么适合当前目标与约束，依据的证据、代价与取舍；假设须明确标注。
6. **备选方案与未采纳原因**：记录实际考虑过的替代方案及排除或暂缓理由，无实际备选时不硬凑。
7. **验收标准与验证方式**：怎样算完成，以及如何验证。
8. **实施与验证结果**：实际改了什么、验证结果和剩余缺口，执行后更新；不能用测试计划冒充结果。
9. **风险、未决问题与异议**：记录已知风险、待确认事项、保留意见及其影响。
10. **变更历史**：保留实质决策变化及其原因，遵循第 6 节。

### 4.1 工程内容的适用性与深度

本节是按风险裁剪的工程内容检查维度，不是固定目录，不要求逐项成章；允许合并章节或引用可定位、版本和范围适用的有效材料。小方案可用简短文字说明，明显无关的工程维度可省略，不要求逐项填写“不适用”或另建全量适用性表。本节裁剪不改变§4十项信息须能定位、尚未发生或不适用时如实标明的要求。

负责人及设计参与者须结合有效需求、设计对象、复杂度和风险，检查下列内容是否为读者理解取舍、后续实施或验证所需；适用内容须在设计文档或明确引用的有效材料中具备足够细节。提案阶段可标明待补内容及查证动作；进入相关实现前补齐所依赖的适用内容，实施及验证结果仍在执行后更新。

- **摘要与现状**：较大或跨模块方案提供便于定位问题、选定方案及主要限制的摘要；说明与决策有关的现状、已有能力和约束，引用已有有效背景即可。
- **方案总览与图示**：存在组件交互、跨线程/进程、状态转移或关键时序且图示有助理解时，提供架构图、时序图或同等清晰的文字表达；标明参与者、边界、先后关系及关键拒绝、取消或失败路径。图与正文、接口和实际证据边界须一致，不以图代替细节或把示意写成已验证行为。
- **详细设计**：按受影响对象检查数据与身份归属、接口与契约、流程与状态、并发与资源生命周期、错误与恢复、性能与资源成本、安全与隔离、可观测性与证据关联。只展开影响本次正确性、取舍、实施或验证的部分；测试方案描述夹具和被测边界，文档或规则方案描述相应对象，不虚构生产接口、存储、指标或平台。
- **影响、引入与回退**：说明受影响模块、使用者、兼容性和外部依赖；需要部署、数据迁移、配置切换或测试资源引入时，说明引入步骤、失败处理和回退/清理边界。无相关变化可简记或引用既有流程，不要求编写无用迁移脚本。
- **验证与完成定义**：对应有效需求说明设计产物完成与实施、验证完成的区别，列出足以支持结论的场景、判定方式和证据范围。存在有来源且适用的关键指标时，定义计数对象、口径、适用范围及判定依据；比例须明确分母及未覆盖/缺证情形，区分预期、阈值和实测。无需量化时使用可核查的定性判据，不创造无需求依据的SLA或验收目标。
- **实施依赖与未决事项**：说明必要实施顺序、依赖、交付物；影响下一步的未知标明核验动作和承担者，区分阻断相关实施与可后续核实的事项。不虚构工期、责任人承诺或额外批准阶段。

对用户明确要求但排除、通常相关却省略、或省略会影响后续判断的内容，在对应取舍或范围说明中简记理由；信息深度随复杂度和风险调整。

### 4.2 设计流程与阶段回退

以下阶段用于定位设计依赖、完成条件和回退方向，不是固定目录或不可逆的单向流水线。可按复杂度与风险合并、简记或裁剪；但第 2.1 节的基线核对和第 4 节十项记录义务仍适用。每一阶段应能从现有设计记录中看出其依据、当前结论、未决项及下一步；不要求逐命令记流水账。

1. **核对需求基线、现状与约束。** 进入设计时引用有效需求基线，说明驱动本次取舍的目标、验收、相关现状和边界。退出本阶段前，确认这些信息足以界定比较范围；对基线及依据标记“符合／偏离／未验证”。基线缺失或关键歧义影响设计时，按需求规范返回澄清，暂停依赖该问题的部分；能独立判定的工作可继续。
2. **识别真实候选并确定比较判据。** 在存在实际取舍时记录考虑过的候选，并用同一组适用的需求/验收判据比较其优缺点、代价与限制；候选数量不设固定下限，不为满足数量而虚构方案。无实际备选时说明原因。比较所需信息不足时，先做与决策相关的查证或轻量方案分析，不要求对所有候选完成全量架构或详细设计。
3. **形成有依据的初选或决定。** 当现有比较证据足以支持取舍时，记录所选方向、理由、证据、代价、假设及未采纳或暂缓候选。证据仍不足时将选择标为暂定或未决，并说明需要的查证；不得将暂定写成已决定。
4. **深化所选方向的架构、接口与适用的详细设计。** 依据第 3 步初选，按第 4.1 节风险裁剪原则展开足以支持实施和验证的结构、契约、状态及关键失败/取消路径。若深化发现方案无法满足需求基线、关键约束或验收判据，返回第 2 步补充或调整候选，或返回第 3 步重新取舍；若问题来自需求理解，则按需求规范澄清后再继续。比较候选所必需的局部草图可以先于初选，但不因此要求为每个候选完成全量设计。
5. **制定验证及必要的引入、迁移和回退计划。** 依据需求验收说明设计产物及后续实施结果如何验证、所需证据范围，以及存在部署、数据迁移、配置切换或资源引入时的失败处理和回退/清理安排。无此类变化时可简记不适用。若计划无法覆盖关键验收或暴露不可接受的风险，返回第 2—4 步调整方案，或在需求基线不足时返回澄清。计划只描述拟执行的方法，不是实施后验证结果。
6. **检查取舍、基线对齐与未决事项。** 负责人检查记录是否能回答：方案是否仍解决用户问题（对基线为符合、偏离或未验证及依据）；为何选择该方向、证据和实际代价是什么；如何按验收判据验证。并核对关键图示、文字、接口契约和异常路径的一致性。记录异议，不将异议或未决内容写成共识；按能否独立判定成败拆分未知，阻断部分先查证或暂停，独立部分可以继续。此检查不要求固定多方会签或新增审批阶段。
7. **留痕决定、交接及后续状态。** 在相关实现开始前，记录设计文档状态、方案状态、选定方向、依据、适用范围、异议/未决项和变更历史，并说明下一步及其依赖。文档已定稿不等于方案已实现或已验证；实施及验证后按第 4 节第 8 项补记实际改动、结果、证据和缺口。阶段回退或需求变化时更新受影响结论及历史，不覆盖先前决定理由。

## 5. 状态区分

- **文档状态**：草案 / 已决定 / 已取代；被取代的文档应关联后继文档。
- **方案状态**：提案 / 已决定 / 已实现 / 已验证；按实际情况说明实现与验证范围，部分完成或待验证须明确披露。
- 文档状态与实施进度分别记录：方案已决定，不代表已实现；已实现，不代表已验证。
- 写进文档不等于达成共识，也不等于已实现；分歧和未决事项不得写成既定结论。

## 6. 变更历史

- 只记录影响目标、行为、接口或决策理由的实质变化，说明「原决定 → 新决定 → 改变原因」。
- 保留历史决策理由；当前方案可更新，但不得覆盖掉旧决定为何改变的依据。
- 不改变上述内容的文字修正交给 Git 历史，不要求逐条写入文档变更历史。

## 7. 责任

- **负责人（owner）**负责整理并实际核对文档，确保结论、状态、证据和剩余缺口一致；包括核对关键图文、契约与异常路径是否一致；检查结论可在现有交接中简记或引用。单 Agent 执行时由该 Agent 承担。
- **协作者**提供所负责部分的证据与异议，发现遗漏或与实际不符时及时提出。
- **最终答复者（final_responder）**依据已审核材料引用文档位置，说明结果与剩余缺口。
- 负责人/独立评估者须检查方案及交接是否对齐用户期望基线，交付结论明示「符合/偏离/未验证」及场景证据；未解决的目标偏离不能记为符合，关键场景缺证据须披露并补验，需调整目标或验收时交用户确认。
- 无法写入时如实披露原因、影响及待补内容，不声称已经落盘。

## 8. 控制范围

- 不逐轮复制聊天记录，不按对话轮次创建文件；记录可供后续理解与维护的设计信息。
- 不把测试计划当验证结果，不把文档记录当实施或验证完成，不覆盖历史决策理由。
- 不为形式增加无关章节、虚构备选方案或引入额外审核系统；信息深度随方案复杂度和风险调整。
