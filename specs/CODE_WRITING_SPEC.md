## 1. 目的与范围

本规范承接原编码与代码检视规范1.4.2的作者职责。独立资格、请求模板、规模、批准及合入规则以[代码检视规范](CODE_REVIEW_SPEC.md)§2、§6—§12为源；作者填写该规范§7模板、按§6统计规模，依§9逐项回应，不得自行关闭阻塞意见。每个功能指定一位作者，实际贡献与共同作者资格按该规范§12判断。本规范中的旧章号保留以便迁移核对。

- 主线为：设计可追溯、作者自查、非作者审核、证据绑定版本、满足门槛后合入。
- 本规范约束作者编码、自查、验证及返修。纯讨论或无代码变更的任务不因修改文档而自动进入代码审核流程。
- 讨论过程引用 [Agent 讨论约束规范](AGENT_DISCUSSION_SPEC.md)，设计适用性、阶段边界及留痕引用 [设计决策留痕规范](DESIGN_DECISION_RECORD_SPEC.md)，不重复其全文。
- coder 与 reviewer 开始工作前均须按项目入口及[规范索引](README.md)记录 `must_follow / not_applicable / uncertain` 三清单及理由；负责人将适用规范 id、版本、路径、关键条款与待澄清项传入任务 instruction。场景变化时复核，交付时提供遵从证据及缺口。
- `depends_on` 表示衔接关系，不代替逐项适用性判定。规范冲突交负责人／用户裁决，不自行设置优先级豁免。
- 标为「强制」的条款是门槛；建议目标不能冒充强制指标。

## 3. 分支与隔离〔强制〕

- 不同功能使用对应工作分支；没有适用分支时先创建，再开展代码修改。
- 禁止在 `main` 直接修改、提交或直接推送；`main` 只接收满足审核及合入门槛的合入。
- 修改前检查当前分支、基线与工作区。不得夹带其他功能改动，也不得丢弃或覆盖他人的未提交内容。
- 同一功能相关的生产代码、测试与文档可在同一审核单元中提交；无关功能须分开。

## 4. 设计对应与偏离〔强制〕

- **先核对用户期望基线**：任务开始及编码、bug 修复、自查、review 前，执行者须实际核对按[需求理解与澄清规范](REQUIREMENTS_ANALYSIS_SPEC.md)§2—§4建立的有效基线及其用户消息／需求来源，检查原始问题、期望场景、结果、范围约束与验收，记录于任务 `instruction` 或适用设计文档，可引用同一基线。协作者须核对摘要与用户原意，不能只按技术子任务推断目标；推断和未确认项按需求规范区分。已有需求稿不免除本条及[CODE_REVIEW_SPEC.md](CODE_REVIEW_SPEC.md)§8.1非作者独立核对。
- **澄清接口**：基线缺失或理解冲突、关键歧义影响当前工作时，按需求规范§3返回澄清并暂停依赖部分，独立已授权部分继续；共享确认原则引用该节，不重复建立基线。代码审核批准和合入操作授权仍按[CODE_REVIEW_SPEC.md](CODE_REVIEW_SPEC.md)分别判断。
- **每步对照与纠偏**：每个有意义的工作步骤（含编码、bug 修复、review 及返修）和任务拆分、需求/方案变化、阶段切换时，须对照基线检查当前动作及结果是否仍解决原始问题、满足期望场景。在现有自查、review 或交接记录中简记「符合/偏离/未验证 + 依据」，可引用复用，不要求逐命令记日志。发现偏离立即在已有授权内纠正并重新验证；拟改变用户目标、场景、范围或验收时按需求规范§6.2返回澄清与确认，并同步基线引用及适用设计记录，不能通过改写基线掩盖偏离。
- 每个功能点须说明「需求／设计条款 → 修改位置 → 为什么这样改 → 验证证据」。
- 是否需要设计文档，按 `design-decision-record-spec` 的 `applies_to / not_applies_to` 判定。无设计取舍的简单修复可对应明确需求或缺陷依据，不强造设计文档。
- 偏离已决定设计须按「提出偏离及影响 → 讨论决定 → 更新设计记录 → 再实现」闭环执行，保留原方案、新方案及改变理由。coder 单方面修改设计文档不等于偏离获得批准。
- reviewer 不接受偏离理由时，该问题阻塞合入，按讨论规范解决分歧；同时核查是否越过设计／实施阶段边界。

## 5. 编码与自查〔强制〕

- 作者自查覆盖适用的正确性、安全、并发、异常、性能、可读性、可维护性、测试、兼容与迁移、可观测性及协议状态一致性；涉及权限、并发、持久化或兼容性时检查对应维度，不适用说明理由。具体风险与测试有效性参照[代码检视规范](CODE_REVIEW_SPEC.md)§8.1，不能只交证据而不核实现。
- 作者执行[代码检视规范](CODE_REVIEW_SPEC.md)§8.3的分支必要性追问与五路处置；非作者仍须独立执行，不以自查替代审核。

- author 完整阅读本次 diff，包括新增文件；移除调试、临时及无关内容，确认改动遵守已决定设计与任务范围。
- 正式提交审核前完成相关本地运行与测试，记录命令、环境、结果、跳过项及未覆盖范围。语法检查不能替代行为测试。
- 允许在未完成时提前讨论方案或请求反馈，但须标明未完成项；提前讨论不等于正式审核通过或已具备合入条件。

### 5.1 边界校验与内部契约〔强制〕

在数据、控制或资源进入信任与契约边界时完成必要校验或规范化，明确可依赖的有效形态和错误行为。边界按数据来源与约束判断，不按函数层级；外部请求、持久化读入、第三方结果、公开入口按实际信任程度判断。

同一数据、同一已校验事实，在数据未修改、契约未失效且未进入使保证不再可信的新边界时，内部依赖契约，不重复校验或添加无依据的默认回退。状态、并发、事务、权限或环境变化时具体判断哪些保证失效，只重查受影响事实；跨函数或跨事务本身不自动要求重查。公共函数存在其他未校验合法入口时可能自身构成边界，须核全部相关调用路径。

### 5.2 分支用途〔强制〕

- 输入校验：在边界建立契约，重复校验须有新增事实或失效依据。
- 合法业务分支：表达需求选择，不因缺少失败测试便预设删除。
- 不变量断言：暴露内部契约破坏，不能承担必要输入或权限校验；诊断价值须有具体依据。
- 外部异常处理：合法输入下外部操作仍可失败，处理须有具体恢复、传播或清理效果，不吞错伪装成功。
- 资源清理与回滚：不因入口已校验而取消。诊断或性能用途须点名可见效果及依据，不以安全起见、以后有用作为充分理由。

## 11. 本地验证与交接〔强制〕

作者执行[代码检视规范](CODE_REVIEW_SPEC.md)§11的本地替代检查：按风险选择充分检查，记录版本、环境、命令、结果、跳过及未覆盖项，区分失败、未运行、跳过和不适用；确认副作用与隔离，区分模拟与真实验收。关键验收缺失不得自行豁免，本地通过不得称CI通过；非作者核对充分性并按需复跑。提交前填写该规范§7请求模板及§6规模统计。作者不得自批，合入另受该规范§10约束。

## 13. 文档同步与复盘〔强制〕

- 适用设计留痕规范时，实施及验证后同步设计文档中的实际结果、验证范围及剩余缺口，不把已实现写成已验证。
- 重大 bug 或反复返工须记录原因与防复发措施，按适用性沉淀回归测试、checklist 或 lint，不机械新增拦截机制。

### 13.1 现状图文同步〔强制〕

作者按[代码检视规范](CODE_REVIEW_SPEC.md)§13.1判断图文影响、在请求中给出具体结论，并将受影响图文随代码同步；无需更新须说明理由。延期仅由用户决定，形式与语义检查分别记录；跨分支按实际目标版本重评。完整规则与reviewer及合入者职责以该节为源。
