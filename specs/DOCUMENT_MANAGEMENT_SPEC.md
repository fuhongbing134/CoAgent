# 文档管理规范（Spec）

| 字段 | 值 |
|---|---|
| id | document-management-spec |
| version | 1.1.0 |
| status | final |
| applies_to | 项目主动维护、供持续使用或决策参考的文档之新增、更新、状态调整、移动、重命名、拆分、合并和删除，含规范、设计、草稿、入口说明、索引、计划及验收结论 |
| not_applies_to | 纯阅读、依赖库、自动生成物、会话与数据库运行态、临时探测产物的日常管理，以及一般的一次性原始日志 |
| depends_on | 无 |

适用性须按实际用途判断。一次性材料被持续引用时，须保护结论及必要证据的引用和历史完整性，原始证据可豁免状态表。

设计决策内容与理由遵循[设计决策留痕规范](DESIGN_DECISION_RECORD_SPEC.md)，协作讨论遵循[Agent 讨论约束规范](AGENT_DISCUSSION_SPEC.md)，代码变更遵循[编码与代码检视规范](CODE_REVIEW_SPEC.md)。

## 1. 分类、位置与索引

1. 新增文档须按用途归位。未正式进入项目或计划的方案、想法和讨论放入 `docs/drafts/`，已有实施或计划依据留在相应正式位置。混合材料须按具体内容与证据判断，可独立拆出的部分建立双向关联。
2. 须就近维护现有入口。`specs/README.md` 管规范，`docs/README.md` 管设计及相关资料，`docs/drafts/README.md` 管草稿，根目录说明沿用各自入口。新增、路径、用途或索引摘要变化时同步受影响索引。
3. 正文须保存完整依据，索引须提供准确摘要。两者冲突时须查证。索引收录仅表示可发现，内容有效性及授权须另据实际依据判断。
4. 索引与 README 条目按名称排序：直接列出文档/文件的清单按文档文件名（忽略大小写）字母序排列；按分区/入口组织的索引按入口路径字母序排列，无对应文件的纯记录条目排末尾；按分类/状态分组的清单保留组间语义顺序，组内按文档文件名字母序排列。新增或调整条目时同步维护排序。

## 2. 状态与依据

1. 凡陈述讨论、计划、实现或验证结论，必须区分这四类含义并给出相应依据，使读者能够辨认“讨论过、已计划、已实现、已验证”。
2. 文档成熟度／有效性、方案去向、计划与实施验证情况，按对读者有意义的维度表达，允许简短文字说明，豁免统一三栏和封闭词表。设计文档沿用“草案／已决定／已取代”等专项词汇。“已实现”可同时“待验证”。
3. 转正、入计划、废弃、取代及实现验证结论，须关联决定记录、计划入口或事实证据。依据不足须标记待确认，并披露部分完成或验证范围。
4. 当前执行依据须结合上述状态、证据及具体任务授权判断。文档批准、定稿或文件移动仅在实际授权范围内生效，方案实施仍须具备相应授权。

## 3. 变更、历史与缺失

1. 移动、重命名前须核对目标冲突、已有修改与引用范围，操作后更新当前有效引用。拆分、合并须保留必要作者、稳定编号、决策理由和后继关系，历史路径保留时须标清时间语境。
2. 废弃默认保留原因和必要历史。删除须具备已有授权，且必要历史或证据有留存位置、有效引用已处理。缺失文件须记录原路径、影响及待处理项，恢复须有依据与授权，禁止凭旧索引虚构正文。
3. 历史日志、原稿及观点修订须保留当时语境。补充当前结论时采用追加或清楚分隔的说明，保留旧结论及其改变原因。
4. 新增及本次改动触及的部分按本规范处理。相关旧问题在任务范围内纠正，范围外问题在交付中披露，既有材料采用渐进维护。

## 4. 检查与交付

| 改动影响 | 最低检查 |
|---|---|
| 错字或纯格式，且路径、状态、索引摘要均未变化 | 局部回读修改处，确认含义与中文正常，豁免索引更新和全仓引用搜索 |
| 新增、实质更新或状态调整 | 检查状态依据、受影响索引、涉及的链接及格式 |
| 移动、重命名、拆分、合并或删除 | 加查引用范围、目标冲突、前后清单和历史保留 |

交付须说明变更、实际检查结果及未解决项。新增及未跟踪文件须实际检查。图示渲染与代码测试按相关改动需要执行，报告须区分已执行和未验证部分。
