## 1. 分类、位置与索引

1. 新增文档须按用途归位。未正式进入项目或计划的方案、想法和讨论放入 `docs/drafts/`，已有实施或计划依据留在相应正式位置。混合材料须按具体内容与证据判断，可独立拆出的部分建立双向关联。
2. 须就近维护现有入口。`specs/README.md` 管规范，`docs/README.md` 管设计及相关资料，`docs/drafts/README.md` 管草稿，根目录说明沿用各自入口。新增、路径、用途或索引摘要变化时同步受影响索引。
3. 正文须保存完整依据，索引须提供准确摘要。两者冲突时须查证。索引收录仅表示可发现，内容有效性及授权须另据实际依据判断。
4. 索引与 README 条目按名称排序：直接列出文档/文件的清单按文档文件名（忽略大小写）字母序排列；按分区/入口组织的索引按入口路径字母序排列，无对应文件的纯记录条目排末尾；按分类/状态分组的清单保留组间语义顺序，组内按文档文件名字母序排列。新增或调整条目时同步维护排序。
5. 索引只收录随仓库交付的对象（含明确拟交付的未跟踪文档），不收录明确不交付的本地产物。索引中列出的文档或文件路径须写成可点击的 Markdown 相对链接（链接文本与目标同为相对文件名），便于直接跳转，不得只写反引号纯文本。

## 2. 状态与依据

1. 凡陈述讨论、计划、实现或验证结论，必须区分这四类含义并给出相应依据，使读者能够辨认“讨论过、已计划、已实现、已验证”。
2. 文档成熟度／有效性、方案去向、计划与实施验证情况，按对读者有意义的维度表达，允许简短文字说明，豁免统一三栏和封闭词表。设计文档沿用“草案／已决定／已取代”等专项词汇。“已实现”可同时“待验证”。
3. 转正、入计划、废弃、取代及实现验证结论，须关联决定记录、计划入口或事实证据。依据不足须标记待确认，并披露部分完成或验证范围。暂停、取消或废弃后，同任务须同步当前正文与活动入口状态，不得留下仍被当作有效的“运行中”或“下一步执行”指示；历史原文可保留并标明当时语境。

4. 当前执行依据须结合上述状态、证据及具体任务授权判断。文档批准、定稿或文件移动仅在实际授权范围内生效，方案实施仍须具备相应授权。

5. 本规范适用的人工维护文档，新增或修订均须先有可追溯的落盘草稿，不能以正式目录中文首标“草案”代替形成过程。新主题先在`docs/drafts/`保存草稿；讨论首次落盘本身即草稿阶段，不递归为草稿另建草稿。既有正式文档修订前，先在关联主题草稿记录拟改文本或补丁、目标位置、来源、接受情况与理由，再更新正式正文。机械修改也须留稿，可同任务多文件合写一条完整记录，不要求每文件全文复制或新增审批。
6. 转正须保留可追溯的草稿基线并建立双向关联；可迁移为正式文档，或在保留可核对的草稿基线及形成记录后原位转正，但仅改状态标签不满足前置留稿义务。后续修订在关联草稿追加清楚分隔的记录，不永久维护两份相同正文。既有文档不伪造过去草稿，从下一次修订执行并披露旧缺口；原始日志等排除对象仍按本文适用边界处理。

## 3. 变更、历史与缺失

1. 移动、重命名前须核对目标冲突、已有修改与引用范围，操作后更新当前有效引用。拆分、合并须保留必要作者、稳定编号、决策理由和后继关系，交付集合内仓库对象的历史相对路径保留时须标清时间语境；明确不交付产物的提及按本节第8条清理。
2. 废弃默认保留原因和必要历史。删除须具备已有授权，且必要历史或证据有留存位置、有效引用已处理。交付集合内仓库对象缺失时须记录当时仓库相对路径、影响及待处理项，供Git历史追溯；明确不随仓库交付的本地产物，其具体提及及替代标注按第8条删除；曾进入Git不构成保留豁免。恢复须有依据与授权，禁止凭旧索引虚构正文。
3. 历史日志、原稿及观点修订须保留当时语境。补充当前结论时采用追加或清楚分隔的说明，保留旧结论及其改变原因。
4. 新增及本次改动触及的部分按本规范处理。相关旧问题在任务范围内纠正，范围外问题在交付中披露，既有材料采用渐进维护。

5. 每份适用文档的“变更历史”小节须集中在文档最后，作为最后一个正文小节；新增正文及附录应插在其前，不得在历史表后继续追加正文或散落版本注记。过程分析、实验结果与证据可保留在正文对应章节，历史表用引用定位，不能相互替代。
6. 变更历史统一使用以下六列及顺序，不自行缩列或改为散文：`时间`、`版本／议题`、`原状态或决定→新状态或决定`、`原因与证据`、`提出／决定者及来源`、`影响范围`。首次创建原状态写“无”；小改可同批合并，但应能定位改动，未知信息如实标明，不为填表虚构决定。历史行按事件时间从近到远排列，最新版本／变更位于第一行，最老记录位于最后。秒级时间未知但版本或阶段演进关系已证实时，按有据演进倒序定位，不推断事件时间；无法确认先后的旧记录保留这些记录的原相对次序并明确说明定位依据及未知项，不以补录时间冒充事件时间。已知时间与版本关系冲突时须查证并披露，不盲目强排。
7. 自本版起，新发生的变更须在发生时获取实际时间，以`YYYY-MM-DD HH:mm:ss ±HH:MM`记录，精确到秒并含时区，禁止用日期或“本轮”替代可获取的时间。记录来源须可核对（如本机时钟命令或带时间的事件记录）。补录既往事件若无法确认其秒级时间，须保留原精度或写“事件时间未确认”并说明原因，同时另列实际秒级记录时间；不得用记录时间冒充事件时间，不得补零伪造秒数。既有无法确认的历史时间不强制追补。

8. 项目主动维护的所有文档（含草稿、废案、索引及历史章节），不得列出明确不随仓库交付的具体本地产物，包括其定位路径、材料类别标注、对象清单及依赖这些产物的入口说明，无论采用链接、代码块、表格还是纯文本。按忽略规则、明确不交付决定及实际交付范围判定，未跟踪不等于不交付。删除相关提及后，保留能在交付正文独立成立的历史事实、方法、结果、版本范围和限制；不能独立成立的结论须降格或删除，不编造替代来源，不以类别、事件标识或占位摘要继续介绍被删除的产物。抽象约束、合法产品接口与必要通用运行说明不在此删除范围。个人主机绝对路径不得作为定位引用；交付对象使用仓库相对路径，运行示例和生成物位置使用通用占位符并说明如何生成。公开URL可保留，产品接口名可解释机制，但不得借示例或接口说明保留具体旧证据定位。清理保留历史事实及版本范围，不要求重写Git历史或删除原始证据。

## 4. 检查与交付

| 改动影响 | 最低检查 |
|---|---|
| 错字或纯格式，且路径、状态、索引摘要均未变化 | 局部回读修改处，确认含义与中文正常，豁免索引更新和全仓引用搜索 |
| 新增、实质更新或状态调整 | 检查状态依据、受影响索引、涉及的链接及格式；核交付集合内相对链接可达、不交付产物提及及替代标注已清除，结论自足 |
| 移动、重命名、拆分、合并或删除 | 加查引用范围、目标冲突、前后清单和历史保留 |

交付须说明变更、实际检查结果及未解决项。新增及未跟踪文件须实际检查。图示渲染与代码测试按相关改动需要执行，报告须区分已执行和未验证部分。

检查还须核对前置草稿及基线关联、历史小节最后位置、六列字段顺序、历史倒序及未知项定位依据与新时间戳的秒级精度和时区；历史未知项须核查是否如实标注，不能以统一格式为由伪造。此次条款依据及拟改稿见[修订草稿](../docs/drafts/DOCUMENT_LIFECYCLE_HISTORY_DISCUSSION.md)。
