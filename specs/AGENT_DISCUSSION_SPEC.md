# Agent 讨论约束规范（Spec）

| 字段 | 值 |
|---|---|
| id | agent-discussion-spec |
| version | 1.3.1 |
| status | final |
| description | 多 Agent 协作中交换、质疑或协调观点，以及与用户交互处理歧义或分歧时，约束讨论参与者的独立判断、逐点回应、证据与异议记录，以及负责人的僵持裁决衔接、调用预算管理和交付审核，直至讨论因证据充分达成一致、条件被明确接受、用户裁决或无法继续取得证据而结束并交接。单 Agent 独立执行且无协作讨论的任务不适用；本规范不代替技术决策内容留痕或代码独立审核。 |

| not_applies_to | 单 Agent 独立执行、无协作讨论的任务 |
| depends_on | 无 |

> 本文档约束多 Agent 协作中「讨论」这一行为，确保讨论充分、观点与理由明确、分歧可收敛、结果可追溯。
> 后续实现项见根目录 `../BACKLOG.md`。

## 1. 目的与范围

- 适用于 Agent 之间的讨论（含与用户的交互）。
- 目标：任何一方可发起讨论；每方观点与理由必须明确；僵持可收敛到用户裁决；异议全程留痕可复盘。

## 2. 讨论发起

- **任何 Agent 都可发起讨论**：执行任务过程中，发现需求描述存在歧义、或不确定是否需用户决策时，可邀请其他 Agent 讨论。
- **「发起讨论」≠「任意启动其他 Agent」**：协作者应把议题、对象、原因交给负责人安排，不能擅自扩大任务范围。
- **协作者互邀**：当前协议仅 entry/owner 可邀请，协作者互邀的实现见 `../BACKLOG.md`。

## 3. 观点与理由

- **每方必须明确观点 + 明确理由**，理由不可模糊。理由应写清：主张、事实/证据、推导、适用条件、风险。
- **回应须先独立形成观点**：回应对方观点前，先独立提出自己的观点与理由，角度不局限于对方已提出的内容；回应时既逐点回应对方观点，也附上自己的独立观点，供对方再度回应。双方按此反复，直到证据充分达成一致；只评审对方观点而不产出自己的独立视角，不算完整回应。
- 提出必须、固定阶段或审批类要求时，须给出现行条款或用户要求及适用条件；无依据者只能标为建议。
- 无证据时标注「假设」；允许明确表示「证据不足，暂不判断」，不为表态编理由。
- **赞同/反对逐点对应**（统一编号）：赞同也要说明核查了什么、在什么条件下成立；不能以「全部接受」代替。
- **观点可变**：发现证据有误（自己或他人发现）、新证据、需求变化、推理漏洞，都可改变观点；必须明确表述「因什么而改变」，并记录「原观点 → 新观点 → 原因 → 影响哪些结论」，旧记录保留。
- **可反驳**：不必赞同对方理由；反驳必须回应对方最强理由，并指出能区分双方判断的证据或验证方法；新一轮须带来新推进，重复立场不算推进；可维持异议，不为收尾假装同意。

## 4. 僵持与用户裁决

- **不等到额度耗尽**：价值取舍、范围、成本等需用户决定时提前提交；技术事实争议若可核验，先核验。
- **连续两次完整回应无实质推进**时，由负责人判断是否转验证或升级用户裁决（建议阈值）。
- 提交用户裁决的表格：

| 议题 | 各方方案及理由 | 已确认事实/未确认假设 | 未解决分歧 | 各方案影响 | 需用户决定的问题 |
|---|---|---|---|---|---|

## 5. 对用户观点的异议

- 收到用户对话的任何 Agent，都需对用户观点做判断；觉得不合适或有遗漏，直接提出（不限于用户指定的 Agent）。
- 用户执意不改：按用户要求执行，但**最后必须补充记录**「哪个 Agent 不同意哪个观点 + 理由 + 时间戳」。
- **边界**：用户坚持不能让不可行操作变可行、不能补足第三方权限、不能突破必须遵守的限制；此时应明示障碍与替代方案，不能假装执行成功。

## 6. 负责人交付审核

- **职责**：负责人（owner）承担实际审核与纠正；最终答复者（final_responder）依据已审核材料汇总结果与剩余缺口。两项职责不能混同，即使由同一 Agent 承担也须先审核、后汇总。
- **逐项核对并留痕**：交付前核对以下五项，各一行记录「检查项：结论；依据或证据位置；有问题时的处理」。结论使用「符合 / 有问题 / 未验证 / 不适用」；不适用须说明理由。复用可读正文或现有 `handoff`，保留一份即可，不新增协议字段。显式填写不等于实质审核，必须实际核对材料。

1. 目标是否偏移了原始目标？核重启等变化后的有效基线及授权。
2. 是否扩大范围或增加不必要的复杂度？核授权范围，以及是否把无依据的必须、固定阶段或审批写成门槛。
3. 目标是否完成？核实际完成度，以及暂停、取消、废弃后的正文与活动入口状态同步。
4. 结论是否有证据？核新读、有效复用、缺失或失败的实际记录及版本来源；核成本、根因的观察、报告、推断和未知。项目维护文档的结论须独立可理解；不交付产物提及的清理及无法自足结论的处理按[文档管理规范](DOCUMENT_MANAGEMENT_SPEC.md)§3核对。
5. 缺口是否披露？核未读、失败、未验证和未完成部分是否准确，不能以披露替代可完成的纠正。

- **时机**：前两项贯穿全过程，在规划、准备扩展任务或机制、需求或方案变化时复核；执行中发现任何一项问题立即处理；交付前完整核对五项。
- **必要程度**：范围扩展须核对必要性与授权依据，比较更简单的替代方案；保留必要的深入与基础保障，不为轻量而漏做必要工作。
- **纠正**：发现问题先在已有授权内补做遗漏、核验证据、纠正结论、按需重新验证，或删减计划、暂停偏离部分、简化方案；不得借简化擅自删除已有成果。确实无法解决或需要用户取舍时，披露障碍、剩余缺口或请求决定；执行中应及时说明影响，不以等待纠正为由隐瞒问题。
- **交付边界**：不得把「目标未完成但已披露」记为审核通过；披露不能代替可完成的纠正。新增程序拦截按具体风险、证据、恢复难度、覆盖范围与成本单独决定，不预设实施顺序。

## 7. 讨论结束条件

- 可因以下任一情况结束：证据充分达成一致、条件被明确接受、用户裁决、无法继续取得证据。
- 关键歧义未解决时，暂停依赖该决策的部分；独立且已授权的工作可继续。
- **沉默、超时、预算用尽均不代表赞同**。

## 8. 预算与轮次

- **区分「调用预算」与「交锋轮次」**：当前 round_limit 是整个 job 的调用预算（含负责人/协作者/final 等调用），一次双方来回消耗多次调用。
- **默认上限 = 20**（已从 8 调整）。
- **提前预留**：进入等待前，负责人说明「已用/上限/剩余」并估计裁决后所需调用。
- **预算不足处理**：用户裁决后二选一——「继续并按需调整上限」或「按现有成果结束」；普通回答不隐含追加授权。
- **不重置（清零）`used`**：累计消耗始终保留。
- **作用域**：`round_limit`/`used` 按 `job_id` 隔离（per-job），只影响当前那一次讨论，不影响其他 job/默认值/全局配置。
- 近期用现有「调整上限」`set_limit` 处理预算追加；专用「追加 N 次」按钮与 B1 兜底见 `../BACKLOG.md`。
- 达到 100 上限后不清零绕过；可结束本任务、以摘要关联新任务。

## 9. 异议记录

- 使用稳定议题编号，记录：Agent、具体主张、理由与证据、提出时间、用户决定及决定时间。
- 时间戳格式：`yyyy-MM-dd HH:mm:ss +08:00`（本地时间 + 时区）。
- 最终仍未撤回的异议列出，已撤回的说明撤回依据，不重复阻挠已决定的工作。

## 10. 协议衔接

- **先不改状态机**（不新增 `discussing` 状态）。
- 观点编号、证据、回应放在可读正文与现有 `handoff` 中。
- 邀请用 `request_collaboration`；需用户选择用 `waiting_user + questions`。
- **等待用户裁决 = 方案 A**：预算耗尽前主动进入 `waiting_user` 挂起。
