# 编码与代码检视规范（Spec）

| 字段 | 值 |
|---|---|
| id | code-review-spec |
| version | 1.3.0 |
| status | final |
| applies_to | 编码与代码检视（coder 编码、reviewer 检视、合入代码变更） |
| not_applies_to | 纯讨论／无代码变更的场景 |
| depends_on | agent-discussion-spec, design-decision-record-spec |

## 1. 目的与范围

- 主线为：设计可追溯、作者自查、非作者审核、证据绑定版本、满足门槛后合入。
- 本规范约束编码及其检视、反馈、复查与合入。纯讨论或无代码变更的任务不因修改文档而自动进入代码审核流程。
- 讨论过程引用 [Agent 讨论约束规范](AGENT_DISCUSSION_SPEC.md)，设计适用性、阶段边界及留痕引用 [设计决策留痕规范](DESIGN_DECISION_RECORD_SPEC.md)，不重复其全文。
- coder 与 reviewer 开始工作前均须按项目入口及[规范索引](README.md)记录 `must_follow / not_applicable / uncertain` 三清单及理由；负责人将适用规范 id、版本、路径、关键条款与待澄清项传入任务 instruction。场景变化时复核，交付时提供遵从证据及缺口。
- `depends_on` 表示衔接关系，不代替逐项适用性判定。规范冲突交负责人／用户裁决，不自行设置优先级豁免。
- 标为「强制」的条款是门槛；建议目标不能冒充强制指标。

## 2. 角色与职责〔强制〕

- 每次审核请求明确 author（编码作者）、reviewer（检视者）、合入执行者及各自职责。
- author 必须自查，但不得批准自己的代码；合入至少需要 1 位非作者 reviewer 的有效批准。
- reviewer 不固定绑定某个 Agent，默认由负责人安排。负责人参与编码时，负责人身份不能充当独立审核资格。
- 负责人依讨论规范进行的交付审核与代码独立审核分别履行，不能用前者代替后者。

## 3. 分支与隔离〔强制〕

- 不同功能使用对应工作分支；没有适用分支时先创建，再开展代码修改。
- 禁止在 `main` 直接修改、提交或直接推送；`main` 只接收满足审核及合入门槛的合入。
- 修改前检查当前分支、基线与工作区。不得夹带其他功能改动，也不得丢弃或覆盖他人的未提交内容。
- 同一功能相关的生产代码、测试与文档可在同一审核单元中提交；无关功能须分开。

## 4. 设计对应与偏离〔强制〕

- **先确认用户期望基线**：任务开始及编码、bug 修复、自查、review 前，执行者须先复述并核对用户的原始问题、期望使用场景、期望结果、范围约束与验收判据，记录于任务 `instruction` 或适用设计文档；后续可引用同一基线及其用户消息/需求来源。协作者须核对传入摘要与用户原意，不能只按技术子任务推断目标；推断和未确认项须明确标注。
- **确认依据**：已有明确用户要求、澄清或授权可作为确认，无需每一步重复询问。影响目标、场景、范围或验收的歧义须先向用户澄清，再推进依赖部分；不依赖该疑点的已授权工作可继续。沉默或 Agent 内部共识不能替代用户确认。
- **每步对照与纠偏**：每个有意义的工作步骤（含编码、bug 修复、review 及返修）和任务拆分、需求/方案变化、阶段切换时，须对照基线检查当前动作及结果是否仍解决原始问题、满足期望场景。在现有自查、review 或交接记录中简记「符合/偏离/未验证 + 依据」，可引用复用，不要求逐命令记日志。发现偏离立即在已有授权内纠正并重新验证；若拟改变用户目标、场景、范围或验收，先说明原因与影响，暂停依赖部分并取得用户确认，再更新基线和设计记录，不能通过改写基线掩盖偏离。
- 每个功能点须说明「需求／设计条款 → 修改位置 → 为什么这样改 → 验证证据」。
- 是否需要设计文档，按 `design-decision-record-spec` 的 `applies_to / not_applies_to` 判定。无设计取舍的简单修复可对应明确需求或缺陷依据，不强造设计文档。
- 偏离已决定设计须按「提出偏离及影响 → 讨论决定 → 更新设计记录 → 再实现」闭环执行，保留原方案、新方案及改变理由。coder 单方面修改设计文档不等于偏离获得批准。
- reviewer 不接受偏离理由时，该问题阻塞合入，按讨论规范解决分歧；同时核查是否越过设计／实施阶段边界。

## 5. 编码与自查〔强制〕

- author 完整阅读本次 diff，包括新增文件；移除调试、临时及无关内容，确认改动遵守已决定设计与任务范围。
- 正式提交审核前完成相关本地运行与测试，记录命令、环境、结果、跳过项及未覆盖范围。语法检查不能替代行为测试。
- 允许在未完成时提前讨论方案或请求反馈，但须标明未完成项；提前讨论不等于正式审核通过或已具备合入条件。

## 6. 规模控制

- **强制**：一个审核／合入请求保持单一目的。
- **建议目标**：变更规模小于 400 行。按相对明确审核基线的「新增＋删除」统计，不采用净变化。
- 分别列出生产、测试、文档、生成文件的新增与删除量。生成文件及锁文件包含在总量内并单列，各分类避免重复计数。
- 超过建议目标须说明必要性及拆分取舍。不得靠压缩代码、省略测试或隐瞒生成文件规避统计，也不为凑行数破坏变更完整性。

## 7. 请求描述〔强制模板〕

无远程 PR 时，本地合入请求仍使用同样的信息结构；提交 commit 本身不等于完成审核。请求至少包含：

```text
作者／审核者／合入执行者：
分支／目标分支／审核基线／审核版本：
范围与规模（生产／测试／文档／生成文件，新增＋删除）：
背景与动机：
用户期望基线及来源（原始问题／场景／期望结果／范围／验收）：
对齐结论与依据／偏离及用户确认／未验证项：
改了什么：
为什么这样改：
需求或设计对应关系／偏离项及决定依据：
文档/图文影响结论（受影响文档与章节／已同步内容／无需更新理由）：
已执行验证（命令、环境、版本、结果、跳过与未覆盖项）：
风险与必要回退方式：
待执行测试计划：
```

不适用项说明理由；待执行计划与已执行结果分开，不用计划冒充通过证据。

## 8. 审核〔强制〕

### 8.1 检视范围与测试有效性

- reviewer 开始检视前须独立核对用户期望基线及来源，检查方案、实现、bug 修复和验证是否覆盖期望场景，而非仅检查代码符合内部设计或测试通过；缺少基线须先补齐，关键用户场景未验证须明示。
- reviewer 实际阅读改动及相关设计、验证证据，按影响与风险检视：正确性、安全、并发竞态、异常与错误处理、性能、可读性、可维护性、测试、兼容性与迁移、可观测性，以及协议与状态一致性。
- 涉及权限、并发、持久化或兼容性的改动，必须检查对应维度；不适用维度说明理由，不机械要求每项相同篇幅。
- 协议与状态一致性检查包括：`continue_work` 与邀请的配对约束、`questions` 与 `waiting_user` 的配对约束，以及消息终态与 lifecycle 的语义对应。以适用协议为准，不把单条已接收消息的完成误判为整个 job 必须完成；同时关注取消、迟到结果、幂等与事务边界。
- 检查测试是否测到真实目标，防止恒真断言、空测试或过度模拟造成假绿。只有正常路径而缺失相关失败／边界／回退路径时，应指出验证不足；语法通过或模拟通过不能冒充实际行为或真实后端验收。
- 涉及持久化或并发时，以日志、状态、reason 等适用证据确认失败后能否定位；不止口头列出可观测性维度。
- 涉及持续维护的现状图文（架构图、调用流程图及其说明、源码引用）事实变化时，按 §13.1 核对作者的影响结论与图文一致性。

### 8.2 评论与结论

- 评论写明「问题＋影响或理由＋建议」，使用稳定编号便于逐条回应。
- 分级：P0 为阻塞；P1 可阻塞，须明确是否阻塞及依据；P2／nit 为非阻塞。
- 一次列全已发现问题，修订后发现新问题仍可补充。避免纠缠个人风格，多用问题澄清理由，不为合入而批准。
- 审核结论为「通过／需修改／证据不足，暂不能通过」三态，不将缺失证据记为通过。
- reviewer 结论中须明示「用户期望对齐：符合/偏离/未验证」，附基线引用、场景验证证据和剩余缺口。未解决的目标偏离阻塞通过；关键场景证据不足不得记为符合，须补验或取得用户对调整验收范围的明确确认。
- 正式审核、批准、测试及本地检查证据绑定明确基线与具体被审核版本（commit）。后续改动须重新判断受影响的批准与检查是否仍有效，并补充必要复查；不沿用旧版本批准覆盖新改动。

## 9. 反馈与复查〔强制〕

- coder 逐条回应：已修复（附位置或证据）、不同意（附理由）、建议延期（附影响及安排）。
- 阻塞意见不能由 coder 单方面移入 backlog 后关闭；须经 reviewer 接受其解决方式，或交用户裁决，未解决前阻塞合入。
- 修订后 reviewer 重新检视该审核单元的全部累计改动（见下条），并复查受影响测试及是否引入新问题；测试选择按影响与风险确定，不机械重做无关检查，也不省略必要复查。
- **修复后复审范围（全量＋回归）〔强制〕**：每轮按 reviewer 意见修订后，reviewer 必须以已声明的审核基线为比较起点，重新检视该审核单元截至本轮的全部累计改动，包括此前轮次已审阅且本轮未再修改的内容，不得仅检视本轮增量或上轮问题涉及的行、文件；并评估该修复对其他功能与既有行为的回归影响，不能只核对问题本身是否已修好。「全量」指对全部累计改动逐一审视其正确性与相互影响，不等于对未改动的无关模块机械重做无关的独立检查。reviewer 在每一轮都须保持这一「全量＋回归」意识，避免逐轮退化为只检上一轮指出的 bug。若实际仅做局部核对，须在结论中明确「局部复审、未覆盖全量」及原因，且该结论不得作为对全量改动的通过。

## 10. 合入门槛〔强制〕

合入前同时满足：

1. 相关测试及适用的本地替代检查通过，验证范围充分。
2. 至少 1 位非作者 reviewer 对实际合入版本有效批准。
3. 无未解决阻塞项。
4. 提交历史清晰，核对目标分支及实际合入内容，无无关夹带。
5. 受影响的现状图文已按 §13.1 同步，或经 reviewer 接受「无需更新」理由。

审核批准不等于获得合入操作授权，合入执行者仍须依据现有用户授权执行。证据缺失如实记录「未验证／门槛未满足」，不得写成通过。

## 11. 本地替代检查〔当前 CI 缺失〕

- 当前项目未配置 CI，经用户确认采用本地替代检查。结果称「本地替代检查通过」，不得称「CI 绿灯」。
- 固定检查类别，每次按改动范围明确可重复执行的具体命令：功能行为测试、受影响回归、语法与 diff 检查；涉及前端或平台机制时增加相应专项检查。按风险说明选择理由，不要求所有任务机械执行同一套命令。
- 证据记录审核版本、环境、命令、通过／失败数量、跳过项及不适用理由；失败、未运行、跳过、不适用分别记录。关键验收缺失即门槛未满足，coder 不得自行豁免。
- reviewer 检查清单充分性与测试有效性，必要时复跑关键检查。代码变化后复核受影响证据。
- 执行前确认副作用并使用适当隔离环境，不盲目操作正在使用的数据库、会话或真实后端；模拟测试与真实验收分别标注。
- 若反复漏跑检查、环境差异导致问题，或参与者与合入频率增加，应重新评估 CI；本条不自动授权搭建 CI。

## 12. 单功能单作者〔默认强制＋兜底〕

- 每个功能指定一位编码作者；reviewer 默认只评不改，由原作者统一修订。
- 共同讨论、提建议或给示例不自动构成共同编码；须按实际审核范围与贡献判断作者资格。
- reviewer 实际修改待合入代码，或交接后保留前作者实现时，重新判定作者与审核资格。共同作者不能互签代替独立审核；没有合格非作者审核者则不合入。
- 不以更换提交人、分支或代提交掩盖实际作者。修改独立文档或临时脚本，也不自动成为所有代码的共同作者。

## 13. 文档同步与复盘〔强制〕

- 适用设计留痕规范时，实施及验证后同步设计文档中的实际结果、验证范围及剩余缺口，不把已实现写成已验证。
- 重大 bug 或反复返工须记录原因与防复发措施，按适用性沉淀回归测试、checklist 或 lint，不机械新增拦截机制。

### 13.1 现状图文同步〔强制〕

- 每次代码变更须判断是否影响持续维护的现状图文与说明：架构图、调用流程图及其说明、源码引用与行号定位。
- author 在提交审核前，于请求描述（§7）给出「文档/图文影响结论」：受影响文档与章节、已同步内容，或「无需更新」及与本次改动相关的具体理由。
- reviewer 独立核对影响结论与图文内容是否与实际代码一致；合入执行者确认实际合入版本包含已审核的更新。
- 受影响的现状图文随代码进入同一审核单元，默认在合入前完成同步；特殊延期须由用户明确决定，记录受影响范围与完成安排，未经批准不得自行延期。错误现状描述为阻塞合入项，严重级别按影响判断，不一律标为最高级；经用户批准的延期范围作为合入门槛（§10）的已确认例外。
- 合入后发现遗漏，由负责人安排补正，记录受影响版本、修正文档与验证结果。
- 跨分支合入、回移与冲突解决后，按目标分支实际版本重新判断影响，不沿用原分支结论；无需每次无关提交刷新整篇基线。
- 同步对象当前为 Markdown 内 Mermaid 图源与说明文字；存在导出图片时核对图片与图源一致。历史原稿保留当时语境；未实施提案若受实现影响，须复核其去向与理由。
- 形式检查（链接可达、图源解析/渲染）与语义核对（图文是否等于代码行为）分别记录证据，不把形式通过写成语义已同步；不据此新增 CI 或自动重写图文，自动检查按实际遗漏增补。

## 14. 变更历史

- 1.3.0：在 §13 新增「现状图文同步」、§7 请求描述增加「文档/图文影响结论」字段、§8 检视与 §10 合入门槛引用该条款。背景：entry-2927 用户提出代码修改后架构图/流程图及说明缺少同步约束，三端讨论后由用户批准；决策：以现状图文所陈述事实是否变化为触发，author 提交影响结论、reviewer 核对、受影响图文随代码同审核单元合入、合入后遗漏补正，跨分支按目标版本重新评估，形式检查与语义核对证据分离，不新增 CI 或自动重写。事实一致性原则沿用 document-management-spec，不重复义务。
- 1.2.0：在 §9 新增「修复后复审范围（全量＋回归）」强制条款。背景：多轮检视中作者与 reviewer 易陷入「检视所有改动提出问题 → 改问题 → 仅检视问题的改动」，后续复审逐渐退化为只核对上一轮 bug；决策：规定每轮修订后的复审必须相对已声明审核基线覆盖该审核单元的累计全量改动并评估回归影响，局部复审须明示且不构成全量通过，reviewer 全程保持「全量＋回归」意识；并统一检视范围（累计全量）与测试选择（按影响与风险）口径。
