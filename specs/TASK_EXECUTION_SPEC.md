## 1. 目的与衔接

使任务围绕用户目标推进，以充分证据作判断，在满足验收后及时交付。进入任务时沿用 [规范索引](README.md) 的适用性判定和传递方式；该入口建立读取义务，不保证实际遵从。

需求基线内容及其变化回流遵循[需求理解与澄清规范](REQUIREMENTS_ANALYSIS_SPEC.md)；设计取舍、设计交付物及实现授权遵循[设计决策留痕规范](DESIGN_DECISION_RECORD_SPEC.md)；协作讨论遵循[讨论规范](AGENT_DISCUSSION_SPEC.md)；作者实现/自查与非作者检视/合入分别遵循[代码编写规范](CODE_WRITING_SPEC.md)和[代码检视规范](CODE_REVIEW_SPEC.md)；维护文档的归位、索引、历史及复盘落稿遵循[文档管理规范](DOCUMENT_MANAGEMENT_SPEC.md)。本规范唯一规定跨阶段状态记录、阶段门、回退后的下游复核和通用执行判断；不复制上述专项义务，也不依赖 skill 发现或按需加载。

## 2. 原生能力与必要前提

涉及能力判断、工具接入或方案选择时，先查与目标相关的已有实现、原生功能和必要前提，优先利用现有能力。根据需要查阅实现、权威资料或执行最小核验；版本、信任、权限等仅在影响判断时核对，不要求每任务遍历全部条件。

提出新增机制前，说明现有能力不能满足的具体场景及新增机制的收益、代价。已知资料充分时可直接形成判断；不能把未找到证据写成能力不存在，也不能把不同工具的正常使用路径判成缺陷。

## 3. 充分验证与停止条件

从用户目标、验收要求和风险确定关键问题、充分证据及停止条件，先采用能回答问题的简单验证。满足验收且无影响结论的未解决问题时应交付。扩展查证、实验或机制须对应未解决场景、失败原因或必要保障，并简记理由与新增成本；不得把内部研究兴趣扩大为用户目标。

“最小”不能省略关键正确性、安全、异常路径或专项规范要求的检查。已有授权内的必要纠正继续完成，不为增加步骤重复请求许可；改变目标、范围、验收或超出授权时按既有规则处理。无法继续取得关键证据时披露限制，不把披露视为完成验收。

## 4. 证据适用性与结论更新

引用本端或他端结论前，核对会影响判断的对象、版本、环境、时间或会话范围，区分直接观察、他端报告和推断。已有证据仍适用时允许复用，不要求逐次重新探测；存在变化迹象、冲突或用户要求最新状态时，补充核验相关部分。

新证据或条件变化影响结论时，及时更新当前判断，说明原结论、替代结论、原因和影响；历史记录保留当时适用范围，持续维护的文档按文档规范更新。当前成功不能自动补足历史实验缺失的证据。

## 5. 实际动作与完成陈述

“已重读、已执行、已检查”等陈述须对应所称时间范围内实际动作及记录；声称“本轮”时须有本轮对应记录。复用先前正文或结果时说明来源与适用性，不称为本轮重读或执行。用户要求读取最新版或已知内容改变时，实际重新加载所需内容后再据此执行。

交接须区分本次新读、有效复用、缺失或失败，并核对象版本与来源适用性。对随仓库交付的对象使用仓库相对路径；交接内容落入项目维护文档时，明确不交付产物的提及及替代标注按[文档管理规范](DOCUMENT_MANAGEMENT_SPEC.md)§3处理。

推理、设计或讨论完成可以对应产物和论据证明，不强制额外工具调用。区分计划、尝试、执行成功、检查通过及整体完成，不用局部成功替代整体验收。交付简记实际结果、依据及缺口，检查深度与影响相称。

## 6. 记录与维护

复用 instruction、handoff 或可读正文记录目标及停止条件、关键依据、实际结果与缺口。简单任务可合并成一句，信息充分时引用已有记录；不要求每任务新增表格、协议字段或独立文档。负责人审核仍按专项规范完成。

规则正文保持单一来源，案例与取舍保留在[共识及复盘记录](../docs/drafts/SKILL_MECHANISM_DISCUSSION.md#entry-2855-教训长期承载形式共识提案)。后续问题先区分执行失败与规则缺失，再修正对应执行或条款，避免每次失败新增规则。生效须有用户决定，并同步正文、索引及相关状态；行为效果须由后续实际任务验证。

## 7. 需求阶段导航与统一状态

本节只规定跨阶段导航和统一状态记录。每项具体义务仍以本节列出的专项规范为唯一权威来源；同一需求可因不同阶段动作同时适用多份规范，但不得用本节替代专项检查，也不得在多个规范重复规定同一义务。追踪范围止于该需求落地，不管理运行反馈、后续运行变更或退役。

### 7.2 每需求状态记录

每条可追踪需求在 `docs/requirements/tracking/` 有一份独立 Markdown 记录，按稳定需求编号命名。`docs/requirements/` 中的正式需求文档仍是需求定义和基线正文；状态记录仅保存统一状态、阶段结论、证据引用和迁移历史，不复制需求或设计正文。目录入口与空白模板见 [`docs/requirements/tracking/README.md`](../docs/requirements/tracking/README.md) 和 [`需求状态记录模板`](../docs/requirements/tracking/REQUIREMENT_STATUS_TEMPLATE.md)。

主状态为：`待澄清 → 已基线 → 设计中 → 设计就绪 → 实现中 → 待检视 → 待验收 → 已验证`。状态表示当前所在阶段或已完成的最后阶段：需求材料尚不足以建立基线时为“待澄清”；基线经需求阶段负责人核对后为“已基线”；有设计取舍时由设计负责人在开展设计后记录“设计中”，满足设计规范交付及实现授权条件后记录“设计就绪”；开始实现后为“实现中”；作者自查形成可交接审核单元后进入“待检视”；适用的检视/合入关口通过并进入需求验收后为“待验收”；需求验收证据充分后为“已验证”。无设计取舍时可由“已基线”进入“实现中”；无代码变更时跳过“待检视”，但仍需记录适用的需求验收状态。每次迁移由当前阶段负责人记录证据、版本和迁移依据；交接由前一阶段负责人记录交付证据并提出目标状态，下一阶段负责人确认接收后推进其阶段状态。发现问题需要返修时，发现方记录问题与受影响范围，并将相关下游结论标为“待复核”；该标记是状态记录中的复核标记，不替代主状态。 “已合入”“已发布”等是单独事实/状态，仅任务实际涉及且证据存在时记录，不得与“已验证”合并。不指定固定的全程状态管理员。

状态记录至少包含：需求编号/标题/正式基线链接及版本；当前状态；阶段适用性及裁剪理由；每阶段交付物链接与版本；验收判据及逐项结果/证据；状态变更时间、推进人、依据和目标版本；合入/发布等独立事实（若适用）；返修根因、受影响范围、复核结果及证据复用理由（若发生）。

### 7.3 回退、返修与复核

严重问题是影响需求达成、接口契约或关键验收标准的问题。按根因回到受影响阶段：需求目标/范围/验收错误回需求分析；设计不可行或实现偏离设计回方案设计；代码缺陷回实现；集成或验收失败按根因返回实现、设计或需求阶段。一般问题可在当前阶段处理。

返修时保留原状态与证据历史，并将所有受影响的下游结论标为待复核。返修后，所有受影响修改及其验收结论都须重新验证；未受影响证据仅在负责人确认其对象/版本/判据仍适用并记录依据后复用。全部受影响复核通过后，阶段负责人才能继续推进状态。目标、范围或验收标准变化同时按[需求规范§6.2](REQUIREMENTS_ANALYSIS_SPEC.md#6-交接变化回流规范衔接与效果边界)回流并更新需求基线。
